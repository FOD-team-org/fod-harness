## 0. 요약

- 새 폴더(`~/Desktop/wisepharm`)를 **워크스페이스 루트**로 만든다. 하네스 상태·문서·판단·백로그는 모두 여기 있다. 제품 레포 3개는 **멤버**로 등록만 한다.
- task 마다 대상 레포(`repo`)를 하나 정한다. 워크트리·검증·병합은 그 레포에서 한다.
- 레포를 넘는 기능은 task 여러 개로 쪼개고 `의존`으로 순서를 건다. 앞 task 가 그 레포 main 에 병합돼야 다음 task 가 시작된다. 지금은 사람이 "앞 레포 끝남"을 확인해 넘겨 주는데, 이 확인이 자동이 된다.
- 멤버 레포 폴더에서 `fodh` 를 쳐도 워크스페이스 창이 열린다.
- 두뇌는 멤버 main 체크아웃을 **읽기만** 한다. 멤버 main 을 바꾸는 길은 `fodh worktree merge` 하나다.
- 한 레포 모드(지금 방식)는 "멤버가 자기 자신 하나인 워크스페이스"로 같은 코드 경로를 탄다. 기존 설정·문서·출력은 바뀌지 않는다.

## 1. 목표와 비목표

목표

1. 한 창에서 WisePharm 전체 백로그를 진행한다.
2. 레포를 넘는 순서(스키마 web → API backend → 화면 app)를 하네스가 지킨다.
3. 두뇌 경계(소스 직접 수정 금지, 비밀 읽기 차단, 승인 필수 동작)가 멤버 레포 전체에 똑같이 걸린다.

비목표

- 레포 병렬 실행. Codex 는 워크스페이스 전체에 1개다(SL1 2026-09-28 부터 슬롯은 프로젝트별, 워크스페이스 = 프로젝트 1개).
- task 하나가 여러 레포를 바꾸는 것. task 하나 = 레포 하나 = 워크트리 하나 = 병합 하나.
- 자동 push. 병합은 멤버 레포 로컬 main 까지만 한다.
  - push 는 지금처럼 하네스 흐름 밖에서 한다(승인 판단 → 사용자).
  - 로컬 main 에 병합되면 다음 레포 task 가 `../chemical` 같은 상대경로로 바로 읽는다. 그래서 레포 간 흐름에 push 는 필요 없다.
- 멤버 레포 main 체크아웃 정리. 하네스는 워크트리만 만들고 지운다. 멤버 main 의 `dist`·`node_modules` 등은 건드리지 않는다(사용자 개발 서버 보호).

## 2. 모양

```
~/Desktop/
  wisepharm/                ← 워크스페이스 루트 (자체 git 저장소, 원격 없음)
    .pi/harness.json        ← workspace.repos 로 멤버 등록
    .pi/…                   ← 상태·원장·잠금·codex 기록 (한 벌)
    .claude/settings.json   ← 두뇌 훅
    CLAUDE.md               ← 관리 블록: 멤버 목록·레포 규칙 위치·레포 간 규칙
    docs/backlog.md         ← 레포 열이 있는 백로그 한 벌
    docs/판단대기.md · 판단기록/ · 작업일지/ · 위임스펙/
  chemical/                 ← 멤버 web     (.git/fodh-workspace 표지)
  wisepharm-backend/        ← 멤버 backend (.git/fodh-workspace 표지)
  wisepharm-app/            ← 멤버 app     (.git/fodh-workspace 표지)
  wp-web-T03/  wp-be-T04/  wp-app-T05/   ← task 워크트리 (각 멤버의 형제)
```

- 두뇌(`claude -p`)의 작업 폴더는 워크스페이스 루트다.
- 워크트리는 지금처럼 멤버의 형제 폴더(`worktrees.root` 기본 `..`, 멤버 기준)에 만든다. 그래야 워크트리 안 스크립트의 `../chemical`·`../wisepharm-backend` 상대경로가 멤버 main 체크아웃을 가리킨다(이관 설계 §3 전제 그대로).
- 한 레포 모드: `workspace` 설정이 없으면 암묵 멤버 하나(이름 `.`, 경로 = 루트)로 본다. 백로그 레포 열·표지 파일·`--repo` 인자는 쓰지 않는다.

- web 은 test 스크립트가 없어 lint + tsc 가 필수다.
  - heavy `npm run build` 가 node_modules 심볼릭 링크 워크트리에서 도는지는 적용 파일럿에서 한 번 확인한다.

- 패턴과 명령은 적용 때 각 레포 `package.json`·`scripts/`·AGENTS.md·CI 와 한 번 더 대조한다(§12).

### 3-2. 규칙

| 키 | 규칙 |
|---|---|
| `workspace.repos` | 객체, 멤버 1~8개. 있으면 워크스페이스 모드 |
| 멤버 이름 | `^[a-z][a-z0-9-]{0,15}$`. `.` 은 예약(한 레포 모드) |
| `path` | 루트 기준 상대경로.<br>• realpath 가 디렉터리이고 `.git` **디렉터리**가 있어야 한다(연결 워크트리·서브모듈 거부).<br>• HOME·`/`·워크스페이스 루트 자신·그 조상·그 안쪽은 금지.<br>• 멤버끼리 같거나 서로 포함하면 안 된다 |
| `baseBranch` | 기본 `main`. 워크트리는 이 브랜치에서 갈라지고, 병합은 멤버 체크아웃이 이 브랜치일 때만 한다 |
| `worktrees` | 멤버마다 `root`(기본 `..`, 멤버 기준)·`prefix`(필수)·`links`·`setup`·`setupTimeoutMinutes`.<br>• `links` 는 **멤버** 기준으로 검사한다(지금 `config.ts` 213-222 는 루트 기준).<br>• (워크트리 폴더, prefix) 쌍은 멤버끼리 겹치면 안 된다 |
| `verify` | 멤버마다 `commands`(필수, 비어 있으면 설정 오류)·`heavy`·`timeoutMinutes` |
| `secrets` | 멤버마다 `readDeny`·`readAllow`. 기본 목록과 최상위 `secrets` 에 더한다.<br>• `/` 가 있는 패턴은 그 멤버 경로 기준이다.<br>• `/` 가 없는 파일 이름 패턴은 **모든 멤버와 루트에 걸린다**(예: web 의 `neon_api.json` 은 backend 에서도 막힌다). 막는 쪽으로만 넓어지므로 그대로 둔다 |
| `approvalRules` | 멤버마다 추가. 최상위 규칙과 합쳐 두뇌 명령 전체에 건다(명령이 어느 폴더에서 돌든). id 는 전체에서 중복 금지 |

- 워크스페이스 모드에서 최상위 `verify`·`worktrees.prefix/links/setup` 이 있으면 설정 오류로 막는다("워크스페이스 모드에서는 workspace.repos.<이름> 아래에 둡니다"). 값이 두 곳에 있으면 어느 쪽이 쓰였는지 헷갈리기 때문이다.
- `cleanup.rebuildablePaths` 는 워크스페이스 루트 기준으로만 쓴다(멤버 main 은 정리하지 않는다).
- `workspace` 는 통째로 승인 전용 키다. 하네스가 병합하는 곳을 넓히기 때문이다. 두뇌는 바꿀 수 없다.
  - 지금 `approvalConfigKeys`(`config.ts` 321행)는 부모 키만 같은지 본다. `workspace.repos.web.path` 같은 하위 키도 잡도록 `key === k || key.startsWith(k + '.')` 로 고친다.
- 설정을 읽을 때마다 멤버 경로 검사를 다시 한다. 멤버 폴더가 사라지거나 옮겨지면 그 멤버 task 만 막는 게 아니라 설정 오류로 창을 열지 않는다(`fodh doctor` 가 원인을 보여 준다).

## 4. 멤버 표지와 실행

### 4-1. 표지

- `fodh workspace add` 가 멤버의 `.git/fodh-workspace` 에 워크스페이스 루트 절대경로 한 줄을 쓴다. `.git` 안이라 커밋·상태에 나타나지 않는다.
- 하네스가 멤버 `.git` 에 쓰는 것은 세 가지다.
  - 이 표지
  - `info/exclude` 의 워크트리 `links` 줄(지금 `linkDependencies` 동작과 같다)
  - `git worktree` 메타데이터
- 표지가 가리키는 워크스페이스의 `workspace.repos` 에 그 멤버 경로(realpath)가 있어야 유효하다.
  - 없으면 "표지가 맞지 않습니다: <워크스페이스>에서 fodh workspace list" 오류를 낸다(조용히 무시하지 않는다).

### 4-2. 창 열기

| 치는 곳 | 결과 |
|---|---|
| 워크스페이스 루트 | 워크스페이스 창 |
| 멤버 레포 안(어느 하위 폴더든) | 표지를 따라 워크스페이스 창. 첫 줄에 `워크스페이스 wisepharm (멤버 web 에서 열림)` |
| 멤버 레포의 연결 워크트리 안(task 워크트리든 사용자 워크트리든) | **거부**: "멤버 web 의 워크트리 안입니다 — 워크스페이스 <경로>에서 여세요" |
| 워크스페이스 루트의 task 워크트리 안(한 레포 모드) | 지금처럼 거부 |
| 표지 없는 일반 레포 | 지금처럼(자기 `.pi/harness.json` 또는 설치 질문) |

- `projectRoots` 는 git 최상위에서 멈출 때 `.git/fodh-workspace` 를 먼저 본다. 표지가 유효하면 그 레포 자신의 `.pi/harness.json` 보다 앞선다.
- 연결 워크트리 판정은 commondir 기준이다. 지금 `cli/root.ts` 14-33 은 commondir 레포의 옛 상태만 본다. 그런데 그 옛 상태는 새 워크트리를 모른다. 그래서 `<commondir>/fodh-workspace` 가 있으면 연결 워크트리는 모두 거부한다.
- `resolveCliRoot`(`fodh state get` 같은 하위 명령)도 같은 순서로 표지를 따른다. backend 처럼 옛 `.pi/harness-state.json` 이 남은 멤버에서 옛 하네스를 건드리지 않게 하려는 것이다.
- 표지가 있으면 멤버 자신의 하네스는 `startPlan`·`fodh init` 모두 거부한다("이 레포는 워크스페이스 <경로>에 속합니다"). 같은 레포에 두뇌 두 개가 붙지 않는다.

### 4-3. 명령

| 명령 | 동작 | 누가 |
|---|---|---|
| `fodh workspace init --repo web=../chemical --repo backend=… --repo app=…` | 빈 폴더(또는 하네스 없는 폴더)에서 `fodh init` + `workspace.repos` 작성 + 표지 기록. 멤버 검사를 모두 통과해야 무엇이든 쓴다 | 사용자 터미널 |
| `fodh workspace add <이름> <경로>` / `remove <이름>` | 멤버 추가·제거. 제거는 그 멤버의 미완 task·워크트리가 없을 때만 한다. 표지도 함께 지운다 | 사용자 터미널(`--approve`) |
| `fodh workspace list` | 멤버·경로·표지·현재 브랜치·미커밋 여부·옛 하네스 유무 | 누구나(두뇌 포함) |

`workspace init` 의 첫 커밋

- 워크스페이스 루트에 저장소 로컬 `user.name`·`user.email` 이 없으면 멤버들의 저장소 로컬 명의를 본다.
  - 모두 같으면 그 값을 워크스페이스 저장소 로컬 설정으로 복사한 뒤 커밋한다.
  - 다르거나 없으면 첫 커밋을 건너뛰고 "`--identity '이름 <메일>'` 로 다시" 안내를 낸다.
  - 전역 명의로 조용히 커밋하지 않는다. `-c user.*` 도 쓰지 않는다.
- 다음 안내는 `/project-start`(새 제품 인터뷰)가 아니다. "`fodh` 로 창을 열고 첫 백로그를 요청합니다(`fodh backlog add --repo …`)"다.

멤버 추가 조건(하나라도 어기면 아무것도 쓰지 않는다)

1. 멤버에 살아 있는 `.pi/harness.lock` 이 없다. 옛 하네스 상태가 `IDLE`·`DONE_ALL`·`PROJECT_READY` 이거나 `.pi` 가 없다.
2. 다른 워크스페이스 표지가 없다.
3. 그 멤버 prefix 로 시작하는 브랜치 가운데 `baseBranch` 에 **병합되지 않은** 것이 없다(`git branch --no-merged <baseBranch> --list '<prefix>*'` 가 비어야 한다).
   - 병합된 옛 브랜치는 허용한다. 그래야 멤버를 뺐다가 다시 넣을 수 있다. 브랜치 삭제는 push-main 급 승인이라 강제하지 않는다.
   - 대신 task 워크트리를 만들 때는 이렇게 한다. 같은 이름 브랜치가 있는데 그 task 가 상태 `worktrees[]` 에 없으면(= 이번 워크스페이스가 만든 게 아니면) 이어 쓰지 않고 거부한다("옛 브랜치 <이름>이 남아 있습니다 — 사용자가 지운 뒤 다시").
   - 지금 `createWorktree` 는 같은 이름 브랜치를 이어 쓴다(회수 뒤 재개용). 위 거부와 새 prefix(`wp-be-`)가 backend 에 남은 파일럿 브랜치 `wpb-wt-T01`·`T02` 사고를 막는다.

## 5. 백로그와 흐름

- task 에 `repo`(멤버 이름)를 더한다. 백로그 표에서 `레포` 열은 `분류` 다음에 온다.
  - 이 열은 워크스페이스 모드에만 있다. 한 레포 모드 표는 지금과 글자까지 같다.
  - `renderBacklog`·`parseBacklog`·`backlogInSync` 는 모드 인자를 받는다.
- `fodh backlog add --repo <이름>` 은 워크스페이스 모드에서 필수다.
  - 없는 멤버 이름이면 거부한다.
  - 워크스페이스 루트 task(`repo: "."`)는 두지 않는다. 루트 `docs/` 는 두뇌가 직접 쓰는 곳이고, task 는 멤버 코드를 바꾸는 단위다.
- `repo` 는 status `ready` 이고 워크트리가 없을 때만 바꿀 수 있다.
  - `backlog.md` 를 손으로 고쳐 들여올 때도 같은 검사를 한다.
  - 진행 중 task 의 `레포` 칸이 바뀌어 있으면 들여오기를 거부한다(다른 보호 칸과 같은 방식).
- 레포 간 순서는 `의존` 으로만 건다. PICK 은 지금처럼 의존 task 가 모두 `done`(병합 커밋 포함)일 때만 고른다. 그래서 "앞 레포 병합 뒤 다음 레포 시작"이 새 코드 없이 지켜진다.

예) 새 복약 필드

| ID | 제목 | 분류 | 레포 | 의존 |
|---|---|---|---|---|
| T01 | 복약 필드 스키마·마이그레이션 파일 | non-design | web | |
| T02 | schema:sync + API + openapi:export | non-design | backend | T01 |
| T03 | sync_openapi + generate_api + 화면 | design | app | T02 |

- T01 의 운영 DB 적용(`db:migrate`)은 task 안에서 하지 않는다. 승인 규칙이 두뇌를 막고, 두뇌는 `[승인]` 판단을 올린다(지금과 같음). T02 에 필요한 것은 마이그레이션 **파일**이 web main 에 들어간 것뿐이다.
- 두뇌가 task 하나로 두 레포를 고쳐야 한다고 판단하면 task 를 쪼갠다. 이 규칙을 스펙 스킬(`fodh-spec-writing`)에 한 줄로 넣는다.

## 6. 레포별 git 동작

`repoOf(task)` 는 멤버 이름·realpath·설정을 돌려준다. 한 레포 모드면 루트 자신이다. 지금 루트 기준인 git 호출을 모두 이것으로 바꾼다.

| 단계 | 지금 | 워크스페이스 모드 |
|---|---|---|
| 워크트리 생성 | 루트 HEAD 브랜치에서 `<root>/../<prefix>T` | 멤버 `baseBranch` 에서 `<멤버>/<worktrees.root>/<prefix>T`.<br>• 멤버 체크아웃이 다른 브랜치여도 base 는 `baseBranch` 다.<br>• `links`·`setup` 은 그 멤버 설정을 쓴다.<br>• 상태 `worktrees[]` 에 `repo` 를 기록한다 |
| 검증 | 워크트리에서 `verify.commands` | 워크트리에서 그 멤버 `verify.commands` |
| 커밋(`fodh worktree commit`) | 워크트리 | 그대로(워크트리). 레포별 명의·pre-commit 훅이 그대로 돈다 |
| 검수 커밋 확인 | 루트에서 rev-parse | 멤버에서 |
| 병합 기준점(REVIEW→MERGE) | 상태 `mergeBase` = 루트 HEAD | **task 의 `merge.base`** = 멤버 `baseBranch` 끝(§6-3) |
| 병합 | 두뇌가 루트에서 `git merge` | **`fodh worktree merge <T>`**(§6-1) |
| 병합 커밋 확인 | 루트 | 멤버 |
| 작업일지·백로그 커밋(DOCS·CLEANUP) | 루트 | 워크스페이스 루트(그대로) |
| 워크트리 제거 | 루트에서 `git worktree remove` | 멤버에서 |

### 6-1. `fodh worktree merge <T>` (새 명령, 두 모드 공통)

1. 조건 확인: 상태 `MERGE`, 현재 task = T, `repoOf(T)` = 멤버 M.
2. 원장에 `worktree:merge` `pre` 를 남긴다. evidence 는 `{repo, branch, review: review.commit, baseTip}` 이다.
3. **이미 병합됨**: M 의 `baseBranch` 끝이 병합 커밋이고 둘째 부모가 `review.commit` 이면 git 을 건드리지 않고 7로 간다. 기록 도중 끊긴 뒤 다시 돌린 경우다.
4. **남은 병합**: M 에 `MERGE_HEAD` 가 있으면 둘로 나눈다.
   - 그 값이 `review.commit` 이고 원장에 이 task 의 `pre` 가 있으면 하네스가 남긴 것이다. `git merge --abort` 로 되돌리고 계속한다.
   - 아니면 사용자 병합이다. 건드리지 않고 오류를 낸다.
5. 사전 검사. 하나라도 어기면 오류를 낸다.
   - M 체크아웃 브랜치 = `baseBranch`.
   - 추적 파일 미커밋 변경이 없다(`git status --porcelain --untracked-files=no`).
   - task 브랜치 끝 = `review.commit`.
   - `task.merge.base` 가 `baseBranch` 끝의 조상이다.
   - 무시되지 않은 추적 안 된 파일이 있으면 **경고만** 한다. 개수와 앞 몇 개 경로를 출력하고 원장에 남긴다. 두뇌가 멤버 main 에 무언가를 만들었는지 드러내기 위해서다.
6. 병합
   1. `git -C M merge --no-ff --no-commit <branch>`
   2. `git -C M commit -m "merge(T): <제목>"`
   - 커밋 단계에서 레포 pre-commit·prepare-commit-msg·commit-msg 훅이 모두 돈다. chemical·app 의 명의 검사는 `.githooks/pre-commit` 에만 있다. 그런데 `git merge` 한 번으로는 pre-commit 이 돌지 않는다. 그래서 두 단계로 나눈다.
   - `--no-verify`·`-c user.*`·`--author` 는 쓰지 않는다.
   - 충돌·훅 거부면 `MERGE_HEAD` 가 있을 때만 `git merge --abort` 로 되돌린다.
     - 오류 문구는 고정문이다("충돌" 또는 "레포 커밋 훅이 거부했습니다 — 명의·훅을 확인").
     - 훅 출력은 옮기지 않는다(비밀값 위험, `init.ts` 와 같은 원칙).
     - 원장에는 종료 코드만 남긴다.
7. 기록: 병합 커밋을 지금 `--merge-commit` 과 같은 검사(`validateTaskCommit` merge, 대상 = M, 기준점 = `task.merge.base`)로 확인한다. 그다음 backlog `merge.commit` 을 쓰고 원장 `done` 을 남긴다.

실패 뒤 두뇌

- 사전 검사 실패·충돌·훅 거부는 모두 `fodh judgment add --blocks T --reclaim` 으로 올린다(`templates/prompts/MERGE.md` 14·19행 방식).
  - MERGE 에서 갈 수 있는 곳은 DOCS·RECLAIM 뿐이다. `--reclaim` 없이 `--blocks` 만 걸면 task 가 MERGE 에 갇힌다.
- 사용자가 정리하고 답하면 회수된 task 는 저장된 단계(MERGE)로 재개한다. 이때 §6-3 에 따라 기준점을 다시 확인한다.

- 워크스페이스 모드에서 멤버 main 을 바꿀 수 있는 것은 이 명령뿐이다(§8).
- 한 레포 모드에서는 두뇌가 루트에서 치는 `git merge` 도 지금처럼 허용한다. 안내만 새 명령으로 바꾼다.

### 6-2. 한 레포 모드 호환

- 멤버 = 루트이므로 §6 표의 오른쪽 열이 지금 동작과 같아진다. 차이는 워크트리 base 하나다.
- 한 레포 모드의 워크트리 base 는 "루트 현재 브랜치"다. 그래서 한 레포 모드에는 `baseBranch` 기본값을 두지 않는다(= 현재 브랜치). 지금 동작이 그대로 유지된다.

### 6-3. task 별 병합 기준점

지금은 상태 `mergeBase` 하나를 REVIEW→MERGE 때 루트 HEAD 로 정한다. 그런데 회수된 task 는 저장된 단계(MERGE)로 바로 재개한다(`reclaim.ts` 31-34, `pick.ts` 54·120). 그 사이 다른 task 가 이 값을 덮어쓰면 `worktree.ts` 89행 검사가 틀린 레포·틀린 커밋으로 실패한다. 레포가 여럿이면 거의 반드시 일어난다.

- REVIEW→MERGE 전이 때 backlog task 에 `merge.base = <멤버 baseBranch 끝 sha>` 를 쓴다(백로그 JSON, 표에는 나오지 않음).
- 재개로 MERGE 에 들어갈 때(`transitionState(…, { resume: true })`)
  - `merge.base` 가 있고 지금 `baseBranch` 끝의 조상이면 그대로 쓴다.
  - 조상이 아니면(사용자가 main 을 되돌림) 재개하지 않고 판단을 올린다.
  - 없으면(옛 진행 중 task) 지금 끝으로 정하고 원장에 `merge-base:reset` 경고를 남긴다.
- `validateTaskCommit`(merge)은 `task.merge.base` 를 쓴다. 상태 `mergeBase` 는 한 레포 모드의 옛 진행 중 task 를 위한 대체값으로만 남긴다. 다음 판에서 지운다.

## 8. 두뇌 경계(훅)

- 훅은 `.pi/harness.json` 에서 멤버 목록을 realpath 로 읽는다.
- **멤버 main** = 어떤 멤버 경로 안이면서 등록 워크트리 밖인 곳.

### 8-1. 멤버 main 은 읽기 명령만

v0.1 은 쓰기 명령 목록(`>`·`cp`·`mv`·`rm`·`sed -i`·`tee` …)만 막았다. 검수에서 `npm --prefix ../chemical run format`, 멤버 폴더에서 치는 `npm install`·`eslint --fix`·`flutter pub get`·`next build`·`tsc` 가 모두 빠진다는 지적이 나왔다. 그래서 방향을 뒤집는다.

명령을 단순 명령으로 쪼갠 뒤, 아래 하나라도 멤버 main 을 가리키면 그 단순 명령은 **읽기 허용 목록에 있을 때만** 통과한다.

1. 유효 cwd
   - 도구 cwd
   - 같은 명령 줄 앞쪽의 `cd`·`pushd`
   - 서브셸 `( cd X; … )`
   - `env -C X`
2. 디렉터리 옵션: `git -C`, `npm --prefix`, `pnpm -C/--dir`, `yarn --cwd`, `make -C`, `tsc -p/--project`, `--cwd`·`--dir`·`--directory`·`--project` 꼴 전반
3. 경로 인자: 유효 cwd 기준으로 풀었을 때 멤버 main 안인 인자(`eslint --fix ../chemical/src`, `next build ../chemical` 등)

읽기 허용 목록(옵션 제한 포함)

| 명령 | 조건 |
|---|---|
| `cat` `head` `tail` `wc` `ls` `stat` `file` `du` `tree` `cmp` `jq` `diff` | 출력 파일 옵션 없음(`diff --output` 거부) |
| `grep` `rg` | `rg --pre`·`--pre-glob` 거부 |
| `find` | `-exec` `-execdir` `-ok` `-okdir` `-delete` `-fprint*` `-fls` 거부 |
| `sed` | `-n` 과 `<범위>p` 꼴 스크립트만. `-i`·`w`·`W`·`e`·`r` 거부 |
| `sort` | `-o` 거부 |
| `git` | §8-2 |
| `npm ls` `npm view` `npm outdated` · `flutter --version` `dart --version` `node --version` | 그대로 |

- 목록 밖(`npm run/install/ci/exec`, `npx`, `node`, `tsx`, `flutter`/`dart` 하위 명령, `eslint`, `tsc`, `next`, `awk`, `python` …)은 거부한다: "멤버 main(<이름>)은 읽기만 합니다 — 바꾸거나 실행하는 일은 task 로 위임합니다".
- 멤버 main 에 대한 Edit·Write 는 지금처럼 거부된다(루트 밖).
- 멤버 main 을 가리키지 않는 명령(루트 안, 워크트리 안)은 지금 규칙 그대로다.

남는 한계(지금 한 레포 모드와 같은 수준)

- 루트에서 도는 인터프리터(`python -c`, `node -e`)나 스크립트가 안에서 `../chemical` 에 쓰는 것은 훅이 보지 못한다.
- 두뇌 규칙이 금지한다. 멤버 main 이 바뀌면 §6-1 의 미커밋 검사(추적 파일 → 병합 거부, 추적 안 된 파일 → 경고)와 `fodh workspace list` 가 드러낸다.

### 8-2. git

대상 판정: 유효 cwd 에 `-C` 를 차례로 적용한다. 아래는 대상을 믿을 수 없거나 실행·쓰기 통로이므로 워크스페이스 모드에서 어디를 대상으로 하든 거부한다.

- 환경 앞붙임 `GIT_*=…`(`GIT_DIR`·`GIT_WORK_TREE`·`GIT_EXTERNAL_DIFF`·`GIT_PAGER` 등)
- 전역 옵션 `--git-dir`·`--work-tree`·`-c`·`--config-env`·`--exec-path`·`-p`/`--paginate`
- 허용 전역 옵션은 `-C`·`--no-pager`·`-P`·`--no-optional-locks` 뿐이다.

대상이 멤버 main 이면 하위 명령별 허용 목록만 통과한다.

| 하위 명령 | 허용 조건 |
|---|---|
| `status` `rev-parse` `rev-list` `ls-files` `ls-tree` `merge-base` `describe` `name-rev` `show-ref` `for-each-ref` `shortlog` | 그대로 |
| `log` `show` `diff` | `--output`·`--ext-diff`·`--textconv` 거부 |
| `grep` | `-O`/`--open-files-in-pager` 거부 |
| `blame` | 그대로 |
| `cat-file` | `--textconv`·`--filters` 거부 |
| `branch` | 목록 꼴만: `--list`·`-a`·`-r`·`-v`·`--show-current`·`--contains`·`--merged`·`--no-merged`. `-d/-D/-m/-M/-c/-C/-f/-u/--set-upstream-to/--unset-upstream/--edit-description` 거부 |
| `remote` | 인자 없음·`-v`·`get-url` 만(`show` 는 네트워크라 거부) |
| `config` | `--get`·`--get-all`·`--get-regexp`·`--list`/`-l`(+`--local`·`--show-origin`)만 |
| `symbolic-ref` | 읽기 꼴(인자 1개, `--short` 허용)만 |
| `worktree` | `list` 만 |
| `stash` | `list`·`show` 만 |

- 그 밖의 하위 명령은 거부한다: "멤버 main 은 fodh worktree merge 로만 바꿉니다".
- **commit·merge·push 는 대상이 워크스페이스 루트일 때만** 허용한다. 지금은 `pretooluse.mjs` 497-506 이 상태만 봐서 MERGE·DOCS 에서 `git -C ../chemical commit` 이 통과한다. 이 대상 검사는 두 모드 모두에 넣는다. 한 레포 모드에서는 대상 = 루트라 동작이 같다. 대상 판정은 `pretooluse.mjs` 446-455 의 보수적 판정(판정 불가면 거부)을 다시 쓴다.
- 등록 워크트리를 대상으로 하는 git 은 지금 규칙 그대로다(커밋은 `fodh worktree commit`).

### 8-3. 비밀 읽기

- 정책은 루트 정책 ∪ 멤버별 정책이다.
  - 기본 목록(`.env*`·키 등)과 파일 이름 패턴은 이미 어디서나 걸린다.
  - 멤버 `/` 패턴은 멤버 경로 기준으로 판정한다.
- `git show <rev>:<path>`·`git cat-file -p <rev>:<path>` 의 경로는 대상 레포 최상위 기준으로 푼다(`./` 로 시작하면 유효 cwd 기준). 풀린 경로에 그 멤버 정책을 적용한다.
  - 지금 `secret-reads.mjs` 103행은 cwd 기준으로 풀어서 `git -C ../chemical show HEAD:<path>` 가 멤버 `/` 패턴을 비껴간다.
- 재귀 검색(`rg --hidden`·`rg -uu`·`grep -r`)의 비밀 제외 조건(`secret-reads.mjs` 133-139)을 검색 대상에 걸린 멤버마다 계산한다.

### 8-4. 승인 규칙

- 최상위 규칙 ∪ 멤버 전체 규칙을 명령이 어느 폴더에서 돌든 건다.
- 매칭 전에 단순 명령마다 정규화한다. 규칙은 **원문과 정규화한 꼴 둘 다**에 건다.
  - `npm` 전역 옵션을 뺀다: `--prefix <v>`·`--prefix=<v>`·`-w/--workspace <v>`·`-s/--silent`·`--loglevel <v>`·`--if-present`·`-q`.
  - `run-script`·`rum`·`urn` → `run`.
  - `npm test|t|tst|start|stop|restart` → `npm run <이름>`.
  - `npm exec … -- X`·`npm x X` → `X`.
  - `pnpm [-C X|--dir X|--filter X] [run] S`·`yarn [--cwd X] [run] S`·`bun run S` → `npm run S`.
  - `npx`·`bunx`·`pnpm dlx` 벗기기는 `shell-commands.mjs` 7-18 을 그대로 쓴다.
- `node [--import X|--loader X|-r X|--require X|--env-file X …] <파일>` 과 `tsx <파일>` 은 정규화하지 않는다. 경로 패턴을 앵커 없이 써서 잡는다(§3-1).
