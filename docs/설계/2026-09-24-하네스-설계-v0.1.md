- 작성: Fable, 2026-09-24 KST. 사용자 지시 "내가 이 프로젝트를 진행하며 활용한 일반적인 룰과 지침으로 나만의 하네스 터미널을 Pi 기반으로 커스터마이징 … 구성 시작해".
- 가칭: **fod-harness** (For Our Dream 팀 하네스). 이름은 [판단대기 A4](../판단대기.md).
- 상태: **설계 초안. 구현 착수 전.** 열린 질문 8건은 [판단대기.md](../판단대기.md)에 있고, 사용자 답이 오기 전에는 코드 구현(Codex)을 시작하지 않는다.
- 근거 자료: `@mariozechner/pi-coding-agent` 0.73.1 문서(`docs/extensions.md`, `skills.md`, `packages.md`, `providers.md`, `sdk.md`, `examples/extensions/file-trigger.ts` 등)와 Savit 작업체계(`social-content-library-docs/docs/작업체계.md`), 메모리 규칙 8건.

## 0. 가능한가 — 결론: 가능

사용자가 원하는 세 가지 핵심 동작은 Pi 확장 API로 모두 구현된다.

| 원하는 동작 | Pi 에서 쓰는 것 | 확인한 근거 |
|---|---|---|
| 한 작업이 끝나면 멈추지 않고, 판단 없이 진행 가능한 작업이 남아 있으면 계속 진행 | `agent_end` 이벤트에서 상태기계를 보고 `pi.sendMessage(..., { triggerTurn: true })` 로 다음 턴을 스스로 연다 | extensions.md "agent_start / agent_end", "pi.sendMessage" |
| 판단대기 문서를 내가 고치면 스스로 읽고 이어서 작업 | `fs.watch` 로 문서 감시 → 내용 해시 변경 + 안정화 뒤 메시지 주입 | examples/extensions/file-trigger.ts 가 같은 패턴 |
| 작업이 중간에 멈춰 있으면 감지 | 60초 타이머에서 `ctx.isIdle()` + 상태기계 + 마지막 활동 시각으로 판정, 재시작 시 `session_start` 에서 상태 파일 복구 | extensions.md "ctx.isIdle()", "session_start" |

전제 조건 두 가지는 사용자 결정이 필요하다: 오케스트레이터 모델의 과금 경로(A1), 판단 트리거 방식(A2).

## 1. 목표와 설계 원칙

사용자 요구를 원칙으로 옮긴 것이다. 구현·검수 때 이 표를 기준으로 판정한다.

| # | 사용자 요구(원문 요지) | 설계 원칙 |
|---|---|---|
| P1 | 작업이 끝나고 내가 판단했다고 할 때까지 멈춰 있는 게 문제 | **판단이 필요 없는 일은 절대 멈추지 않는다.** 멈추는 조건은 "남은 작업이 전부 판단 대기" 하나뿐 |
| P2 | 판단 문서를 스스로 읽지 않는 게 문제 | **문서가 진실(source of truth)이다.** 판단대기·백로그·상태 파일을 항상 파일로 유지하고, 워처가 변경을 감지하면 오케스트레이터가 반드시 읽는다 |
| P3 | 워처는 "수정됐는지, 멈췄는지"만 판단 | **워처는 판단하지 않는다.** 감지 사실만 메시지로 주입하고, 해석·결정·다음 작업 선택은 오케스트레이터(LLM)가 한다 |
| P4 | 언제나 검수 | **검수 없는 완료는 없다.** 상태기계에서 `REVIEW` 를 건너뛰는 전이는 존재하지 않는다 |
| P5 | project-start 는 아주 상세히 질문 | **인터뷰 프로토콜**(§12)로 18개 영역을 라운드 단위로 묻고, 답을 결정기록에 남긴 뒤에만 PRD 를 쓴다 |
| P6 | 메모리 누수 금지, 작업+검수 끝나면 프로세스 정리 필수 | **하네스가 띄운 프로세스는 하네스가 등록·종료한다.** 정리는 상태기계의 필수 단계(`CLEANUP`)이며 건너뛸 수 없다 |
| P7 | 저장공간: 재생성 가능한 캐시·성능 무관 산출물 정리 | 프로젝트 설정(`harness.json`)에 **재생성 가능 경로 목록**을 선언하고 `CLEANUP` 에서 지운다. 목록에 없는 것은 절대 지우지 않는다 |
| P8 | 다른 프로젝트에서도 재사용 | 하네스 = **전역 Pi 패키지**, 프로젝트별 차이는 `.pi/harness.json` 한 파일로만 표현 |
| P9 | (기존 규칙) 디자인=Claude, 나머지=Codex, Fable 은 직접 구현 안 함 | 위임 브리지가 작업을 `design` / `non-design` 으로 분류해 라우팅. 오케스트레이터는 스펙·검수·문서·병합만 |

## 2. 전체 구조

```
┌─ 터미널: pi (TUI) ──────────────────────────────────────────────────────┐
│  오케스트레이터 = Pi 에이전트 (Claude, 모델은 A1)                          │
│  시스템 프롬프트 = Pi 기본 + 하네스 규칙(before_agent_start 로 주입)         │
│                                                                          │
│  fod-harness 패키지 (전역 설치, ~/Desktop/fod-harness)                     │

│  │                          상태기계, 백로그, 문서 스캐폴딩, 자동 다음-턴   │

│  ├ extensions/delegate      codex_task / codex_review / claude_design 도구 │
│  ├ extensions/cleanup       프로세스 레지스트리, 캐시 정리, 메모리 워치독   │
│  ├ extensions/guard         비밀값·위험 명령·승인 필수 동작 차단            │
│  ├ skills/                  project-start, develop-start, review, cleanup, │
│  │                          prd, market-research, delegation-spec          │
│  └ templates/               문서 골격(PRD, 판단대기, 백로그, 작업체계 …)    │
└──────────────────────────────────────────────────────────────────────────┘
        │ 자식 프로세스 (하네스가 pid 등록·종료)
        ├─ codex exec  (gpt-6-astra, effort high, 한 번에 1개)   ← 구현·교차검수·조사
        ├─ Pi SDK createAgentSession (Opus 5.5, in-process)      ← 디자인 서브에이전트
        └─ mcporter call <server> <tool>                         ← MCP 호출 (Pi 는 MCP 내장 없음)

프로젝트 폴더
  .pi/harness.json          프로젝트별 설정 (§11)
  .pi/harness-state.json    상태기계 현재 상태 (재시작 복구용)
  docs/판단대기.md           사용자 결정 원장 (§4)
  docs/backlog.md           작업 목록·상태 (§5)
  docs/PRD.md, 설계/, 검수/, 결정기록/, 위임스펙/, 조사/, 작업일지.md, 작업체계.md
```

왜 이렇게 나누나:
- 워처·정리·가드는 LLM 없이 도는 순수 TypeScript 다. LLM 이 잠들거나(컨텍스트 압축 중) 멈춰도 감시·정리는 계속된다.
- 오케스트레이터의 판단은 전부 문서에 쓰인다. 세션이 죽어도 문서 + 상태 파일로 그대로 복구된다(§9).

## 3. 상태기계

### 3-1. project-start

```
IDLE ─/project-start─▶ INTERVIEW ─▶ RESEARCH ─▶ PRD_DRAFT ─▶ ARCH ─▶ REVIEW ─▶ WAIT_JUDGMENT ─▶ PROJECT_READY
                          ▲                                            │                │
                          └──── 검수에서 "질문 추가 필요" 반려 ◀────────┘                │
                                                                                        └─ 사용자 답 반영 → 미결 0건이면 READY
```

| 상태 | 하는 일 | 산출물 | 끝나는 조건 |
|---|---|---|---|
| INTERVIEW | §12 프로토콜로 라운드별 질문. 유한 선택지는 `ctx.ui.select`, 서술형은 채팅 | `docs/결정기록/YYYY-MM-DD-인터뷰.md` (질문·답·추천·미결) | 18개 영역 모두 "답 있음" 또는 "판단대기로 이관" |
| RESEARCH | 시장·경쟁·규제·기술 조사. 조사는 Codex 에 위임(비디자인 규칙) | `docs/조사/…` | 조사 보고 + 오케스트레이터 검수 통과 |
| PRD_DRAFT | 템플릿 기반 PRD 작성(§11 템플릿) | `docs/PRD.md` v0.1 | 인터뷰 답이 전부 반영됨 |
| ARCH | 아키텍처·문서 구조·필요 스킬·MCP·저장소 구조 확정 | `docs/설계/아키텍처.md`, `docs/설계/도구-스킬-MCP.md`, `.pi/harness.json` 초안 | — |
| REVIEW | Codex 읽기 전용 교차검수(PRD+아키텍처) | `docs/검수/…-PRD-아키텍처-검수.md` | 높음 지적 0건 |
| WAIT_JUDGMENT | 미결 항목을 판단대기에 쓰고 멈춤 | `docs/판단대기.md` | 사용자 답(워처 감지) → 반영 → 미결 0건 |

### 3-2. develop-start (작업 루프)

```
PROJECT_READY ─/develop-start─▶ PLANNING ─▶ ┌─────────── task loop ───────────┐
                                             │ PICK → SPEC → IMPLEMENT → VERIFY │
                                             │  → REVIEW → (FIX ↺ ≤3) → MERGE  │
                                             │  → DOCS → CLEANUP → PICK …       │
                                             └──────────────┬─────────────────┘
                                                            │ 진행 가능한 task 0건
                                                            ▼
                                                     WAIT_JUDGMENT ──(문서 수정 감지)──▶ PICK
```

| 상태 | 하는 일 | 규칙 |
|---|---|---|
| PLANNING | PRD → `docs/backlog.md` (task ID, 의존, 분류 design/non-design, 판단 필요 여부) | 한 task = 한 브랜치·워크트리, 반나절 이내 크기로 쪼갠다 |
| PICK | `ready` 이면서 의존이 모두 `done` 인 task 중 우선순위 최상 선택 | 없으면 WAIT_JUDGMENT. 있으면 멈추지 않는다(P1) |
| SPEC | 위임스펙 작성(무엇·왜·수용기준·건드릴 파일·검증법·금지사항) | `docs/위임스펙/…` |
| IMPLEMENT | design → Claude 서브에이전트, 그 외 → `codex_task` | 오케스트레이터는 직접 코드 수정 금지(가드가 write/edit 를 소스 경로에 대해 차단, 문서 경로만 허용) |
| VERIFY | 오케스트레이터가 빌드·테스트·lint 실행(Codex 샌드박스가 못 하는 것) | 실패 → IMPLEMENT 로 반려(FIX 횟수 계수) |
| REVIEW | 교차검수: Claude 산출물은 Codex 읽기 전용, Codex 산출물은 Claude 검수 에이전트(Opus 5.5) | `docs/검수/…` 에 모델·effort 머리말 |
| FIX | 지적 반영. 3회 초과 시 task 를 `blocked` 로 바꾸고 판단대기에 올린다 | 무한 루프 방지 |
| MERGE | 병합·push. `harness.json.requiresApproval` 에 걸리면 판단대기로 | 예: 프로덕션 마이그레이션, 스토어 업로드 |
| DOCS | 작업일지·백로그·판단대기 "지금 상태" 갱신 | — |
| CLEANUP | §8. 건너뛸 수 없음 | 완료 보고에 before/after 수치 |

### 3-3. 판단이 필요한 순간의 처리(핵심)

- 어느 상태에서든 "사용자 결정 없이는 못 정한다" 가 나오면: 판단대기에 항목(배경·선택지·추천·회신 형식) 추가 → 현재 task 를 `blocked(A번호)` → **즉시 PICK 으로 가서 다른 task 를 잡는다.** 멈추는 것은 PICK 이 빈손일 때뿐.
- `WAIT_JUDGMENT` 진입 시: 판단대기 §"지금 상태" 에 요약 쓰기 → 알림(A3) → 에이전트 턴 종료(토큰 소비 0).

## 4. 판단대기 문서 규격과 워처

### 4-1. 문서 규격 (`docs/판단대기.md`)

```markdown
# 판단대기
## 지금 상태
(오케스트레이터가 WAIT_JUDGMENT 진입 때 갱신: 어디까지 됐고, 무엇을 기다리는지 5줄 이내)

## 열린 판단
### A12 — 제목                       ← 번호는 원장 고유, 재사용 금지
- 배경: …
- 선택지: ① … ② … ③ …
- 추천: ② (이유)
- 막힌 작업: T07, T09
- 답: ⟵ 사용자가 여기에만 쓴다 (예: `2` 또는 자유 서술)

## 결정 완료
(오케스트레이터가 답을 읽고 반영한 뒤 옮김. 답 원문·반영 커밋·날짜)
```

### 4-2. 워처 규칙 — "감지만" (P3)

| 감지 대상 | 방법 | 주입 메시지(사실만) |
|---|---|---|
| 판단대기 수정 | `fs.watch` + 폴링 5초 백업. 내용 SHA-256 이 바뀌고 **10초간 안정** 후 발화(편집 중 저장 오탐 방지) | `[watcher] 판단대기.md 변경 감지 (해시 a1b2→c3d4, 변경 줄: 43-45). 답이 채워진 항목: A12, A14.` |
| 작업 정지 | 60초 타이머: 상태가 활동 상태(INTERVIEW~CLEANUP)인데 `ctx.isIdle()` 이 `stallMinutes`(기본 10) 넘게 참 | `[watcher] 상태 IMPLEMENT(T07) 에서 12분간 활동 없음. 마지막 이벤트: codex_task 시작 12:41.` |
| 자식 프로세스 정지 | 레지스트리의 pid 가 `timeoutMinutes` 초과 또는 사라짐 | `[watcher] codex exec pid 4123 이 35분 경과(한도 30). 종료할지 판단 필요.` |
| 세션 복구 | `session_start` 에서 상태 파일이 활동 상태면 | `[watcher] 이전 세션이 REVIEW(T05) 에서 끊김. 상태 파일 시각 09-24 02:13.` |

- 메시지 주입은 `pi.sendMessage({ customType: "harness-watcher", … }, { triggerTurn: true, deliverAs: "followUp" })`. 에이전트가 바쁘면 현재 턴이 끝난 뒤 전달된다.
- 워처는 파일을 **해석하지 않는다**. 어느 항목이 답인지 판단·반영·다음 task 선택은 오케스트레이터가 한다.
- 판단 트리거를 "답 채워짐" 으로 볼지 "명시 마커" 로 볼지는 [A2](../판단대기.md).

## 5. 백로그 규격과 완료 정의

`docs/backlog.md` 는 표 한 장이다. 오케스트레이터만 쓰고, 사용자는 읽는다.

| ID | 제목 | 분류 | 의존 | 상태 | 판단 | 브랜치 | 검수 | 비고 |
|---|---|---|---|---|---|---|---|---|
| T07 | 공유폴더 초대 API | non-design | T03 | ready / doing / verify / review / fix(2) / merge / done / blocked(A12) | — | feat/t07 | 검수/… | |

완료 정의(DoD): 수용 기준 통과 + 오케스트레이터 VERIFY 통과 + 교차검수 높음 0 + 병합 + 작업일지 + CLEANUP 보고. 하나라도 빠지면 `done` 으로 못 바꾼다(확장이 상태 전이 때 검사).

## 6. 위임 브리지

### 6-1. Codex (`codex_task`, `codex_review`, `codex_research`)

- 실행: `codex exec -s workspace-write -C <worktree> -m gpt-6-astra -c model_reasoning_effort=high --json -o <결과파일> - < prompt.md`. 교차검수·조사는 `-s read-only`.
- **companion 스크립트(app-server-broker)는 쓰지 않는다.** 이유: cwd 마다 브로커가 고아로 남아 OOM 을 낸 원인(메모리 2026-09-06·09-09). `codex exec` 는 브로커를 띄우지 않는다(2026-09-14 확인).
- **동시 1개**: 잠금 파일 `.pi/codex.lock`. 두 번째 호출은 도구가 거부하고 오케스트레이터에게 "대기 후 재시도" 를 돌려준다.
- 후속 프롬프트: `codex exec resume <session-id>` 로 같은 스레드 이어가기(스레드 id 는 백로그 task 행에 기록). 샌드박스 모드는 스레드에 고정되므로 읽기 전용 검수 뒤 수정은 새 스레드.
- 프롬프트 머리말 자동 삽입: 작업 폴더, "전체 jest·flutter test 절대 금지", "비밀값 기록 금지", "산출물(빌드·캐시) 남기지 말 것", 수용기준, 검증법.
- pid 는 레지스트리에 등록, 종료 코드·소요·토큰을 백로그에 기록. `timeoutMinutes` 초과는 워처가 알린다(죽이는 결정은 오케스트레이터).

### 6-2. Claude 디자인 서브에이전트 (`claude_design`)

- Pi SDK `createAgentSession({ model: opus-5.5, sessionManager: SessionManager.inMemory(), tools: [read, write, edit, bash] })` 로 in-process 실행. 디자인 분류(화면·레이아웃·색·서체·아이콘·에셋)만 여기로.
- 끝나면 `dispose()`. in-process 라 프로세스 누수는 없고 메모리는 세션 객체 해제로 회수.
- 검수 에이전트(Codex 산출물 검수)도 같은 방식.

### 6-3. MCP

- Pi 는 MCP 를 내장하지 않는다. 전역 설치된 `mcporter` 0.7.3 으로 `mcporter call <server> <tool> …` 을 bash 에서 호출한다. project-start 의 ARCH 단계에서 "이 프로젝트가 쓸 MCP 서버 목록" 을 `docs/설계/도구-스킬-MCP.md` 에 정하고 `~/.mcporter/` 설정을 만든다.
- 시장조사용 웹 검색 경로는 [A7](../판단대기.md).

## 7. 검수 체계

- 이중 검수 원칙: 만든 쪽이 아닌 쪽이 본다. Claude 산출물 → Codex 읽기 전용, Codex 산출물 → Claude 검수 에이전트. 문서(PRD·설계)도 Codex 교차검수.
- 검수 문서 템플릿(`docs/검수/YYYY-MM-DD-<ID>-검수.md`): 머리말(대상 커밋·검수 모델·effort·서브에이전트 모델), 지적(높음/중간/낮음, 파일:줄, 재현, 수정안), 판정(채택/반려), 반영 커밋.
- 반려 3회 초과 → `blocked` + 판단대기. 사람이 방향을 정해야 하는 신호로 본다.

## 8. 정리(CLEANUP) 단계 — 필수

### 8-1. 프로세스

- **레지스트리**: 하네스가 `pi.exec`/`spawn` 으로 띄운 모든 pid 를 `.pi/harness-procs.json` 에 (pid, 명령, task, 시작시각) 으로 기록. 정리는 이 목록 + `harness.json.processes.killPatterns` 만 대상.
- **절대 종료 금지**(`neverKill`, 기본값): 사용자 개발 서버(`nest start --watch` 등 설정값), 에뮬레이터·시뮬레이터, 사용자의 대화형 `codex`/ChatGPT.app 프로세스, 현재 Pi 세션 자체.
- **실행 시점**: 각 task 의 CLEANUP 상태, `WAIT_JUDGMENT` 진입 직전, `session_shutdown`. 세 곳 모두 자동.
- **메모리 워치독**: 60초마다 `vm_stat`·`sysctl vm.swapusage`. 스왑 사용이 `swapWarnGB`(기본 8) 를 넘으면 (1) 레지스트리 프로세스 중 task 가 끝난 것 즉시 종료 (2) 오케스트레이터에 경고 주입. 그래도 넘으면 새 `codex_task` 시작을 거부(상태를 `paused(memory)` 로).

### 8-2. 저장공간

- `harness.json.cleanup.rebuildablePaths` 에 선언된 경로만 삭제. Savit 기준 기본 예: `app/build`, `~/Library/Developer/Xcode/DerivedData/<App>-*`, `~/.gradle/caches/<ver>/transforms`, 워크트리의 `server/dist`·`coverage`, `$TMPDIR/cxc-*`, `$TMPDIR/XcodeDistPipeline.*`, 하네스 스크래치 로그(읽은 뒤).
- 병합 끝난 워크트리는 CLEANUP 에서 제거(`git worktree remove`). `node_modules` 는 심링크만 허용.
- `keepPaths`(예: `server/node_modules`, 시뮬레이터·AVD, release-artifacts) 는 목록에 있어도 건드리지 않는 안전장치.
- 보고: before/after `df -h /`, `vm_stat` free, swap 을 CLEANUP 결과에 항상 붙인다(사용자가 눈으로 확인).

## 9. 컨텍스트·세션 전략

- **문서가 진실**: 백로그·판단대기·상태 파일·작업일지가 있으면 어느 세션에서든 복구된다. 세션 파일은 보조.
- **task 마다 새 세션(handoff)** 권장: CLEANUP 뒤 오케스트레이터가 다음 task 의 착수 프롬프트(맥락 요약 + task 스펙 경로)를 만들고 `ctx.newSession()` 으로 넘어간다. Pi 의 `handoff.ts` 예제 방식. 컨텍스트가 작게 유지되어 비용·오류가 준다. ([A9] 확인 필요 없음, 기본 채택; 원하면 끌 수 있게 설정)
- 자동 압축은 백업. `ctx.getContextUsage()` 60% 넘으면 task 경계에서 handoff, 80% 넘으면 즉시 compact.

## 10. 가드레일 (`extensions/guard`)

- `tool_call` 훅에서 차단: (1) write/edit 내용에 API 키·토큰·비밀번호 패턴 (2) 프로젝트 밖 `rm -rf` (3) `requiresApproval` 동작(프로덕션 마이그레이션, 스토어 업로드, 결제 관련, main 직접 push, env 삭제) → 판단대기 항목 생성 후 차단 (4) 오케스트레이터의 소스 코드 직접 수정(문서 경로 외 write/edit 는 "위임하라" 로 거부, P9).
- 전체 테스트 스위트 실행은 오케스트레이터만(VERIFY), 위임 프롬프트에는 금지 문구 자동 삽입.

## 12. project-start 인터뷰 프로토콜 (P5)

- 라운드 규칙: 한 라운드 5~8문항. 유한 선택지는 TUI 선택 다이얼로그, 서술형은 채팅. 각 문항에 **Fable 추천 기본값**을 붙여 "그대로" 로 답할 수 있게 한다. 답이 모호하면 그 자리에서 되묻고, 사용자가 "나중에" 라고 하면 판단대기로 보낸다.
- 종료 조건: 18개 영역 전부 답 또는 판단대기 이관. 오케스트레이터가 "더 물을 것 없음" 을 선언하고 요약을 사용자에게 확인받는다.
- 질문 영역(질문 은행은 `skills/project-start/references/interview-bank.md` 에 영역당 5~15문항):
  1. 문제·목적·한 줄 정의 2. 사용자·페르소나·핵심 시나리오 3. 기능 범위와 우선순위(MVP 선) 4. 플랫폼(iOS/Android/웹/서버/데스크톱) 5. 기술 스택 제약·기존 자산 6. 데이터 모델·개인정보·보존 7. 인증·계정 8. 결제·광고·구독 9. 인프라·배포·비용 상한 10. 외부 API·서비스 11. 디자인 방향·브랜드·접근성 12. 일정·마일스톤·출시 목표 13. 성공 지표·분석 14. 비기능(성능·오프라인·보안·확장) 15. 운영(모니터링·백업·장애) 16. 법무·심사·약관 17. 팀 규칙(역할 분담·모델·검수·정리·승인 필수 목록) 18. 리스크·미결·가정.
