# 워크스페이스 모드 설계 v0.1 (2026-09-27)

> 여러 git 레포를 한 하네스 창에서 한 두뇌·한 백로그로 진행한다. 첫 적용 대상은 WisePharm(web=`~/Desktop/chemical`, backend=`~/Desktop/wisepharm-backend`, app=`~/Desktop/wisepharm-app`).
> 관련: [WisePharm 이관 설계](../이관/2026-09-25-WisePharm-이관-설계.md) §2·§3(레포별 루트 방식, 지금 동작), [하네스 설계 v0.3](2026-09-24-하네스-설계-v0.3.md).

## 0. 요약

- 새 폴더(`~/Desktop/wisepharm`)를 **워크스페이스 루트**로 만든다. 하네스 상태·문서·판단·백로그는 모두 여기 있다. 제품 레포 3개는 **멤버**로 등록만 한다.
- task 마다 대상 레포(`repo`)를 하나 정한다. 워크트리·검증·병합은 그 레포에서 한다. 레포를 넘는 기능은 task 여러 개로 쪼개고 `의존`으로 순서를 건다. 앞 task 가 그 레포 main 에 병합돼야 다음 task 가 시작된다. 지금 사람이 넘겨 주던 "앞 레포 끝남" 확인이 자동이 된다.
- 멤버 레포 폴더에서 `fodh` 를 쳐도 워크스페이스 창이 열린다.
- 한 레포 모드(지금 방식)는 "멤버가 자기 자신 하나인 워크스페이스"로 같은 코드 경로를 탄다. 기존 설정·문서·동작은 바뀌지 않는다.

## 1. 목표와 비목표

목표

1. 한 창에서 WisePharm 전체 백로그를 진행한다.
2. 레포를 넘는 순서(스키마 web → API backend → 화면 app)를 하네스가 지킨다.
3. 두뇌 경계(소스 직접 수정 금지, 비밀 읽기 차단, 승인 필수 동작)는 멤버 레포 전체에 똑같이 걸린다.

비목표

- 레포 병렬 실행. Codex 는 기계 전체 1개(전역 슬롯) 그대로다.
- task 하나가 여러 레포를 바꾸는 것. task 하나 = 레포 하나 = 워크트리 하나 = 병합 하나.
- 자동 push. 병합은 멤버 레포 로컬 main 까지다. push 는 지금처럼 하네스 흐름 밖(승인 판단 → 사용자)에서 한다. 로컬 main 에 병합되면 다음 레포 task 가 `../chemical` 같은 상대경로로 바로 읽으므로 레포 간 흐름에 push 는 필요 없다.
- 멤버 레포 main 체크아웃 정리. 하네스는 워크트리만 만들고 지운다. 멤버 main 의 `dist`·`node_modules` 등은 건드리지 않는다(사용자 개발 서버 보호).

## 2. 모양

```
~/Desktop/
  wisepharm/                ← 워크스페이스 루트 (자체 git 저장소, 원격 없음)
    .pi/harness.json        ← workspace.repos 로 멤버 등록
    .pi/…                   ← 상태·원장·잠금·codex 기록 (한 벌)
    .claude/settings.json   ← 두뇌 훅
    CLAUDE.md               ← 관리 블록: 멤버 목록·레포 규칙 위치·레포 간 규칙
    docs/backlog.md         ← 레포 열이 있는 백로그 한 벌
    docs/판단대기.md · 판단기록/ · 작업일지/ · 위임스펙/
  chemical/                 ← 멤버 web     (.git/fodh-workspace 표지)
  wisepharm-backend/        ← 멤버 backend (.git/fodh-workspace 표지)
  wisepharm-app/            ← 멤버 app     (.git/fodh-workspace 표지)
  wp-web-T03/  wp-be-T04/  wp-app-T05/   ← task 워크트리 (각 멤버의 형제)
```

- 두뇌(`claude -p`)의 작업 폴더는 워크스페이스 루트다. 멤버 레포는 읽기만 한다.
- 워크트리는 지금처럼 멤버의 형제 폴더(`worktrees.root` 기본 `..`)에 만든다. 그래야 워크트리 안 스크립트의 `../chemical`·`../wisepharm-backend` 상대경로가 멤버 main 체크아웃으로 풀린다(이관 설계 §3 전제 그대로).
- 한 레포 모드: `workspace` 설정이 없으면 암묵 멤버 하나(이름 `.`, 경로 = 루트)로 본다. 백로그 레포 열·표지 파일·`--repo` 인자는 쓰지 않는다.

### 3-2. 규칙

| 키 | 규칙 |
|---|---|
| `workspace.repos` | 객체, 멤버 1~8개. 있으면 워크스페이스 모드 |
| 멤버 이름 | `^[a-z][a-z0-9-]{0,15}$`. `.` 은 예약(한 레포 모드) |
| `path` | 루트 기준 상대경로. realpath 가 디렉터리이고 `.git` **디렉터리**가 있어야 한다(연결 워크트리·서브모듈 거부). HOME·`/`·워크스페이스 루트 자신·그 조상·그 안쪽 금지. 멤버끼리 같거나 서로 포함하면 안 된다 |
| `baseBranch` | 기본 `main`. 워크트리는 이 브랜치에서 갈라지고, 병합은 멤버 체크아웃이 이 브랜치일 때만 한다 |
| `worktrees` | 멤버마다 `root`(기본 `..`, 멤버 기준)·`prefix`(필수)·`links`·`setup`·`setupTimeoutMinutes`. (워크트리 폴더, prefix) 쌍은 멤버끼리 겹치면 안 된다 |
| `verify` | 멤버마다 `commands`(필수, 비어 있으면 설정 오류)·`heavy`·`timeoutMinutes` |
| `secrets` | 멤버마다 `readDeny`·`readAllow`. 기본 목록과 최상위 `secrets` 에 더한다. `/` 가 있는 패턴은 그 멤버 경로 기준 |
| `approvalRules` | 멤버마다 추가. 최상위 규칙과 합쳐 두뇌 명령 전체에 건다. id 는 전체에서 중복 금지 |

- 워크스페이스 모드에서 최상위 `verify`·`worktrees.prefix/links/setup` 이 있으면 설정 오류로 막는다("워크스페이스 모드에서는 workspace.repos.<이름> 아래에 둡니다"). 값이 두 곳에 있으면 어느 쪽이 쓰였는지 헷갈리기 때문이다. `cleanup.rebuildablePaths` 는 워크스페이스 루트 기준으로만 쓴다(멤버 main 은 정리하지 않는다).
- `workspace.repos` 는 통째로 승인 전용 키다(`approvalConfigKeys`). 하네스가 병합하는 곳을 넓히기 때문이다. 두뇌는 바꿀 수 없다.
- 설정을 읽을 때마다 멤버 경로 검사를 다시 한다. 멤버 폴더가 사라지거나 옮겨지면 그 멤버 task 만 막히는 게 아니라 설정 오류로 창을 열지 않는다(`fodh doctor` 가 원인을 보여 준다).

## 4. 멤버 표지와 실행

### 4-1. 표지

- `fodh workspace add` 가 멤버의 `.git/fodh-workspace` 에 워크스페이스 루트 절대경로 한 줄을 쓴다. `.git` 안이라 커밋·상태에 나타나지 않는다.
- 표지가 가리키는 워크스페이스의 `workspace.repos` 에 그 멤버 경로(realpath)가 있어야 유효하다. 없으면 "표지가 맞지 않습니다: <워크스페이스>에서 fodh workspace list" 오류를 낸다(조용히 무시하지 않는다).

### 4-2. 창 열기

| 치는 곳 | 결과 |
|---|---|
| 워크스페이스 루트 | 워크스페이스 창 |
| 멤버 레포 안(어느 하위 폴더든) | 표지를 따라 워크스페이스 창. 첫 줄에 `워크스페이스 wisepharm (멤버 web 에서 열림)` |
| task 워크트리 안 | 지금처럼 거부(연결 워크트리) |
| 표지 없는 일반 레포 | 지금처럼(자기 `.pi/harness.json` 또는 설치 질문) |

- `projectRoots` 가 git 최상위에서 멈출 때 `.git/fodh-workspace` 를 먼저 본다. 표지가 유효하면 그 레포 자신의 `.pi/harness.json` 보다 앞선다.
- `resolveCliRoot`(`fodh state get` 같은 하위 명령)도 같은 순서로 표지를 따른다. backend 처럼 옛 `.pi/harness-state.json` 이 남은 멤버에서 옛 하네스를 건드리지 않게 하기 위해서다.
- 멤버 자신의 하네스는 표지가 있으면 `startPlan`·`fodh init` 모두 거부한다("이 레포는 워크스페이스 <경로>에 속합니다"). 같은 레포에 두뇌 두 개가 붙지 않는다.

### 4-3. 명령

| 명령 | 동작 | 누가 |
|---|---|---|
| `fodh workspace init --repo web=../chemical --repo backend=… --repo app=…` | 빈 폴더(또는 하네스 없는 폴더)에서 `fodh init` + `workspace.repos` 작성 + 표지 기록. 멤버 검사를 모두 통과해야 아무것도 쓴다 | 사용자 터미널 |
| `fodh workspace add <이름> <경로>` / `remove <이름>` | 멤버 추가·제거. 제거는 그 멤버의 미완 task·워크트리가 없을 때만. 표지도 함께 지운다 | 사용자 터미널(`--approve`) |
| `fodh workspace list` | 멤버·경로·표지·현재 브랜치·미커밋 여부·옛 하네스 유무 | 누구나(두뇌 포함) |

멤버 추가 조건(하나라도 어기면 아무것도 쓰지 않는다)

1. 멤버에 살아 있는 `.pi/harness.lock` 이 없다. 옛 하네스 상태가 `IDLE`·`DONE_ALL`·`PROJECT_READY` 이거나 `.pi` 가 없다.
2. 다른 워크스페이스 표지가 없다.
3. 그 멤버 prefix 로 시작하는 브랜치가 아직 없다(`git branch --list '<prefix>*'`). 이 prefix 의 브랜치는 이 워크스페이스만 만든다는 보장이다. 지금 `createWorktree` 는 같은 이름 브랜치가 있으면 이어 쓰는데(회수 뒤 재개용), backend 에 남은 파일럿 브랜치 `wpb-wt-T01`·`T02` 를 새 T01·T02 가 이어 쓰는 사고를 이 조건과 새 prefix(`wp-be-`)가 막는다.

## 5. 백로그와 흐름

- task 에 `repo`(멤버 이름)를 더한다. 백로그 표에 `레포` 열을 `분류` 다음에 둔다(워크스페이스 모드만. 한 레포 모드 표는 지금과 똑같다).
- `fodh backlog add --repo <이름>` 이 워크스페이스 모드에서 필수다. `repo` 는 status `ready` 이고 워크트리가 없을 때만 바꿀 수 있다.
- 레포 간 순서는 `의존` 으로만 건다. PICK 은 지금처럼 의존 task 가 모두 `done`(병합 커밋 포함)일 때만 고른다. 그러므로 "앞 레포 병합 뒤 다음 레포 시작"이 새 코드 없이 지켜진다.

예) 새 복약 필드

| ID | 제목 | 분류 | 레포 | 의존 |
|---|---|---|---|---|
| T01 | 복약 필드 스키마·마이그레이션 파일 | non-design | web | |
| T02 | schema:sync + API + openapi:export | non-design | backend | T01 |
| T03 | sync_openapi + generate_api + 화면 | design | app | T02 |

- T01 의 운영 DB 적용(`db:migrate`)은 task 안에서 하지 않는다. 승인 규칙이 두뇌를 막고, 두뇌는 `[승인]` 판단을 올린다(지금과 같음). T02 는 마이그레이션 **파일**이 web main 에 들어간 것만 필요하다.
- 한 task 가 두 레포를 고쳐야 한다고 두뇌가 판단하면 task 를 쪼갠다. 스펙 스킬(`fodh-spec-writing`)에 한 줄 규칙을 넣는다.

## 6. 레포별 git 동작

`repoOf(task)` = 멤버 이름·realpath·설정. 한 레포 모드면 루트 자신. 지금 루트 기준인 git 호출을 모두 이것으로 바꾼다.

| 단계 | 지금 | 워크스페이스 모드 |
|---|---|---|
| 워크트리 생성 | 루트 HEAD 브랜치에서 `<root>/../<prefix>T` | 멤버 `baseBranch` 에서 `<멤버>/<worktrees.root>/<prefix>T`. 멤버 체크아웃이 다른 브랜치여도 base 는 `baseBranch`. `links`·`setup` 은 그 멤버 설정. 상태 `worktrees[]` 에 `repo` 기록 |
| 검증 | 워크트리에서 `verify.commands` | 워크트리에서 그 멤버 `verify.commands` |
| 커밋(`fodh worktree commit`) | 워크트리 | 그대로(워크트리). 레포별 명의·pre-commit 훅이 그대로 돈다 |
| 검수 커밋 확인 | 루트에서 rev-parse | 멤버에서 |
| `mergeBase`(REVIEW→MERGE) | 루트 HEAD | 멤버 `baseBranch` 끝 |
| 병합 | 두뇌가 루트에서 `git merge` | **`fodh worktree merge <T>`**(아래) |
| 병합 커밋 확인 | 루트 | 멤버 |
| 작업일지·백로그 커밋(DOCS·CLEANUP) | 루트 | 워크스페이스 루트(그대로) |
| 워크트리 제거 | 루트에서 `git worktree remove` | 멤버에서 |

### 6-1. `fodh worktree merge <T>` (새 명령, 두 모드 공통)

1. 상태 `MERGE`, 현재 task = T.
2. 멤버 체크아웃 브랜치 = `baseBranch`. 추적 파일 미커밋 변경이 없다(`git status --porcelain --untracked-files=no`). 사용자가 멤버에서 작업 중이면 여기서 멈추고 "멤버 <이름>에 미커밋 변경이 있습니다 — 사용자가 정리한 뒤 다시" 오류를 낸다. 두뇌는 `[승인]` 이 아닌 일반 판단(`--blocks T`)으로 올린다.
3. task 브랜치 끝 = `review.commit`.
4. `git -C <멤버> merge --no-ff --no-edit -m "merge(T): <제목>" <branch>`. 레포 pre-commit·commit-msg 훅이 돈다(`--no-verify` 없음).
5. 충돌·훅 실패면 `git merge --abort` 로 되돌리고 오류를 낸다. 두뇌는 판단을 올린다(지금 MERGE 에서 충돌 난 때와 같음).
6. 성공하면 병합 커밋을 지금 `--merge-commit` 검사와 같은 검사로 기록한다.

- 워크스페이스 모드에서는 이 명령만 멤버 main 을 바꿀 수 있다(§8). 한 레포 모드에서는 두뇌의 `git merge` 도 지금처럼 허용하고, 안내는 새 명령으로 바꾼다.

### 6-2. 한 레포 모드 호환

- 멤버 = 루트이므로 위 표의 오른쪽 열이 지금 동작과 같아진다. 단 한 가지: 워크트리 base 가 "루트 현재 브랜치"다. 한 레포 모드에는 `baseBranch` 기본값을 두지 않고(= 현재 브랜치) 지금 동작을 유지한다.

## 7. 위임

- task 위임(`fodh codex task`): cwd 는 등록 워크트리 그대로. 머리말에 한 줄 추가: `대상 레포: web (~/Desktop/chemical) — 다른 멤버 레포는 읽기만 한다. 그 레포의 AGENTS.md 규칙을 따른다.` Codex 는 워크트리의 AGENTS.md 를 스스로 읽는다.

- 검수 위임(`fodh codex review`): task 워크트리 그대로.
- Claude Agent 위임(design 분류): 등록 워크트리 쓰기만 허용(지금 훅 그대로).

## 8. 두뇌 경계(훅)

훅은 `.pi/harness.json` 에서 멤버 목록을 읽는다(realpath). 멤버 main 체크아웃 = 멤버 경로 안이면서 등록 워크트리 밖.

| 동작 | 지금 | 워크스페이스 모드 |
|---|---|---|
| Edit·Write 로 멤버 main 파일 | 루트 밖이라 거부 | 거부(같음) |
| Bash 쓰기(`>`·`cp`·`mv`·`rm`·`sed -i`·`tee` …)로 멤버 main | 루트 밖 Bash 쓰기는 통과 | **거부**: "소스 파일은 두뇌가 쓰지 않습니다" |
| git 을 멤버 main 에(`-C`·`cd`·도구 cwd 로 판정) | 해당 없음 | 읽기 목록만 허용: `status log diff show rev-parse ls-files blame grep cat-file merge-base describe shortlog branch(--list·-a·-v) remote -v config --get worktree list`. 그 밖은 "멤버 main 은 fodh worktree merge 로만 바꾼다". `GIT_DIR`·`--git-dir`·`--work-tree` 가 있으면 대상 판정 불가로 거부 |
| 비밀 읽기 | 루트 기준 정책 | 루트 정책 ∪ 멤버별 정책. 기본 목록(`.env*`·키 등)은 파일 이름 패턴이라 멤버에도 이미 걸린다. 멤버 `/` 패턴은 멤버 경로 기준 |
| 승인 규칙 | 루트 `approvalRules` | 최상위 ∪ 멤버 전체. 명령이 어느 폴더에서 돌든 건다 |

- 지금과 같은 한계: `python -c`·`node -e` 로 파일을 쓰는 것은 훅이 다 잡지 못한다(한 레포 모드와 같은 수준). 두뇌 규칙이 금지하고, 멤버 main 이 바뀌면 `fodh worktree merge` 의 미커밋 검사와 `fodh workspace list` 가 드러낸다.
- Codex 는 훅 밖이다. Codex 가 `../chemical/.env` 를 읽는 것은 지금도 샌드박스가 막지 않는다(머리말 금지로만 막음). 이 설계에서 바뀌지 않는다.

## 13. 구현 계획

Codex 1개로 3단계, 단계마다 관련 테스트만 돌리고, 끝에 메인이 직렬 전체를 돌린다. 이어서 Opus 독립 검수 → 보정 → tmux 짧은 실기 → 사용자 터미널.

| 단계 | 범위 | 주요 파일 |
|---|---|---|
| W1 설정·멤버십 | `workspace.repos` 검증, `repoOf`, 표지, `projectRoots`·`resolveCliRoot`·`startPlan`·`init` 표지 처리, `fodh workspace init/add/remove/list`, 백로그 `repo`·`레포` 열·`--repo`, doctor | `config.ts`·`cli/{project-root,root,start,init,index,commands}.ts`·`backlog.ts`·`doctor.ts`·새 `workspace.ts` |
| W2 레포별 git | worktree create/remove/commit/validate·`rootHead`→멤버, `mergeBase`, `fodh worktree merge`, verify 멤버 명령, codex 머리말·`research --repo`, cleanup 워크트리 경로, 원장 `repo` | `worktree.ts`·`state.ts`·`verify.ts`·`codex.ts`·`cleanup.ts`·`templates/codex-header.md` |
| W3 경계·안내 | 훅 멤버 쓰기 거부·git 읽기 목록·멤버 비밀 정책·승인 규칙 합집합, CLAUDE.md 관리 블록, brain-rules·스킬, 상태줄 `T·repo` | `hooks/pretooluse.mjs`·`hooks/secret-*.mjs`·`claude-md.ts`·`templates/*`·`skills/*`·`extensions/*` |

필수 테스트

- 임시 폴더에 멤버 git 저장소 3개 + 워크스페이스. 가짜 Codex 로 T01(web)→T02(backend, 의존 T01)→T03(app, 의존 T02) 전 흐름. T02 는 T01 병합 전에는 PICK 되지 않는다.
- 멤버 폴더 하위에서 `fodh` 시작 계획이 워크스페이스로 간다. 표지 불일치·멤버 옛 잠금·prefix 브랜치 존재 시 추가 거부.
- 훅: 멤버 main 에 Bash 쓰기·`git -C <멤버> commit/checkout/reset/merge` 거부, `git -C <멤버> log` 허용, 워크트리 쓰기 허용, 멤버 `/` 패턴 비밀 읽기 거부.
- `fodh worktree merge`: 멤버 미커밋 변경·다른 브랜치·충돌(abort 확인)·성공 기록.
- 한 레포 모드 회귀: 기존 테스트 전부 그대로 통과(백로그 표 열·출력 문구 불변).
