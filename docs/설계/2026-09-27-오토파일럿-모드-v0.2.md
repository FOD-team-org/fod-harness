# 오토파일럿 모드 설계 v0.2 (2026-09-27)

> 사용자 요청(2026-09-27): "너의 권장사항으로만 진행하는 autopilot 모드도 만들어줘".
> 켜 두면 하네스가 사용자 대신 **두뇌의 추천안**으로 판단에 답하고, 멈추지 않고 진행한다.
> 되돌리기 어렵거나 밖으로 나가는 동작은 켜져 있어도 사용자 몫이다.

## 0. 요약

| 멈추는 곳 | 지금 | 오토파일럿 |
|---|---|---|
| 두뇌가 `fodh judgment add` 로 올린 선택형 판단(추천 번호 있음) | 사용자가 `- 답:` 을 채울 때까지 대기 | 유예(기본 30초) 뒤 추천 번호로 자동 답 → 적용 → 진행 |
| 승인 필수 판단, 또는 되돌리기 어려운 낱말이 있는 판단(§2-2) | 대기 | **대기(바뀌지 않음)** |
| 하네스가 스스로 올린 판단(교착·소진·정리 실패·고아·훅 승인) | 대기 | **대기** |
| 추천 번호가 없거나 `추천 없음` 인 판단, 재질문, 후속 질문 | 대기 | 대기 |
| 진행 정체 판단(자동 턴 한도) | 대기 | 같은 상태·단계·task 에서 켜져 있는 동안 **1번만** 자동 재개. 두 번째 정체는 대기 |
| 인터뷰 질문(INTERVIEW, 인터뷰에서 넘긴 판단) | 대기 | 대기. `--interview` 로 켰을 때만 추천으로 진행 |
| 두뇌의 `대기: 사용자`(기획 단계) | 대기 | "추천안으로 정하고 진행" 회신을 자동으로 보낸다. 진척 없이 연속 2회까지만 |
| PROJECT_READY(기획 끝, 개발 시작 전) | 사용자가 `/develop-start` | 자동 개발 시작 |
| DONE_ALL(백로그 끝) | 대기 | 대기. 새 범위는 사용자가 정한다 |

- 자동 답은 판단기록에 `- 답 출처: 오토파일럿` 으로 남고, `최근 결정` 에 `(오토)` 가 붙는다. 알림과 상태줄로도 알린다.
- 켜고 끄는 것은 사용자만 한다. 두뇌는 켤 수도 끌 수도 없다.

## 1. 켜고 끄기

| 명령 | 동작 |
|---|---|
| `fodh autopilot on [--for 8h] [--max 30] [--interview]` | 켠다. `--for` 가 지나거나 자동 답이 `--max` 에 이르면 스스로 꺼진다(기본: 기간 없음, 30개). `--interview` 는 인터뷰도 추천으로 진행한다 |
| `fodh autopilot off` | 끈다. 유예 중이던 자동 답도 취소한다 |
| `fodh autopilot status` | 켜짐 여부, 켠 시각, 남은 기간, 자동 답 수/한도, 유예 중인 판단, 정체 재개를 쓴 범위 |
| Pi 창 `/autopilot on\|off\|status` | 위와 같다 |

- 상태 파일은 `.pi/harness-autopilot.json` 이다. 쓸 때는 파일 잠금을 잡는다.

  ```json
  {
    "enabled": true, "since": "…", "until": "…", "interview": false,
    "maxAnswers": 30, "answered": 3,
    "perTask": { "T04": 1 }, "perScope": { "PLANNING:project": 2 },
    "stallResumed": { "ARCH:project:-": true },
    "pending": { "A31": { "firstSeen": "…", "rev": 1, "questionHash": "…", "option": 1 } },
    "recentTitles": ["…"],
    "chat": { "scope": "PLANNING:project", "count": 1 }
  }
  ```

- 두뇌는 이 파일에 쓸 수 없다. 훅이 `.pi/harness*.json` 을 막는다(`pretooluse.mjs:181`).
- CLI `on`·`off` 는 `assertNotBrain` 을 거친다. 두뇌가 스스로 켜서 자기 판단에 자기가 답하는 길을 막는다. `status` 는 누구나 읽는다.
- 켜면 기록을 새로 시작한다. `answered`·`perTask`·`perScope`·`stallResumed`·`recentTitles`·`chat` 을 비운다.
- Pi 창에서는 `ctx.ui.setStatus('fodh-autopilot', '오토 3/30')` 로 따로 표시한다. 결과만 보기 모드가 작업 메시지를 지워도 남는다.
- 헤드리스(`ctx.hasUI === false`)에서는 동작하지 않는다. 사용자가 보는 창이 있을 때만 대신 답한다.

## 2. 판단 자동 답

### 2-1. 출처 표지

판단 항목 끝에 숨은 줄 `<!-- fodh-origin: <값> -->` 을 적는다. 사용자 화면에는 보이지 않는다.

| 값 | 적는 곳 | 뜻 |
|---|---|---|
| `brain` | `addCliJudgment`, 호출자가 두뇌일 때 | 두뇌가 `fodh judgment add` 로 올린 판단 |
| `cli` | `addCliJudgment`, 호출자가 두뇌가 아닐 때 | 사용자가 직접 올린 판단. 대상이 아니다 |
| `stall` | `stopForJudgment`(resume.ts 정체 경로) | 자동 턴 한도로 멈춘 판단 |
| `interview` | `deferQuestion` | 인터뷰에서 판단대기로 넘긴 질문 |

- 두뇌 판별은 `assertNotBrain` 과 같은 검사를 쓴다. `brain-guard.ts` 에 `isBrainProcess(root)` 를 빼고 `assertNotBrain` 도 그것을 부른다.
- 표지가 없는 판단은 모두 대상이 아니다. 예: pick 교착·소진(`pick.ts:125-133`), 정리 실패(`state.ts:326-334`, `resolution: cleanup`), 고아(`pick.ts:112-118`), 훅 승인(`turn.ts:142-148`), 재질문(`judgment.ts:529`).
- 이 기능 전에 만든 판단도 표지가 없어 대상이 아니다.
- 표지는 `questionHash`·rev 계산에 넣지 않는다. `migrateItem` 의 알려진 줄 목록과 순서 목록에 더해 이관해도 남게 한다.
- 두뇌는 판단 파일을 직접 고칠 수 없다(`pretooluse.mjs:238,243`). 표지를 위조할 수 없다.

### 2-2. 대상

아래를 **모두** 만족하는 열린 판단만 자동으로 답한다.

1. 출처가 `brain`, `stall`(§2-4), 또는 `interview` 다. `interview` 는 `--interview` 로 켰을 때만이다.
2. 답이 비어 있다. `held`·`followup`·`reaskOf` 가 없고, `resolution` 이 `cleanup` 이 아니다.
3. `autopilotBlocked(item, config)` 가 거짓이다. 이 판정은 제목·배경·선택지·**추천**·자세히 링크 글자를 모두 본다.
   - 기존 `approvalRequired` 조건: `승인 필수: 예`, 설정 `requiresApproval` 낱말, 기존 낱말 목록
   - 더하는 낱말: 마이그레이션·migrat·배포·deploy·운영·prod·릴리스·release·출시·삭제·delete·drop·되돌리·revert·reset·force·태그·tag·토큰·token·secret·시크릿·키·과금·비용·요금·billing·계정·권한·permission·publish·게시·공개·발송·이메일·SMS·알림 발송
   - 설정 `requiresApproval` 값이 카테고리 ID(`deploy-prod` 등)이면, 그 규칙의 사람이 읽는 이름도 낱말로 쓴다.
4. 선택지가 2개 이상이고, `추천` 이 선택지 번호로 **시작**한다.
   - 허용 꼴: `①…`, `1…`, `1번…`, `1)`, `1.`
   - 번호는 선택지 범위 안이어야 한다.
   - 뒤에 다른 번호가 섞여도 맨 앞 번호만 본다.
   - `추천 없음` 으로 시작하면 대상이 아니다.
5. 한도 안이다.
   - 전체: `answered < maxAnswers`
   - task 를 막는 판단: 막는 task 마다 `perTask[T] < perTaskMax`(기본 3)
   - `--blocks -` 판단: `perScope["상태:단계"] < perScopeMax`(기본 3)
   - 제목을 정규화(공백·번호·rev 제거)한 값이 이번에 켠 뒤 자동으로 답한 제목(`recentTitles`)과 같지 않다. 같으면 "같은 질문이 되풀이됐다" 로 보고 사용자에게 넘긴다.

### 2-3. 흐름

1. **훑기(`autopilotSweep`).** Pi 프로세스가 `agent_end` 뒤와 watcher tick 마다 부른다. 다음 중 하나면 아무것도 하지 않는다.
   - 꺼져 있음, 또는 `until` 이 지나 스스로 끔
   - 두뇌 턴이 돌고 있음
   - `hasActiveJudgmentSnapshot`
   - `userAborted`·`userHold`
   - `hasUI === false`
2. **유예 등록.** 대상인데 `pending` 에 없으면 `{ firstSeen, rev, questionHash, option }` 을 적고 알린다.
   - 알림 키: `autopilot:<A번호>`. 60초 묶음 억제를 피한다.
   - 알림 글: 200자 안. `오토파일럿: A31 을 30초 뒤 ①(<선택지 앞 24자>)로 답합니다 — 막으려면 직접 답하거나 /autopilot off`
3. **유예 만료 검사.** tick 마다 `지금 − firstSeen ≥ delaySeconds` 인 것을 모은다. 타이머를 따로 만들지 않는다(`decisionTimers` 와 겹치지 않는다).
4. **다시 검사.** 모은 판단마다 §2-2 를 다시 본다. rev·`questionHash`·추천 번호가 등록 때와 다르면 `pending` 에서 빼고 새로 등록한다(유예를 다시 센다). 대상이 아니게 됐으면 빼기만 한다.
5. **답 쓰기.** 통과한 판단마다 이렇게 쓴다.

   ```ts
   answerJudgment(root, id, String(option), { expectEmpty: true, expectedRaw: item.raw, source: 'autopilot' })
   ```

   - 판단 파일 잠금 안에서 답이 비었는지와 raw 가 같은지 비교한다.
   - 다르면 `AnswerConflict` 로 끝나고, 사용자 답을 덮어쓰지 않는다.
   - `- 답:`, `- 답 기준 rev:`, `- 답 출처: 오토파일럿` 을 한 번에 쓴다.
6. **한 번에 적용.** 이번 tick 에 쓴 답을 모아 `applyAndResume(pi, context, root, ids, expectedAnswers, 'autopilot')` 을 한 번 부른다. `expectedAnswers` 는 쓴 뒤의 raw 다.
   - 스냅샷이 그사이 생기면 `JudgmentConflict` 가 난다(`judgment.ts:446`). 이때 답은 남기고 다음 tick 에 다시 적용한다. 답이 `답 출처: 오토파일럿` 이고 아직 열린 판단은 "적용 대기" 로 다시 모은다.
   - 오토파일럿 자신의 쓰기는 `judgment-changed` 를 다시 일으키지 않는다(검수 확인). 그래서 이 재시도가 필요하다.
7. **기록.**
   - 원장 `judgment:autopilot`: `{ id, option, recommend(앞 80자), origin, delaySeconds, blocks }`
   - `answered`·`perTask`·`perScope`·`recentTitles` 를 올리고, `pending` 에서 뺀다.
8. **실패.** 적용이 재질문을 만들거나 실패하면 그 판단과 재질문은 사용자 몫으로 남긴다. 재질문은 표지가 없어 대상이 아니다. 알림: `오토파일럿: A31 적용 실패 — 직접 확인이 필요합니다`.

### 2-4. 진행 정체 판단

- `stopForJudgment` 가 `stall` 표지와 함께 범위 키 `상태:단계:task(없으면 -)` 를 적는다(`<!-- fodh-origin: stall ARCH:project:- -->`).
- 켜져 있는 동안 같은 범위 키로 **1번만** 자동 답(① ready 로 되돌려 재개)한다. `stallResumed[범위]` 에 적는다.
- 같은 범위에서 두 번째 정체가 오면 사용자 몫이다. 알림: `오토파일럿: ARCH 에서 두 번째 정체 — 사용자 확인이 필요합니다`.
- 이것으로 "프로젝트 단계 정체는 task 한도가 안 걸려 최대 90턴 돈다"(H1)를 막는다.

### 2-5. 공용 적용 함수

- decideInbox 의 적용+재개 블록(`extensions/orchestrator/index.ts` 적용 호출 ~ `autoResume`, 지금 357-367행)을 `applyAndResume` 로 뺀다. decideInbox 와 오토파일럿이 같이 쓴다.

  ```ts
  applyAndResume(pi, context, root, ids, expectedAnswers, kind): Promise<{ applied: string[]; reasked: …; resumed: boolean }>
  ```

- 적용된 것이 있고 활성 상태면 `awaitingUser: false, autoTurns: 0` 으로 바꾸고 `autoResume` 을 부른다. 지금 decideInbox 동작과 같다.
- decideInbox 의 출력·알림은 바뀌지 않아야 한다(기존 테스트 무수정).

### 2-6. 기록 모양

- 판단기록 항목에 `- 답 출처: 오토파일럿` 이 남는다(`completeJudgment` 가 옮긴다).
- `parseArchive` 가 이 줄을 읽어 `CompletedJudgment.answerSource` 로 준다.
- `최근 결정` 줄은 `→ 답 "1"(오토)` 로 쓴다.
- 이미 적용된 결정을 자동으로 되돌리지 않는다. 사용자가 바꾸려면 두뇌에게 지시하거나 새 판단으로 올린다.

## 3. 두뇌의 `대기: 사용자` 자동 회신

- 지금은 PICK·task 단계·RECLAIM 의 사용자 대기를 거부해 되돌려 보낸다. 그 밖의 단계는 `awaitingUser: true` 로 멈춘다(`extensions/orchestrator/index.ts:253-297`).
- 오토파일럿이 켜져 있으면, 아래를 **모두** 만족할 때 멈추는 대신 두뇌에게 회신을 보낸다.
  1. 상태가 RESEARCH·PRD_DRAFT·ARCH·프로젝트 REVIEW·PLANNING 중 하나다. INTERVIEW 는 `--interview` 일 때만이다.
     - WAIT_JUDGMENT 는 `instruction` 이 받지 않는 비활성 상태라 제외한다.
     - task 단계·PICK·PROJECT_READY 는 제외한다. PROJECT_READY 는 §4 가 따로 다룬다.
  2. `userHold` 가 없다. 사용자가 직접 입력한 턴은 건드리지 않는다.
  3. 대상이 되는 열린 판단(§2-2)이 없다. 있으면 그 판단의 자동 답을 기다린다.
  4. 같은 범위(상태:단계)에서 진척 없이 보낸 회신이 `maxChatReplies`(기본 2)보다 적다.
- 진척(상태·단계·task 변화, 또는 판단 적용)이 생기면 `chat` 계수를 0 으로 되돌린다.
- 한도를 넘으면 지금처럼 멈추고 알린다: `오토파일럿: 두뇌가 사용자 답을 계속 기다립니다`.
- 회신 문구:

  > [오토파일럿] 사용자가 추천안으로 진행하도록 맡겼다. 방금 물은 것은 각각 네 추천으로 정하고 근거를 문서에 남긴 뒤 진행하라. 인터뷰 답은 `--source default` 로 기록한다. 승인 필수이거나 되돌리기 어려운 것, 추천을 정할 수 없는 것만 `fodh judgment add` 로 등록하고(되돌리기 어려우면 `--requires-approval`) 대기: 사용자.

## 4. 단계 관문

- **PROJECT_READY**
  - `/develop-start` 처리기 몸통을 `startDevelopment(pi, ctx, root)` 로 뺀다(`prepareProject`·`send` 포함). 명령과 오토파일럿이 같이 쓴다.
  - 부르는 곳은 두 군데다: tick(켜져 있고, PROJECT_READY 이고, `userHold`·`userAborted` 가 없을 때), 그리고 `/autopilot on` 직후.
  - PROJECT_READY 에 들어올 때 걸린 `awaitingUser` 를 푼다.
  - 사용자 전용 전이(`userOnlyTransitions`)지만, 오토파일럿은 사용자가 켠 것이라 Pi 프로세스가 대신한다. 두뇌 CLI 로는 여전히 거부된다.
  - 알림: `오토파일럿: 기획 완료 → 개발 시작`.
- **DONE_ALL**: 진행하지 않는다. 알림: `오토파일럿: 백로그를 모두 끝냈습니다 — 새 범위는 사용자가 정합니다`.
- **paused(memory)·paused(slot)·CLEANUP_FAILED·DEADLOCK**: 지금 동작 그대로다. 이들이 만드는 판단은 표지가 없어 대상도 아니다.

## 5. 두뇌 안내

- 켜져 있으면 자동 재개 지시(`instruction`) 맨 앞에 한 줄을 붙인다.

  > [오토파일럿 켜짐] 사용자에게 채팅으로 묻지 말고 판단으로 등록한다. 추천은 네가 실제로 고를 안의 번호로 시작한다(예: `① …`). 고를 수 없으면 `추천 없음 — 이유`. 되돌리기 어렵거나 밖으로 나가는 동작은 `--requires-approval` 로 올린다.

- `fodh judgment add` 는 추천을 **거부하지 않는다**. 켜져 있고 선택지가 있는데 추천이 범위 안 번호로도, `추천 없음` 으로도 시작하지 않으면 경고만 낸다: `오토파일럿이 이 판단을 자동으로 답할 수 없습니다: 추천이 번호로 시작하지 않음`. 두뇌가 번호를 지어내게 만들지 않는다.
- `templates/brain-rules.md` 와 `skills/fodh-workflow` 에 두 가지를 적는다.
  - `--requires-approval` 사용법. 지금은 문서에 없다.
  - 오토파일럿 절: 추천은 실제로 고를 안이다. 승인 필수를 피하려고 낱말을 바꾸지 않는다. 같은 질문을 제목만 바꿔 다시 올리지 않는다.

## 6. 인터뷰

- `deferQuestion` 은 이미 추천 선택지를 맨 앞(①)에 둔다. 선택지가 없으면 `['추천안 채택','직접 답하기']` 다.
- 추천을 `① <추천 글>` 꼴로 적는다. 추천이 선택지 어디에도 맞지 않으면 지금처럼 글만 적는다(번호 없음 → 대상 아님).
- `interview` 표지를 적는다. 자동 답은 `--interview` 로 켰을 때만 한다.
- 새 인터뷰 출처 값은 만들지 않는다. 채팅 회신으로 두뇌가 기록하는 답은 `--source default` 다.

## 8. 테스트

1. `recommendedOption`
   - 꼴: `①`, `1번`, `1)`, `1.`, `1 `
   - 범위 밖이면 없음. 번호로 시작하지 않으면 없음. `추천 없음` 이면 없음.
2. `autopilotBlocked`
   - 추천 칸에만 "배포" 가 있어도 막힌다.
   - `승인 필수: 예` 는 막힌다.
   - 설정 카테고리 ID 의 이름 낱말이 있으면 막힌다.
3. 출처 표지
   - 두뇌(`FODH_BRAIN=1`)의 `judgment add` → `brain`. 사용자 CLI → `cli`.
   - pick 교착·정리 실패·고아·훅 승인·재질문 판단은 표지가 없어 대상이 아니다.
   - 표지는 `questionHash`·rev 를 바꾸지 않고, `judgment migrate` 뒤에도 남는다.
4. 대상 판정
   - held·followup·reaskOf·cleanup, 선택지 1개 이하, 전체·task·범위 한도, 같은 제목 되풀이는 제외된다.
   - `interview` 는 `--interview` 없이는 제외된다.
5. 경합
   - 유예 중 사용자가 답하면 건너뛴다.
   - 끄면 취소된다.
   - rev·`questionHash`·추천이 바뀌면 다시 센다.
   - 두뇌 턴 중이나 활성 스냅샷이 있을 때는 쓰지 않는다.
   - `answerJudgment` 가 잠금 안에서 사용자 답을 발견하면 `AnswerConflict` 로 끝나고 덮어쓰지 않는다.
   - 적용 중 `JudgmentConflict` 가 나면 다음 tick 에 다시 적용된다.
6. 흐름
   - 가짜 두뇌가 task 판단(`--blocks T --reclaim`)을 올린다 → 테스트 시계로 30초 뒤 ① 답 → 적용 → `awaitingUser` 가 풀리고 PICK 이 T 를 다시 고른다.
   - 판단기록에 `답 출처: 오토파일럿`, `최근 결정` 에 `(오토)`, `parseArchive().answerSource === '오토파일럿'` 이 남는다.
   - 같은 tick 에 만료된 두 판단은 `applyJudgments` 한 번으로 적용된다.
7. 정체
   - 같은 범위 첫 정체는 자동 재개되고, 두 번째는 대기한다.
   - 프로젝트 단계(`blocks -`) 정체도 같다.
8. `대기: 사용자`
   - PLANNING 에서 두 번까지 회신하고, 세 번째는 `awaitingUser` 로 멈춘다. 진척이 있으면 계수가 되돌아간다.
   - INTERVIEW 는 `--interview` 없이는 회신하지 않는다.
   - task 단계·PICK·PROJECT_READY 에서는 회신하지 않는다.
   - `userHold` 가 있으면 보내지 않는다.
   - 대상 판단이 열려 있으면 회신하지 않는다.
9. PROJECT_READY
   - 켜진 상태에서 들어오면 자동 PLANNING 으로 간다.
   - PROJECT_READY 에서 `/autopilot on` 을 하면 바로 시작한다.
   - DONE_ALL 은 멈춘다.
10. 권한
    - 두뇌의 `fodh autopilot on`·`off` 는 거부된다.
    - 두뇌가 `.pi/harness-autopilot.json` 에 쓰면 훅이 거부한다.
11. 꺼져 있으면 기존 동작·출력이 바뀌지 않는다. 기존 테스트가 무수정으로 통과한다. `applyAndResume`·`startDevelopment` 추출 뒤에도 같다.
12. 알림 키가 판단마다 다르고, 글이 200자 안이다.

## 10. 한계

- 막는 낱말 판정은 넓게 잡는다. 예: "배포 방식 선택" 같은 기획 판단도 자동으로 답하지 않는다. 막는 쪽 오차라 그대로 둔다. 자주 걸리면 설정으로 낱말을 조정하는 것을 뒤에 검토한다.
- 추천의 질은 두뇌에 달렸다. 오토파일럿은 추천을 검증하지 않는다. 기록·알림·`(오토)` 표시로 사후 확인을 돕는다.
- Pi 창이 떠 있을 때만 동작한다. 창을 닫으면 자동 답도 멈춘다.
- 이 기능 전에 만든 판단은 표지가 없어 자동으로 답하지 않는다.

## 11. 구현 순서

- 워크스페이스 모드 W1 이 끝나고 검수·커밋한 **다음**, W2 **전**에 한 번의 Codex 작업으로 넣는다. Codex 는 한 번에 하나만 돌린다.
- 이유: `config.ts`·`cli/index.ts` 를 W1 이 고쳤으니 그 위에서 한다. W2 는 orchestrator·훅을 크게 고치니 그 전에 넣으면 겹침이 적다.
- 사용자에게 새로 물을 것은 없다. 사용자가 요청했고, 되돌리기 어려운 동작은 범위에서 뺐다.
