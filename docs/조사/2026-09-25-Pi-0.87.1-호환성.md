### 3-1. 필수: `agent_end` 자동 재개가 멈춘다

- **0.73.1 동작**: 확장 `agent_end` 를 별도 이벤트 큐에서 비동기로 돌렸다(`O:dist/core/agent-session.js:234-244`). 그 사이 agent 의 `finishRun()` 이 `isStreaming=false` 로 만든다(`O:node_modules/@mariozechner/pi-agent-core/dist/agent.js:342-348`). 그래서 우리 핸들러가 여러 번 await 한 뒤 도달하는 `autoResume` 의 `isIdle()` 검사가 통과할 수 있었다(코드상 추정. P7 실사용이 방증).
- **0.87.1 동작**: "event settlement 를 awaited lifecycle 로" 바꿨다(CL:1593, 0.75.4).
  - `_handleAgentEvent` 가 확장 `agent_end` 를 run 안에서 await 한다(`agent-session.js:556`, `:579-580`, `:715-716`).
  - `_isAgentRunActive` 는 `_runAgentPrompt` 시작 때 true 가 된다(`:1078-1080`). false 로 돌아가는 곳은 `_emitAgentSettled` 하나뿐이다(`:531-533`).
  - `isIdle` 은 `!_isAgentRunActive && !isCompacting` 이다(`:875-877`). `ctx.isIdle` 은 이 값을 그대로 넘긴다(`:2447`, `runner.js:589-591`).
- **결과**: `extensions/orchestrator/index.ts:260·273·282` 의 `autoResume(…'agent_end')` 는 `resume.ts:53` 에서 항상 `{skipped:'busy'}` 를 돌려준다. 타이머·워처 경로(`index.ts:345-430`)는 유휴 때 도니까 영향이 없다.
- **안 A(권장)**: `agent_end` 에서 부를 때만 유휴 검사를 건너뛰고 `deliverAs:'followUp'` 으로 보낸다.
  - streaming 중의 followUp 은 `agent.followUp()` 으로 동기 큐에 들어간다(`agent-session.js:1494-1497`). `_handlePostAgentRun` 이 큐를 보고 `agent.continue()` 한다(`:1134-1137`, CL:1492 0.77.0).
  - 공식 예제도 `agent_end` 에서 `{triggerTurn:true, deliverAs:'followUp'}` 를 유휴 검사 없이 쓴다(`N:examples/extensions/plan-mode/index.ts:262`, `:328`).
  - run 이 계속 active 라서 다른 경로의 `autoResume` 은 busy 로 막힌다. "검사와 전환 사이 await 없음" 불변식(`resume.ts:97`)도 유지된다.
- **안 B**: 재개를 `agent_settled` 로 옮긴다. 여기서는 `isIdle()===true` 다(CL:41). 다만 triggerTurn 이 `_deferredSettledActions` 로 연기된다(`agent-session.js:1502-1505`). 연기 창 동안 워처 타이머가 `isIdle()` true 를 보고 두 번째 메시지를 보낼 수 있다. `agent_settled` 에는 `messages` 도 없어서 `agent_end` 판정을 저장해 두어야 한다.
- **테스트**: 가짜 ctx 가 `agent_end` 중 `isIdle:()=>false` 를 돌려주는 경우를 추가한다.

### 4-2. K2(session_start 재설치 + 턴마다 맨 앞 복구)

- 여전히 맞다.
  - Pi 는 init 에서 한 번 prepend 한 뒤 다시 등록하지 않는다(`registerSignalHandlers()` 호출은 :629 한 곳).
  - session_start 는 그 뒤에 온다(:739 → `agent-session.js:2313`).
  - `ensureShutdownReclaimFirst()` 의 `rawListeners`/`prependListener` 조작도 그대로 통한다.
- 이유는 약해졌다. `src/provider/shutdown.ts:24` 주석의 "may exit synchronously" 는 0.87.1 에서는 거짓이다(SIGHUP 동기 종료 제거). 맨 앞 위치는 "회수를 제일 먼저" 보장용으로만 남긴다. 주석은 고친다.

### 4-3. SIGHUP·SIGTERM 흐름(0.87.1)

1. 우리 처리기(맨 앞)가 두뇌 그룹에 TERM 과 KILL 을 보내고 orphan 파일을 쓴다. 그다음 자기를 해제하고 같은 신호를 자기에게 재전송한다(`shutdown.ts:27-39`).
2. 같은 dispatch 에서 Pi 처리기가 `shutdown({fromSignal:true})` 를 시작한다.
3. 재전송된 신호는 Pi 처리기(아직 등록됨)가 받는다. `isShuttingDown` 이라 무시한다(:3363-3365). signal-exit 도 "리스너가 자기뿐"이 아니라 아무것도 안 한다.
4. `dispose()` 가 `session_shutdown` 을 발행한다. provider 는 `controller.abort()` 한 뒤 **`await pending`(상한 없음, `extensions/provider/index.ts:111`)**, 잠금 해제 순으로 진행한다. 끝나면 `exit(0)` 이다.

- **개선**: SIGHUP 에서도 `.pi/harness.lock` 해제와 확장 정리가 돈다. 0.73.1 에서는 exit(129) 로 건너뛰었다.
- **위험**: 우리 핸들러나 다른 확장의 `session_shutdown` 이 멈추면 Pi 가 영영 안 끝난다. 터미널이 닫힌 뒤라 좀비가 된다.
  - **권장**: `await pending` 을 수 초 상한의 `Promise.race` 로 감싼다. watcher 의 `await pending; await memoryPending`(`extensions/watcher/index.ts:120`, `:137`)도 같다.
  - 종료 코드는 129/143 이 아니라 0 이 된다. fodh 는 종료 코드에 의존하지 않는다(확인 범위 내).

### 4-4. K3(SIGINT 물러섬): 판정이 실제 Pi 에서 항상 참

- Pi 는 시작하자마자 proper-lockfile 을 로드한다. 그 모듈 최상위의 `onExit()` 가 signal-exit v3 를 load 하고, signal-exit 는 `SIGINT`·`SIGHUP`·`SIGTERM` 등에 `process.on` 리스너를 단다.
  - 0.73.1 근거: `O:dist/core/settings-manager.js:4`, `O:dist/core/auth-storage.js:12`, `O:node_modules/proper-lockfile/lib/lockfile.js:331`, `O:node_modules/signal-exit/index.js:144-158`.
  - 0.87.1 근거: `N:package.json:66` proper-lockfile 4.1.2. 번들 chunk 최상위에 `import_proper_lockfile=__toESM(require_proper_lockfile(),1)` 가 있다. `cli-runtime.js` 가 그 chunk 를 정적 import 한다.
- 그래서 `shutdown.ts:28` 의 "표식 없는 SIGINT 리스너가 하나라도 있으면 물러선다"는 Ctrl+Z 중이 아니어도 항상 참이다.
- 게다가 signal-exit 는 "리스너 수 == 자기 수"일 때만 재전송해 죽는다(`signal-exit/index.js:111-131`). 우리 리스너가 남아 있으니 그 조건도 거짓이다. **외부 `kill -INT` 는 두뇌도 회수하지 않고 Pi 도 죽이지 않고 그냥 사라진다.**
- P8 테스트(`test/p7-brain-lifecycle.test.ts:210`, `:223`)는 vitest 프로세스에 signal-exit 가 없어서 통과한다.
- 이 결함은 0.73.1 에도 똑같이 있다. 업그레이드가 만든 문제가 아니다. 0.87.1 에서도 달라지지 않는다.
- **권장 수정**:
  - 표식 없는 SIGINT 리스너 수에서 `process.__signal_exit_emitter__?.count ?? 0` 을 빼고, 남는 것이 있을 때만 물러선다.
  - 또는 Pi 의 일시 정지 상태를 직접 본다. `handleCtrlZ` 는 정지 중에만 `SIGCONT` once 리스너를 단다. `process.listenerCount('SIGCONT') > 0` 이면 물러서는 식이다.
  - 회수 뒤 우리가 해제하고 재전송하면 signal-exit 가 마지막 리스너가 된다. 그러면 unload → exit 이벤트 → 재전송으로 기본 종료된다.
  - 테스트에 signal-exit 모사 리스너를 넣는다.

## 5. 프로바이더 계약

- **등록**: `registerProvider('claude-code', config)` 는 그대로다.
  - `streamSimple` 에는 `api` 가 필수다(`N:dist/core/provider-composer.js:306-307`). 모델 `api` 가 같으면 우리 `streamSimple` 로 보낸다(`:337-338`).
  - 인증 수단이 없으면 예외를 던진다(`:334`). `apiKey:'local-cli-no-credential'` 은 리터럴로 해석된다(ProviderConfig 주석 `types.d.ts:1166`). 문제없다.
  - 로드 중 등록은 큐에 들어갔다가 세션을 만들기 전에 적용된다(`N:dist/core/agent-session-services.js:72-84`). 그래서 `--model claude-code/<id>` 를 해석할 수 있다(실행 미확인).
- **모델 필드**: 필수 필드는 `id·name·reasoning·input·cost·contextWindow·maxTokens` 다(`types.d.ts:1209-1240`). 우리는 모두 준다. `cost.tiers` 는 선택이다(`AI:dist/types.d.ts:781-784`, CL:952).
- **streamSimple 입력**: `context` 가 `Context` 에서 `TranscriptContext` 로 바뀌었다(CL:99, 0.86.0; `AI:dist/types.d.ts:446-455`). 시스템 프롬프트와 도구는 `messages` 안의 system 메시지로 온다.
  - 우리는 `systemPrompt`·`tools` 를 읽지 않는다. `latestMessage()` 는 마지막 user/custom 메시지만 읽는다(`src/provider/turn.ts:371-378`).
  - custom 메시지는 LLM 문맥에서 user 로 바뀐다(`N:dist/core/messages.js:89-95`). 그래서 영향이 없다.
  - 타입: `stream.ts` 의 `context: Context` 매개변수는 구조적으로 `TranscriptContext` 를 받는다(추정. typecheck 로 확인 필요).
- **스트림 이벤트**: `start`, `text_start/delta/end`, `done{reason:stop｜length｜toolUse｜deferred}`, `error{reason:aborted｜error}` 이다(`AI:dist/types.d.ts:456-523`).
  - 우리는 `done:'stop'` 과 `error:'error'｜'aborted'` 만 낸다(`extensions/provider/stream.ts`). 규약 안이다.
  - 준비 실패 때 `start` 다음 바로 `error` 를 내는 것도 허용된다(같은 파일 주석 :462-465).
- **StopReason**: `pending`·`deferred` 가 추가됐다(`AI:dist/types.d.ts:292`, CL:672). 우리는 내지 않는다.
- **Usage**: `input·output·cacheRead·cacheWrite·totalTokens·cost{…,total}` 로 같다. `cacheWrite1h`·`reasoning` 이 선택 필드로 추가됐다(`AI:dist/types.d.ts:270-291`).
- **`onPayload`/`onResponse` 호출 의무**(ProviderConfig 주석): HTTP 요청을 보내는 프로바이더에 해당한다. 로컬 CLI 인 우리에게는 해당 없다.

## 6. 그 밖의 관련 변경

- **컴팩션 설정**: 키 `compaction.enabled` 는 그대로다(`N:docs/settings.md:54`). 모델별 `compaction.modelOverrides` 가 생겼지만 `enabled` 는 전역 전용이다(`N:docs/compaction.md:459`, CL:110).
  - 현재 `~/.pi/agent/settings.json` 에는 `lastChangelogVersion` 만 있어서 컴팩션이 켜져 있다.
  - 프로젝트 `.pi/settings.json` 은 신뢰 대상이다(§6 신뢰 항목). **전역 `~/.pi/agent/settings.json` 에 `"compaction": {"enabled": false}` 를 넣는 것을 권장**한다. `extensions/provider/index.ts:85` 안내 문구도 그에 맞춘다.
- **`-e`**: 그대로 반복 가능하다(`N:docs/cli.md:150-151`). 명령줄 확장은 신뢰 게이트 대상이 아니다. `project_trust` 이벤트에 참여할 수도 있다(`N:docs/extensions.md:50`, `N:docs/security.md:61`). `--` 옵션 끝 구분자(0.84.3)와 `--mode` 값 검증(0.87.1)이 추가됐다. 우리 실행법에는 영향이 없다.
- **프로젝트 신뢰·샌드박스**: 0.79.0 부터 `.pi/settings.json`, `.pi/extensions|skills|prompts|themes`, `.pi/SYSTEM.md`·`APPEND_SYSTEM.md` 가 있으면 신뢰를 묻는다(CL:1367-1375; `N:docs/security.md:35-44`).
  - 빈 `.pi` 나 우리 `.pi/harness.json`·`harness.lock`·상태 파일은 해당하지 않는다(security.md:44).
  - TUI 기본값은 `defaultProjectTrust:"ask"` 다(CL:1331, 0.79.1). 결정은 `~/.pi/agent/trust.json` 에 저장되고 `--approve` 로 1회 허용할 수 있다(cli.md:192).
  - `CLAUDE.md`·`AGENTS.md` 는 신뢰와 무관하게 로드된다(security.md:55).
  - 샌드박스는 여전히 없다(security.md:3-7).
- **세션 저장**: `CURRENT_SESSION_VERSION` 은 양쪽 다 3 이다(`N:dist/core/session-manager.js:11`, `O:` 같은 파일 :8).
  - 0.87.0 부터 `SessionManager` 가 문맥의 기준이 되고 `ContextEditEntry` 가 추가됐다(CL:37-38). 우리는 sessionManager 를 쓰지 않는다.
  - 0.87.1 로 만든 세션을 0.73.1 로 이어 쓰는 것은 보장되지 않는다(§8).
- **input `source`**: 값 집합은 그대로다(§3). 우리 `event.source !== 'extension'` 검사(`extensions/orchestrator/index.ts:98-`)는 유지된다.
- **sendMessage 옵션**: `triggerTurn:false` 관련 수정(CL:410 0.84.2, CL:273 0.84.4)은 우리가 쓰지 않는 경로다. 명령 경로 `send()`(`resume.ts:37-40`)가 streaming 중 deliverAs 없이 보내면 steer 가 된다. 이것도 이전과 같다.
- **setActiveTools**: 의미는 그대로다. 0.87 은 세션 재개 때 transcript 에 기록된 도구 구성을 복원한다(`agent-session.js:1062-1074`). 우리 `selectTools` 와의 순서는 미확인이다(§8).
- **확장 로딩 수명**:
  - 같은 디렉터리의 세션 전환은 모듈을 재사용하고 인스턴스만 새로 만든다(0.79.9). 모듈 전역 상태는 global Symbol 이라 안전하다.
  - 공식 문서는 팩토리에서 프로세스·타이머를 시작하지 말라고 한다(`N:docs/extensions.md:58-60`). `extensions/provider/index.ts:24` 는 팩토리에서 신호 처리기를 단다. 세션 없이 확장만 로드하는 호출(예: `pi --help`)에서도 붙는다. 영향은 작지만 session_start 로 옮기는 것을 고려한다.
- **자동 업데이트 알림**:
  - 시작 때 pi.dev 최신 버전을 조회한다. `PI_SKIP_VERSION_CHECK=1` 로 끄고, `PI_OFFLINE=1` 은 카탈로그 갱신까지 끈다(`N:docs/environment-variables.md:84-85`).
  - `pi update` 는 Pi 자체를 올린다(cli.md:225-240). 의도하지 않은 업그레이드를 막으려면 실행 레시피에 `PI_SKIP_VERSION_CHECK=1` 을 넣는다.
  - 첫 실행 때 변경 기록이 한 번 표시된다(`lastChangelogVersion`).

## 7. 이관 절차 제안

1. **선행**: P8 push 를 마친다. 실행 중인 `pi`·하네스 세션을 모두 끝낸다(전역 교체 중 lazy chunk 로드가 깨지는 것을 막기 위해). `pi --version` 이 0.73.1 인지 기록한다.
2. **Codex 위임 스펙(1건)**:
   - (a) import·package.json 이름 교체(§2 목록), `test/p7-turn.test.ts:209`, `test/revision.test.ts:173`.
   - (b) §3-1 안 A 와 그 테스트.
   - (c) §4-4 K3 판정 수정과 signal-exit 모사 테스트.
   - (d) `session_shutdown` 대기 상한(provider·watcher).
   - (e) `shutdown.ts:24` 주석과 `index.ts:85` 안내 문구.
   - 코드는 설치 전에 써도 된다. typecheck 와 test 는 3단계 뒤에 한다.
3. **전역 설치**(사용자 승인 뒤):
   ```sh
   npm uninstall -g @mariozechner/pi-coding-agent
   npm install -g @earendil-works/pi-coding-agent@0.87.1
   pi --version   # 0.87.1
   ```
   `~/.pi/agent/settings.json` 에 `"compaction": {"enabled": false}` 를 넣는다. 같은 bin 이름 때문에 순서를 바꾸면 npm 이 EEXIST 로 거부할 것으로 본다(미확인).
4. **저장소 테스트**: `npm install`(새 `file:` 링크) → `npm run typecheck` → `npm test`. 기준선 대비 실패 0 이어야 한다.
5. **장난감 스모크**(`PI_SKIP_VERSION_CHECK=1 pi -e …/provider/index.ts -e …/orchestrator/index.ts -e …/watcher/index.ts --model claude-code/<model>`):
   - 확장 로드 오류가 없고 신뢰 프롬프트가 안 뜨는지(뜨면 원인 파일 확인).
   - 두뇌 1턴이 끝난 뒤 자동 재개가 되는지(원장·`autoTurns` 증가).
   - `/hold`, `/status` 가 되는지.
   - 터미널 닫기(SIGHUP) 뒤 두뇌 그룹이 사라지고, `.pi/harness.lock` 이 해제되고, 다음 시작 때 orphan 복구가 되는지.
   - `kill -INT <pi>` 에서 회수하고 종료하는지.
   - Ctrl+Z → `fg` 뒤 회수가 없는지.
   - `/reload` 뒤 `process.listenerCount('SIGHUP')` 이 늘지 않는지(원장 `shutdown:reorder` 로 간접 확인).
   - 그다음 Opus 5.5·Fable 5.1 비교 시험으로 넘어간다.
6. **롤백**:
   ```sh
   npm uninstall -g @earendil-works/pi-coding-agent
   npm install -g @mariozechner/pi-coding-agent@0.73.1
   ```
   저장소는 이관 커밋을 되돌리고 `npm install` 로 링크를 복구한다. 0.87.1 에서 만든 세션은 재개하지 말고 새 세션으로 시작한다. `~/.pi/agent/trust.json` 과 settings 의 컴팩션 항목은 0.73.1 에서도 무해하다. 예비로 `npm pack @mariozechner/pi-coding-agent@0.73.1` tarball 을 보관해 둔다.

## 8. 미확인

- 실제 실행은 하나도 하지 않았다: 0.87.1 `pi` 기동, `npm run typecheck`, `npm test`, 장난감 스모크 모두.
- 0.73.1 에서 `agent_end` 중 `isIdle()` 이 true 였다는 것은 코드상 추정이다(이벤트 큐 + finishRun 순서). 0.87.1 에서 false 인 것은 코드로 확인했다.
- K3 에서 signal-exit 리스너가 실제 프로세스에 붙어 있다는 것은 코드 경로로 확인했다. `process.listeners('SIGINT')` 를 실측하지는 않았다.
- SIGHUP 때 `controller.abort()` 뒤 `pending` 이 얼마 만에 풀리는지 확인하지 않았다(`runTurn` 중단 경로 실측 필요).
- `--model claude-code/<id>` 시작 해석, `TranscriptContext` 타입 적합성, 세션 재개 때 도구 복원과 `selectTools` 의 순서는 확인하지 못했다.
- npm 전역 bin 충돌 동작, `auth.json` 호환, 0.87.1 세션을 0.73.1 이 읽을 수 있는지도 확인하지 못했다.
- 번들은 압축 파일이라 신호 코드와 proper-lockfile 외의 부분은 비번들 dist 와 같다고 가정했다.
- Codex 가 P8 작업 트리를 편집 중이라 `src/provider/shutdown.ts` 등의 줄 번호는 바뀔 수 있다.
