# VC1 보정 3 — 위임 스펙

- 기준: VC1 + 보정 1·2 작업 트리(미커밋). 전체 직렬 123파일 · 3805 / 3805, typecheck 통과.
- 근거: Opus 3차 검수(APPROVE_WITH_FIXES).
  - 설정이 들어간 뒤는 단조 규칙이 막는다(변형 공격 모두 거부 확인).
  - 남은 구멍은 **첫 자동 채움**과 git clean 판정에 있다.
- 범위: `src/core/verify.ts`, `src/core/verify-detect.ts`, `src/core/workspace.ts`·`src/cli/init.ts`(호출만), `templates/prompts/VERIFY.md`, README, vc1 테스트, 결과 문서.

## 배경 — 검수 재현

모두 설정이 빈 첫 채움이다. 훅은 두뇌에게 이 조작을 허용한다.

1. `git update-index --skip-worktree package.json` 뒤 `test` 스크립트 삭제 → status 가 비어 있음 → `[typecheck,lint]` 로 채움, `ok:true, clean:true`.
2. `git config status.showUntrackedFiles no` + 미추적 `pubspec.yaml` → node 프로젝트가 dart 로 설정된다.
3. `mv .git .git.bak` → `clean:null` 이라 검사를 건너뛰고 채움 → 복원 뒤 `clean:true`.
4. `chmod 444 web` → `package.json` 읽기 EACCES 를 `catch {}` 가 삼켜 `web` 의 node 명령이 조용히 빠진다.

1·2 는 VC1 이전부터 있던 REVIEW 게이트 clean 증거도 똑같이 속인다.

근본 원인: 감지가 **두뇌가 흔들 수 있는 작업 디렉터리**를 읽는다.

## I1 [중간] 두뇌가 닿는 감지는 커밋된 트리(HEAD)를 읽는다

- `detectVerify` 의 파일 읽기를 "트리 읽기" 한 겹으로 감싼다. 구현은 두 가지다.
  - **fs**: 지금 동작(readdir·readFile·lstat).
  - **git HEAD**: `git -C <base> ls-tree` 로 디렉터리 항목(이름·종류·심링크 모드 120000)을 읽고, `git -C <base> show HEAD:<경로>`(또는 `cat-file -p`)로 파일 내용을 읽는다.
    - 경로는 base 기준 상대 경로다. base 가 저장소 루트의 하위 폴더일 수 있으니 `git rev-parse --show-prefix` 를 붙인다.
    - 심링크 항목은 fs 와 똑같이 건너뛴다.
    - 탐색 깊이·건너뛸 이름·우선순위·`hasTests`·G7·G8 규칙은 fs 와 똑같다. 명령 모양도 같다.
- 어디서 무엇을 읽는가
  - `runVerify` 자동 채움(I3 새로 고침 포함)과 `fodh verify detect`(미리보기·`--apply` 모두): base 가 git 작업 트리면 **git HEAD** 를 읽는다. 아니면 fs 를 읽는다.
  - `fodh init`·`workspace init/add`(사용자 전용): 지금처럼 **fs** 를 읽는다(사용자가 아직 커밋하지 않은 코드에서도 설치 가능해야 함).
  - `--approve`(사용자) 경로도 git HEAD 를 읽는다. 사용자가 미커밋 파일로 설정하고 싶으면 커밋하면 된다. 문구에 적는다.
- **fail closed**: base 가 등록 워크트리(`state.worktrees` 기록이 있음)인데 git 정보를 못 읽으면 감지·기록하지 않고 실패한다. 예: `mv .git`, HEAD 없음.
  - `runVerify`: `finish({ ok: false, error: '등록 워크트리에서 git 정보를 읽을 수 없습니다 — .git 과 HEAD 를 확인하세요' })`
  - `detect`: 같은 문구로 throw.
- HEAD 를 읽으면 skip-worktree·미추적 숨김·chmod·gitignore 조작이 감지에 영향을 주지 못한다.
  - 두뇌가 약화를 **커밋**하면 검수 diff·로그에 남는다.
  - 커밋 뒤 되돌려도 I3 새로 고침이 최종 HEAD 에서 다시 채운다.
- 보정 2 H1-1(clean 에서만 자동 기록)은 남긴다. 판정은 I2 의 강화된 clean 을 쓴다.
- 테스트(검수 재현 1~4 를 회귀로)
  - 빈 설정의 git 워크트리에서 각 조작 뒤 `verify run` → 설정에 `npm test`(또는 node 명령)가 들어가거나, dirty·git 오류로 실패한다. 어느 쪽이든 줄어든 설정은 기록되지 않는다.
  - `mv .git` 은 git 오류로 실패한다.
  - fs 와 git HEAD 가 같은 트리에서 같은 결과를 내는지 표 테스트를 한다(기존 vc1-verify-detect 케이스 중 대표 몇 개를 git 커밋 뒤 HEAD 모드로 한 번 더).

## I2 [중간] clean 판정 강화(`gitSnapshot`)

- `gitSnapshot` 의 clean(REVIEW 게이트 증거와 자동 기록 모두 쓴다)을 저장소 설정과 무관하게 고정한다.
  - `git -c core.fsmonitor=false status --porcelain --untracked-files=all --ignore-submodules=none` 가 비어 있어야 한다.
  - `git ls-files -v` 에서
    - 소문자 태그(assume-unchanged) 항목이 하나라도 있으면 dirty 다.
    - `S`(skip-worktree) 항목 중 작업 트리에 파일이 **존재하는** 것이 있으면 dirty 다(sparse checkout 으로 없는 파일은 제외).
- `dirtyPaths` 도 같은 status 옵션을 쓴다.
- 전역 excludesFile(`.DS_Store` 등)은 존중한다(바꾸지 않는다).
- 테스트
  - skip-worktree + 수정된 파일 → clean=false.
  - assume-unchanged → clean=false.
  - `status.showUntrackedFiles=no` 설정 + 미추적 파일 → clean=false.
  - sparse 로 없는 S 항목만 있으면 clean=true.
- 이 변경이 기존 REVIEW 게이트 테스트를 깨면 멈추고 결과 문서에 적는다.

## I3 [낮음·설계] 자동 설정 새로 고침(추가만)

- 첫 채움 때 `test/` 가 없으면 `flutter test` 가 빠지고, 뒤에 테스트를 커밋해도 추가되지 않는다. 사용자 요구("알아서 세팅")와 어긋난다.
- 결정: 일반 `verify run`(heavy 아님)에서 설정이 **자동 관리 상태**면 매번 HEAD 를 다시 감지한다. 자동 관리 상태 = 표지 있음 + hash 일치 + 자리표시 아님.
  - 감지 결과가 현재 설정을 **포함하고 더 많을 때만**(commands·heavy 모두 추가만, heavySource 'user' 면 heavy 는 비교·변경하지 않음) `writeAutoVerify` 로 기록한다. 그리고 원장 `verify:auto-config`(`via: 'refresh'`)과 알림을 남긴다.
  - 같거나, 빠지거나, 감지 실패·git 오류·dirty 면 아무것도 쓰지 않고 현재 설정으로 그대로 실행한다. 오류가 아니다. 원장은 쓰지 않아도 된다.
  - 새로 고침은 실행 전에 한다. 실행되는 명령은 새 설정이다.
- 테스트
  - flutter 앱 첫 채움(`test/` 없음) → `test/x_test.dart` 커밋 → 다음 `verify run` 이 `flutter test` 를 추가하고 실행한다.
  - lint 스크립트 삭제 커밋 뒤 run → 설정 그대로(`npm run lint` 실행, 실패).
  - 사용자 설정(표지 없음)은 새로 고치지 않는다.
  - 커밋 → 되돌림 공격: `test` 삭제 커밋 → 첫 채움 `[typecheck,lint]` → 되돌림 커밋 → 다음 run 에서 `npm test` 가 다시 들어간다.

## I4 [낮음] 파일 읽기 오류

- `verify-detect.ts` 의 `package.json` 파싱 `catch {}` 는 `SyntaxError` 만 삼킨다.
- 감지용 파일(`package.json`·`pubspec.yaml`·`pyproject.toml`) 읽기의 `EACCES`·`EPERM` 은 `DetectUnreadableError(상대경로)` 로 바꾼다(fs 모드).
- `runVerify` 는 이 오류를 throw 하지 않고 `finish({ ok:false, … })` 로 돌려준다. 보정 2 의 폴더 오류와 같은 경로다.
- init·workspace 는 경고 + 미감지로 설치를 끝낸다. `harness.json` 을 만든 뒤 중간에 끊기지 않는다.
- 테스트
  - fs 모드에서 `chmod 444 web`(readdir 가능·파일 읽기 불가), `pubspec.yaml` 000 → runVerify(비-git) `ok:false` 감지 실패 문구.
  - `fodh init` 은 경고와 함께 완료된다.

## 템플릿·문서

- `VERIFY.md`: 새 오류 문구(`등록 워크트리에서 git 정보를 읽을 수 없습니다`)를 더한다. 자동 설정은 "커밋된 내용 기준"이라는 한 줄을 넣는다. 예: 새 테스트·스크립트는 커밋 뒤 다음 검증에서 자동 추가된다.
- README 프리셋 절: HEAD 감지·새로 고침(추가만)·단조 규칙을 3줄로 적는다.

## 작업 규칙

- 전체 테스트(`npm test`, 인자 없는 `npx vitest run`)는 돌리지 않는다.
  - 반드시 돌릴 파일: vc1 3개, `verify.test.ts`, `w1-membership.test.ts`, `w1-config.test.ts`, `templates.test.ts`, `w3b-templates.test.ts`, `w3b-golden.test.ts`.
  - I2 때문에 `rg -l "clean" test/` 로 REVIEW 게이트·clean 관련 테스트 파일을 찾아 함께 돌린다.
  - 모든 vitest 호출에 `FODH_NOTIFY_OS=off --maxWorkers=1 --no-file-parallelism` 을 붙인다.
  - `npm run typecheck`·`git diff --check` 도 돌린다.
- VC1 이전 테스트의 단언은 바꾸지 않는다. 바꿔야 하면 멈추고 결과 문서에 적는다. vc1 테스트는 이 스펙대로 고친다.
- `/bin/ps` 차단 때문에만 실패하는 테스트는 기록만 한다.
- 커밋·브랜치는 만들지 않는다(테스트용 임시 저장소는 괜찮다). 비밀값을 쓰지 않는다.
- 결과 문서 끝에 "보정 3" 절을 더한다. 내용: I1~I4 변경 파일:줄, 새·바뀐 테스트, 돌린 파일과 결과 수.
