## S1 (중간) — 병합 검사에 루트 브랜치 고정 (`src/core/worktree.ts` `validateTaskCommit`)

- `createWorktree` 는 `base` 커밋과 함께 **`baseBranch`**(만든 시점 루트의 `git rev-parse --abbrev-ref HEAD`; detached 면 거부 `루트가 브랜치 위에 있어야 합니다`) 를 `state.worktrees[]` 항목에 기록한다.
- `--merge-commit` 검사에 "루트의 현재 브랜치 == 등록 `baseBranch`" 를 추가한다. 다르면 거부 `루트 브랜치가 base 브랜치(<name>)가 아닙니다`. 기존 항목에 `baseBranch` 가 없으면(업그레이드 전) 검사는 건너뛰고 원장 `merge-commit:base-branch-unknown` 을 남긴다.
- 테스트(실제 git): 루트에서 task 브랜치를 checkout 한 뒤 review sha 로 merge-commit → 거부; base 브랜치로 돌아와 실제 병합 → 허용.

## S2 (중간) — `awaitingSlot` 삭제 예외

보정 5 M3(b) "모든 전이에서 삭제" 의 예외: 목적지가 `paused(slot)`, `WAIT_RESOURCE`, 또는 `lastPaused === 'slot'` 인 PICK 이면 표지를 유지한다(워처가 `WAIT_RESOURCE` 에서 `slot-free` 를 내려면 표지가 필요, `watcher.ts` 참조). 이미 그렇게 구현했으면 확인만. 테스트: `paused(slot)` → PICK → `WAIT_RESOURCE` 경로에서 표지 유지 + 소유자 사망 → `slot-free` → RESUME(기존 p7-slot 테스트가 이를 덮으면 근거만 적는다).

## S3 (중간) — CLEANUP processes 재시도 경로와 `cleanup.ok`

CLEANUP 템플릿의 재시도 경로는 `--scope processes` 성공 뒤 `--scope all` 로 전체 증거를 갱신하므로 M2 규칙과 양립한다. 확인할 것: `CLEANUP_FAILED → CLEANUP --task` 재진입 뒤 `--scope all` 성공이 `cleanup.ok` 를 기록하고 `CLEANUP→PICK` 이 통과하는지(CLEANUP 진입 시각 검사가 재진입 시각을 쓰는지). 테스트 1건: processes 실패 → CLEANUP_FAILED → CLEANUP 재진입 → processes 재시도 성공 → all 성공 → `cleanup.ok` 기록 + `--status done` 허용.

## S4 (낮음) — 검증한 코드 = 검수한 커밋

- 순서를 바꾼다: VERIFY 템플릿은 **먼저 `fodh worktree commit {{taskId}} -m …`**(변경이 없으면 "커밋할 변경이 없습니다" 는 무시하고 진행) 뒤에 `fodh verify run` 을 실행한다.
- `fodh verify run` 은 cwd 가 git 이면 `head`(`git rev-parse HEAD`)·`clean`(`git status --porcelain` 비어 있음) 을 `state.verify` 와 `result.json` 에 기록한다(비-git 은 null).
- VERIFY→REVIEW 게이트: git 워크트리 task 는 `verify.clean === true` 도 요구한다(아니면 거부 `검증 당시 미커밋 변경이 있었습니다: fodh worktree commit 뒤 다시 fodh verify run`).
- `--review-commit <sha>`: `state.verify` 가 같은 task 이고 `head` 가 있으면 `sha === verify.head` 를 요구한다(아니면 거부 `검수 커밋이 검증 시점 HEAD 와 다릅니다`).
- 테스트(실제 git): 미커밋 상태 verify ok → REVIEW 거부; 커밋 뒤 verify ok → REVIEW 허용 → review-commit = HEAD 허용, 다른 sha 거부.
