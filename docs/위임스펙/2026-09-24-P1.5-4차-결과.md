# P1.5 4차 수정 결과

작성: 2026-09-24 KST.
기준: `2026-09-24-P1.5-4차-수정.md`, 설계 v0.3.1의 실행 관리자·회수 계약.

**§1·§2 반영 완료. 최종 `npm test`는 245개 중 244 통과 / 1 실패, `npm run typecheck`는 exit 0 / 오류 0이다.** 회수 관련 테스트 실패는 0개다. 전체 0 실패 목표에는 도달하지 못했다. 남은 1개는 스펙 §3에서 예외 사유로 명시한 실제 ps 시작 시각 조회 경로이며, 아래에 실패 위치와 오류를 기록했다.

## 항목별 반영

| 항목 | 반영 내용 | 검증 |
|---|---|---|
| §1 ESRCH | `groupAlive()`에서 `kill(-pgid, 0)`의 ESRCH는 즉시 false. ps를 호출하지 않음. | ESRCH 단위 테스트: 회수 true, signal 0 한 번, ps 호출 없음. |
| §1 EPERM·기타 오류 | EPERM은 true. 그 외 오류만 C 로케일 ps 목록으로 재확인하고 ps 실패는 true 유지. | EPERM, EACCES, EIO, ps 실패 테스트 통과. |
| §1 회수 후 ps 보조 검사 | ps가 성공하고 해당 그룹이 보이면 false. ps 실패는 무시하고 커널 판정을 사용. | 기존 동작 유지. ps 사용 불가 환경에서도 정상·중단 회수 테스트 통과. |
| §2 휴리스틱 제거 | 50ms 대기 및 `readableEnded`/`inheritedPipe` 판정 삭제. | 즉시 code 1 종료와 ps 조회 지연 회귀 테스트 통과. |
| §2 출력 소비 | 레지스트리 등록을 기다리기 전에 readline iterator를 연결하고 for-await로 끝까지 소비. EOF만으로 회수하지 않고 exit/error/abort가 시작한 회수를 기다림. | 정상 code 0의 마지막 result 수신, EOF 뒤 150ms 후 정상 종료 및 stderr 수신 테스트 통과. |
| §2 close 유예 | 그룹 회수 후 close를 기본 3000ms 대기. close 수신 시 `cleaned = reclaimed`. 유예 초과 시 stdout/stderr를 destroy하고 readline을 닫으며 cleaned=false. | 정상·오류 종료 모두 cleaned=true와 빈 레지스트리. 그룹 밖 파이프 보유 자손은 cleaned=false 및 레지스트리 보존. |
| §2 전체 close 한도 | 회수 완료 시점부터 close 대기 전체 10초에 grace를 포함. destroy 후에는 남은 시간만 대기. | hang-orphan은 900ms deadline을 포함하여 약 3950ms에 반환, 기존 10초 미만 기준 통과. |
| §3 ps EPERM 회귀 | `first`/code 0, `no-verbose`/code 1 각각 일반 호출 경로와 ps EPERM mock 경로를 검사. ps 등록 조회에 100ms 지연을 적용. | 추가 4개 모두 통과. 일반 호출 경로도 이 샌드박스에서는 실제 ps가 거부되므로, ps 허용 환경을 검증했다고 주장하지 않음. |

## 추가로 확인한 종료 경합

첫 수정 뒤 전체 테스트에서 `bad-init` 및 `api-key` 중단 경로가 간헐적으로 cleaned=false를 반환했다. 임시 진단으로 **그룹 신호 전송의 EPERM과 직후 그룹 생존 판정 true**를 확인했다. 이 현상은 ps 호출 거부와 별개다. 진단 출력은 최종 코드에서 제거했다.

`reclaimOwnedGroup()`은 신호 EPERM 발생 시 추가 종료 신호나 ps 조회 없이, 최대 2초 동안 25ms 간격으로 `kill(-pgid, 0)`을 재확인한다. **ESRCH를 확인한 경우에만 true**를 반환한다. 생존 또는 EPERM이 계속되면 false, 다른 조회 오류도 false다. 종료와 신호의 경합 때문에 이미 소멸한 그룹을 회수 실패로 고정하는 오탐을 줄이되, 권한 오류를 회수 성공으로 취급하지 않는다.

EPERM 뒤 ESRCH 전환, 지속 EPERM, 후속 EIO에 대한 3개 회귀 테스트를 추가했다. 기존 신호 오류 반환 테스트도 유지했다. 최종 provider 25개 및 extension 6개가 모두 통과했고, revision의 회수·빈 레지스트리 검증도 모두 통과했다.

### 남은 실패 1개

- 테스트: `test/revision.test.ts:198`, `잠금 소유자의 실제 프로세스 시작 시각이 다르면 PID가 살아 있어도 stale이다`.
- 실제 호출: `/bin/ps -p <테스트 PID> -o lstart=`. C 로케일을 지정한 직접 조회다.
- 오류: `Error: spawn EPERM`. startedAt 비교에 필요한 실제 시작 시각을 읽는 단계에서 실패한다.
- 이 테스트는 그대로 유지했다. mock으로 실제 조회를 대체하거나 잠금 소유자 비교 정책을 변경하지 않았다. ps 허용 환경의 재검증이 남아 있다.

## 이전 결과의 원인 분류 정정

3차 결과 문서에서 회수 관련 34개 실패와 실제 ps 조회 실패 1개를 모두 ps 제한·회수 확인 불가 경로로 묶은 설명은 부정확했다. 4차 스펙의 Fable 재검증은 ps 허용 환경에서도 237개 중 10개가 실패한다고 보고했고, ESRCH 재확인 및 50ms 파이프 휴리스틱이라는 실제 구현 오류를 지적했다.

이번 수정은 그 두 오류를 제거했고, 추가로 관측한 신호 EPERM 종료 경합도 보완했다. **최종 실행에서 ps 제한을 실패 사유로 분류한 것은 위 잠금 실경로 1개뿐이다.** 이전 결과 문서는 실행 이력을 보존하기 위해 수정하지 않았으며, 원인 판단은 이 문서로 정정한다. Fable의 샌드박스 밖 수치는 전달받은 검수 근거이며 이번에 직접 재현한 결과가 아니다.

## 변경 파일·의도적 이탈과 세부 판단

- `src/provider/runner.ts`: ESRCH 판정, close 유예, 출력·종료 순서, 신호 EPERM 경합 보완.
- `test/runner.test.ts`: 기존 ESRCH 기대값 수정, 회귀 8개 추가, orphan 유예 하한 검증 추가.
- `test/fake-claude/claude`: stdout EOF 뒤에도 150ms 살아 있다가 정상 종료하는 전용 시나리오 추가.
- `docs/위임스펙/2026-09-24-P1.5-4차-결과.md`: 이 결과 문서.

1. 두 필수 수정 외에 실측 실패를 해소하기 위한 **신호 EPERM의 최대 2초 비파괴 재확인**을 추가했다. 이는 명시 스펙에 없는 세부 보완이다. 단순 오류만으로 성공 처리하지 않고 확정적 ESRCH를 요구한다.
2. `closeGraceMs`는 선택적 실행 옵션으로 추가했다. 기본 3000ms, 유한한 값은 0~10000ms로 제한하고 비유한 값은 기본값을 사용한다. 전체 close 한도 10초를 넘기지 않기 위한 세부 판단이다.
3. EOF는 exit와 다르므로 회수를 개시하지 않는다. exit/error/abort를 기다리며 기존 maxMs deadline을 유지한다. 그룹 밖 자손 자동 탐색·회수(P4)는 추가하지 않았다.
4. **0 실패 수용 목표 미달**은 의도적 기능 이탈이 아니라 실제 ps 실행 권한의 검증 한계다. 이 한계를 숨기기 위한 테스트 변경은 하지 않았다.

git 명령(status/diff 포함), 실제 claude/cswap/codex 실행, 비밀값 추가는 하지 않았다. 가짜 실행파일만 사용했고 서브에이전트는 동시에 1개 이하로 읽기 검토에만 사용했다.
