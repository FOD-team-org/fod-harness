## F12 (high) — VERIFY→REVIEW 는 검증 증거로만

1. `fodh verify run`(`src/core/verify.ts`) 은 결과를 `.pi/verify/<runId>/result.json`(report 전체 + `taskId`, `startedAt`, `finishedAt`, `heavy`) 으로 쓰고, 상태 파일에 `verify: { runId, taskId, ok, at: finishedAt, heavy }` 를 `updateState` 로 남긴다(마지막 실행이 이긴다).
2. `transitionState` VERIFY→REVIEW: `state.verify` 가 있고 `taskId === options.taskId`, `ok === true`, `at ≥ verifySince`(VERIFY 진입 시각, 복귀 경로에서는 유지 — N3 의 `reviewSince` 와 같은 방식) 일 때만 허용. 아니면 거부 `검증 증거가 없습니다: fodh verify run 이 통과해야 REVIEW 로 갈 수 있습니다(실패면 FIX)`. FIX→VERIFY·IMPLEMENT→VERIFY 진입 시 `verifySince` 갱신(이전 결과 무효).
3. `fodh backlog set --verify-ok` 플래그 **삭제**. `task.verify.ok` 는 VERIFY→REVIEW 전이가 통과할 때 하네스가 `{ ok: true, runId, at }` 로 기록한다. DoD `missingDoD` 는 그대로 `verify.ok` 를 본다.
4. `templates/prompts/VERIFY.md`: "통과 → `fodh state transition REVIEW`(하네스가 verify 증거를 검사한다)", "실패한 검사를 범위 밖으로 제외하려면 `fodh judgment add` 로 사용자 판단을 받는다(두뇌가 면제하지 않는다)".
5. 테스트: 증거 없음 거부 / fail 증거 거부 / 다른 task 증거 거부 / VERIFY 진입 전 증거 거부 / ok 증거 허용 + `task.verify.ok` 기록 / FIX→VERIFY 뒤 이전 ok 무효.

## F14 (medium) — 검수·병합 커밋은 실제 커밋이어야

1. `fodh backlog set --review-commit <sha>`(task): git 프로젝트면 sha 가 task 의 등록 워크트리(없으면 루트)에서 `git cat-file -e <sha>^{commit}` 로 존재하고 **워크트리의 `git status --porcelain` 이 비어 있어야**(작업이 전부 커밋돼 있어야) 받는다. 아니면 거부 `검수 대상 커밋이 없거나 미커밋 변경이 있습니다`. 비-git 프로젝트는 sha 대신 `--review-commit none` 만 허용.
2. `fodh backlog set --merge-commit <sha>`: 루트 저장소에서 존재하고 `git merge-base --is-ancestor <review.commit> <sha>` 가 참(검수한 커밋을 포함) 이어야 한다. 비-git 은 `none`.
3. **커밋 주체 공백 해소**: Codex 는 git 금지, 두뇌 `git commit` 은 MERGE·DOCS 만 허용이라 IMPLEMENT 결과를 커밋할 주체가 없다. 하네스 CLI `fodh worktree commit <task> -m "<메시지>"` 를 추가: task 의 등록 워크트리 안에서만 `git add -A && git commit`(비밀값 패턴이 diff 에 있으면 거부, 원장 `worktree:commit`), 두뇌 허용(사용자 승인 불필요). VERIFY 템플릿 통과 경로에 "먼저 `fodh worktree commit {{taskId}} -m …` 로 작업 커밋을 만든다" 를 넣는다. 훅 규칙 5 는 `fodh worktree commit` 을 막지 않는다(fodh 명령이므로 해당 없음 — 확인만).
4. 테스트: 존재하지 않는 sha 거부 / 미커밋 변경 거부 / 커밋 뒤 허용 / merge-commit 조상 검사 / `worktree commit` 정상·비밀값 거부.

## F15 (high) — DoD 플래그 자기 보고 제거

1. `--docs-ok`, `--cleanup-ok` 플래그 삭제.
2. `task.cleanup.ok` 는 `fodh cleanup run --task <T>` 가 성공(`.pi/cleanup-last.json` 의 `ok: true`, `taskId` 일치, CLEANUP 진입 이후) 했을 때 하네스가 기록한다(`src/core/cleanup.ts` 끝에서 `setTask`).
3. `task.docs.ok` 는 DOCS→CLEANUP 전이가 통과할 때 하네스가 기록하되, 전이 조건 = `docs/작업일지/` 에 오늘 날짜 파일이 있고 그 안에 taskId 문자열이 있으며 `docs/backlog.md` 가 JSON 과 동기화돼 있음(`backlog sync --check` 상당). 미충족이면 거부 `작업일지·백로그 갱신이 없습니다`.
4. CLEANUP→PICK 의 `status done` 검사는 유지(이제 세 플래그가 전부 하네스 기록이므로 자기 보고로 통과 불가). `fodh backlog set --status done` 은 CLEANUP 상태·현재 task·DoD 충족일 때만(기존 유지).
5. 템플릿 VERIFY/DOCS/CLEANUP 의 `--verify-ok/--docs-ok/--cleanup-ok` 문구 제거, `templates.test.ts` 갱신. README 흐름표 갱신.
6. 테스트: cleanup 성공 → `cleanup.ok` 자동 / 작업일지 없이 DOCS→CLEANUP 거부 / 세 플래그 옵션이 CLI 에서 "알 수 없는 옵션" 으로 거부.

## F16 (medium) — Codex 슬롯 사용 중 정식 대기 경로

1. `startCodex`(`src/core/codex.ts`) 가 슬롯 거부를 만나면 상태에 `awaitingSlot: { kind: 'codex', owner: { runId, root, pid }, since }` 를 기록하고 CLI 결과에 `wait: 'slot'` 을 넣는다. 슬롯 획득에 성공하면 `awaitingSlot` 을 지운다.
2. 프로바이더 턴 종료(`src/provider/turn.ts` 또는 `extensions/provider`): 상태에 `awaitingSlot` 이 있고 두뇌가 위임을 시작하지 못했으면 `paused(slot)` 로 전이(`resumeState` = 현재 상태, `taskId` 보존, 기존 `paused(*)` 규칙과 같음). 정체 안전망(자동 턴 3회 → 판단)은 그대로.
3. 워처(`src/core/watcher.ts`): `paused(slot)` 또는 `WAIT_RESOURCE(lastPaused=slot)` 이면 60초마다 `slotOwnerAlive` 를 검사, 소유자가 사라지면 인박스 `slot-free` → `decideInbox` → `autoResume` → PICK `RESUME` 으로 원 상태 복귀(기존 memory 회복 경로와 같은 모양).
4. 템플릿 IMPLEMENT·REVIEW·RESEARCH·FIX: "`codex 슬롯 사용 중` 오류면 다른 방법을 찾지 말고 `대기: 슬롯 codex` 로 턴을 끝낸다(가짜 runId 금지)". 오케스트레이터의 `대기:` 파서는 `대기: 슬롯 codex` 를 인식해 위임 대기와 같이 자동 재개를 멈춘다.
5. 테스트: 슬롯 거부 → `awaitingSlot` 기록 / 턴 종료 → `paused(slot)` / 워처 `slot-free` → RESUME / 템플릿 문구.
