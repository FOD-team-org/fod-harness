# W1 결과 — 완료 (2026-09-27)

W1 설정·멤버십·루트 판정·백로그·doctor 구현을 완료했다. 사용자 후속 설계 결정 1~3과 Opus 검수 M1~M3·L1~L7을 반영했고, 지정한 W1 테스트 **7파일·102개**, 영향받는 기존 테스트 **15파일·485개**가 모두 통과했다. 합계 **22파일·587개 통과**, `npm run typecheck`도 통과했다.

## 1. 후속 설계 결정 반영

1. **workspace 설정은 config set으로 변경 불가.** `approvalConfigKeys`는 원래 목록으로 복원했다. `setConfig`는 `workspace` 및 `workspace.*`를 호출 경로·`--approve`와 무관하게 거부한다. 문구는 `워크스페이스 설정은 fodh workspace add/remove 또는 사용자의 harness.json 직접 편집으로 바꿉니다`다. 파일 잠금·설정 쓰기 전에 거부하며, CLI와 코어 호출 모두 harness.json 바이트 불변을 테스트했다. 기존 승인 키의 동등·하위·부모 키 검사는 유지했다.
2. **제거된 멤버의 done task는 기록으로 보존.** 현재 멤버 존재 검사는 done이 아닌 task에만 적용한다. done task에도 비어 있지 않은 유효한 멤버 이름은 필요하다. 모두 done인 멤버 제거 후 sync·list·render·들여오기·doctor가 성공한다. done task의 repo 변경은 CLI·Markdown 모두 거부하며, 제거된 멤버를 참조한 채 미완료 상태로 바꾸는 것도 거부한다. doctor는 제거된 멤버의 done task에 대해 정보·경고를 추가하지 않는다.
3. **기본 검증 명령 경고.** 멤버의 `verify.commands`가 정확히 `['git diff --check']`일 때 `warning`을 낸다. 문구는 `멤버 <이름> 검증 명령이 기본값뿐입니다 — harness.json 의 workspace.repos.<이름>.verify.commands 를 채우세요`다. 추가 검증 명령을 넣거나 다른 명령으로 바꾸면 해제된다. 경고만으로 doctor가 실패하지 않는다.

## 스펙 차이와 구현 선택

- 원본 §1-3·§5·doctor 요구는 이번 후속 설계 결정으로 대체했다. workspace 승인 키를 별도 예외로 숨기는 방식 없이 기존 목록을 복원하고 전용 거부를 구현했다.
- 승인 키의 부모 검사 `k.startsWith(key + '.')`는 승인된 판단대로 유지했다. 하위 키 검사와 함께 부모 객체 교체 우회를 막는다.
- init/add 입력은 이름과 경로뿐이므로 초기값은 `baseBranch: main`, `worktrees.prefix: wt-<이름>-`, `verify.commands: ['git diff --check']`다. 제품별 명령을 추측·실행하지 않으며 doctor 경고와 README에서 사용자 직접 설정을 안내한다.
- 명의 부재·첫 커밋 실패 뒤 재시도를 구분하는 `.pi/harness-workspace-init.json`을 사용한다. 기존 하네스 일반 폴더는 거부하고, 재개 기록과 요청 멤버 설정이 일치하는 설치만 재개한다. 기존 `.pi/harness-*.json` ignore 패턴이 적용된다. 재개 기록은 initProject가 harness.json 설치를 마친 뒤 기록하므로 설치 전 실패에는 남지 않는다.
- 이번 후속 결정 외에 W2·W3로 구현 범위를 넓히지 않았다.

## 남은 한계

- W1은 설정·멤버십·루트·백로그까지다. PICK 이후 멤버별 워크트리·검증·병합·위임은 W2에서 연결해야 하며, W3의 멤버 읽기 경계·정책 합집합도 아직 없다.
- 실제 claude/codex/pi 실행 및 사용자 터미널 실기는 수행하지 않았다. doctor 두뇌 검사는 mock, 런처는 planner·가짜 pi로 검증했다.
- 설치 재시도는 요청 멤버 설정과 재개 기록의 JSON이 일치해야 한다. 설치 도중 사용자가 멤버 설정을 편집한 복구 경로는 검증하지 않았다.
- 멤버 사전 검사와 표지 기록 사이의 외부 프로세스 변경·강제 종료 복구는 검증하지 않았다.
- doctor는 잘못된 설정의 첫 오류를 보고한다. 유효한 설정의 멤버 운영 상태는 검사 목록으로 보고한다.
- 멤버 수 1~8 규칙 때문에 마지막 멤버 제거는 거부한다. done 기록의 repo는 그대로 보존하며 삭제된 멤버의 작업 실행 대상으로 사용하면 안 된다.

`loadConfig` 결과의 workspace 멤버 설정에는 기본값이 채워진다. 그러나 최상위 verify/worktrees 기본값까지 포함한 전체 결과를 harness.json에 저장하면 workspace 최상위 키 금지와 충돌한다. 설정 쓰기는 원본 JSON의 멤버 부분을 변경해야 한다. `setConfig`로 workspace를 변경할 수 없으며 멤버십은 add/remove, 세부 설정은 사용자의 직접 편집을 사용한다.

`repoOf`는 현재 멤버에만 해석된다. 제거된 멤버의 done task는 조회·렌더·동기화를 위한 기록이며 repoOf의 실행 대상이 아니다. 한 레포의 baseBranch는 undefined이므로 W2에서 현재 브랜치 의미를 유지해야 한다. `worktrees[].repo`의 실제 기록과 레포별 Git 실행 연결은 W2 몫이다.

`BacklogMode`는 불리언이 아니라 `{ workspace?: ... }` 모양이다. 순수 render/parse에는 config를 모드 인자로 전달하고, root를 받는 백로그 함수는 설정에서 모드를 읽는다. done task에도 repo 이름은 필요하지만 현재 멤버 존재 여부는 검사하지 않는다.


## 4. 검수 반영

Opus 독립 검수의 **고친 뒤 승인** 판정에 따라 아래 항목을 모두 처리했다. 최종 지정 검사 **W1 102개 + 기존 485개 = 587개 통과**, typecheck 통과다. 독립 검수의 재승인을 받았다는 뜻은 아니다.

### 남은 범위·API 주의

- W2/W3 실행·정책 구현 및 실제 터미널 실기·외부 프로세스 경합·강제 종료 복구는 여전히 이번 검증 범위 밖이다.
- `validateMarker`에 표지 파일 경로를 넘기던 호출자는 이제 common dir을 넘겨야 한다.
- 제거 복구를 위한 `readBacklog(root, mode?)`의 명시적 mode는 경로 검증을 건너뛴다. 일반 실행 경로에서는 생략한다.
- workspace 멤버의 검증·워크트리 설정은 ResolvedWorkspaceMember에서 읽어야 한다. 최상위 config.verify/worktrees 기본값은 멤버 설정을 대체하지 않는다.
