# W1 워크스페이스 설정·멤버십·백로그 (2026-09-27)

> 설계: [워크스페이스 모드 v0.2](../설계/2026-09-27-워크스페이스-모드-v0.2.md). 판단 A25 ①·A26 ①·A27 ①(2026-09-27)로 승인됐다.
> 이 단계는 설계 §13 의 W1 이다. W2(레포별 git·병합·검증·codex)·W3(훅·안내·화면)는 **하지 않는다**.
> 완료 조건: 한 레포 모드 동작·출력이 바뀌지 않는다(기존 테스트 무수정 통과가 기준). 워크스페이스 모드는 설정·멤버십·루트 판정·백로그까지만 동작한다.

## 1. 설정 (`src/core/config.ts`)

1-1. 타입: `HarnessConfig.workspace?: { repos: Record<string, WorkspaceMember> }`.

```ts
interface WorkspaceMember {
  path: string;                       // 워크스페이스 루트 기준 상대경로
  baseBranch?: string;                // 기본 'main'
  worktrees: { root?: string; prefix: string; links?: string[]; setup?: string[]; setupTimeoutMinutes?: number };
  verify: { commands: string[]; heavy?: string[]; timeoutMinutes?: number };
  secrets?: { readDeny?: string[]; readAllow?: string[] };
  approvalRules?: ApprovalRule[];     // 최상위 approvalRules 와 같은 모양·같은 검사
}
```

1-2. 검증: 설계 §3-2 표 전부. 설정을 읽을 때마다(`loadConfig`) 다시 검사하고, 어기면 설정 오류(throw)를 낸다.

- 멤버 수는 1~8개다. 이름은 `^[a-z][a-z0-9-]{0,15}$` 이고 `.` 은 예약이다.
- `path`:
  - realpath 가 디렉터리이고 `<path>/.git` 이 **디렉터리**여야 한다(lstat). 파일(연결 워크트리·서브모듈)은 거부한다.
  - HOME·`/`·워크스페이스 루트 자신·루트의 조상·루트 안쪽은 금지다.
  - 멤버끼리 realpath 가 같거나 서로 포함하면 안 된다.
- `worktrees.prefix` 는 필수다. `worktrees.root` 기본값은 `..`(멤버 기준)이다. (realpath(멤버/root), prefix) 쌍은 멤버끼리 겹치면 안 된다.
- `worktrees.links` 는 **멤버 기준**으로 검사한다. 지금 루트 기준 검사(213-222행 근처)와 같은 규칙을 멤버 경로에 적용한다.
- `verify.commands` 는 비어 있으면 안 된다.
- approvalRules id 는 최상위와 모든 멤버를 통틀어 중복 금지다.
- 워크스페이스 모드에서 사용자가 `harness.json` 에 최상위 `verify` 나 `worktrees.prefix`·`worktrees.links`·`worktrees.setup` 을 **직접 적었으면** 오류다: "워크스페이스 모드에서는 workspace.repos.<이름> 아래에 둡니다". 기본값 병합으로 생긴 값은 오류가 아니다. 원본 JSON 에 키가 있었는지로 판정한다.

1-3. 승인 전용 키:

- `workspace` 를 통째로 승인 전용 키에 넣는다.
- `approvalConfigKeys`(321행 근처)의 판정을 `key === k || key.startsWith(k + '.')` 로 바꾼다. 그래야 `workspace.repos.web.path` 같은 하위 키도 잡힌다. 기존 키에도 똑같이 적용되므로 기존 테스트로 회귀를 확인한다.

1-4. 한 레포 모드: `workspace` 가 없으면 아무것도 바뀌지 않는다.

## 2. `src/core/workspace.ts` (새 파일)

- `isWorkspace(config)`
- `workspaceMembers(root, config)`: `{ name, path(realpath), baseBranch, worktrees, verify, secrets, approvalRules }[]`.
  - 한 레포 모드면 암묵 멤버 하나를 돌려준다: 이름 `.`, 경로 = 루트, 나머지는 최상위 설정. 이때 `baseBranch` 는 `undefined` 다(= 현재 브랜치, 설계 §6-2).
- `repoOf(root, config, task)`: 워크스페이스 모드면 `task.repo` 멤버(없거나 모르는 이름이면 오류), 한 레포 모드면 암묵 멤버. W2 가 쓴다. W1 은 만들고 테스트만 한다.
- 표지:
  - 경로는 `<멤버 git common dir>/fodh-workspace`, 내용은 워크스페이스 루트 realpath 한 줄이다.
  - `readMarker(memberGitCommonDir)`, `writeMarker`, `removeMarker`
  - `validateMarker(path)` → `{ workspace, member?, ok, reason? }`. 표지가 가리키는 워크스페이스의 `workspace.repos` 에 이 레포 realpath 가 있어야 `ok` 다.

## 3. 루트 판정·창 열기 (`src/cli/project-root.ts`, `src/cli/root.ts`, `src/cli/start.ts`, `src/cli/init.ts`)

설계 §4-2 표 그대로.

- git 최상위에서 멈출 때 `<git common dir>/fodh-workspace` 를 먼저 본다.
  - 표지가 있고 cwd 가 그 레포의 **연결 워크트리**면(git dir ≠ common dir) 거부한다: `멤버 <이름>의 워크트리 안입니다 — 워크스페이스 <경로>에서 여세요`. 표지가 맞지 않아도 거부하되, 문구는 표지 오류 쪽을 쓴다.
  - 주 체크아웃이고 표지가 유효하면 루트 = 워크스페이스다. 그 레포 자신의 `.pi/harness.json`·`.pi/harness-state.json` 보다 앞선다.
  - 표지가 무효면 오류: `표지가 맞지 않습니다: <워크스페이스>에서 fodh workspace list`. 조용히 무시하지 않는다.
- `projectRoots`·`resolveCliRoot`(`FODH_PROJECT_ROOT` 명시 경로는 지금 규칙 유지)·`startRoot`/`startPlan`·`implicitStart` 가 모두 같은 판정을 쓴다.
- 멤버에서 열린 경우 시작 계획에 한 줄을 더한다: `워크스페이스 <루트 폴더 이름> (멤버 <이름> 에서 열림)`. 사용자 터미널에 보이는 첫 안내 자리다(`startShell` 이나 설치 질문을 출력하는 곳).
- 표지가 있는 레포 **안에서 그 레포 자체를 하네스 루트로** 쓰려는 `fodh init` 은 거부한다: `이 레포는 워크스페이스 <경로>에 속합니다`. 표지 판정이 앞서므로 `startPlan` 은 자연히 워크스페이스로 간다.

## 4. `fodh workspace` 명령 (`src/cli/index.ts`·`commands.ts`, 로직은 `workspace.ts`)

| 명령 | 동작 |
|---|---|
| `fodh workspace init --repo <이름>=<경로> [--repo …] [--identity '이름 <메일>'] [--dry-run]` | cwd 를 워크스페이스 루트로 만든다 |
| `fodh workspace add <이름> <경로> --approve` | 멤버 추가 |
| `fodh workspace remove <이름> --approve` | 멤버 제거 |
| `fodh workspace list` | 멤버 상태 JSON |

4-1. 공통 멤버 추가 검사(설계 §4-3). 하나라도 어기면 **아무것도 쓰지 않는다**.

1. 설정 검증(§1-2)을 통과한다.
2. 멤버에 살아 있는 `.pi/harness.lock` 이 없다. 기존 lock 판정 함수를 쓴다.
3. 멤버의 옛 하네스 상태가 `IDLE`·`DONE_ALL`·`PROJECT_READY` 이거나 `.pi/harness-state.json` 이 없다.
4. 다른 워크스페이스를 가리키는 표지가 없다. 같은 워크스페이스를 가리키는 표지는 허용한다(재실행 안전).
5. `git -C <멤버> branch --no-merged <baseBranch> --list '<prefix>*'` 가 비어 있다. 비어 있지 않으면 그 목록을 보여 주며 거부한다.
6. `baseBranch` 가 존재한다(`rev-parse --verify refs/heads/<b>`).

4-2. `init`

- cwd 조건: 하네스 없는 폴더여야 한다(`.pi/harness.json` 없음). git 이 아니거나, 자체 git 최상위이면서 연결 워크트리가 아니어야 한다. cwd 가 어느 멤버 안이면 거부한다.
- 순서:
  1. 모든 멤버를 검사한다(§4-1).
  2. 기존 `initProject` 흐름으로 설치하되 `workspace.repos` 를 넣은 `harness.json` 을 쓴다. 최상위 `verify`·`worktrees.prefix/links/setup` 은 쓰지 않는다.
  3. 표지를 쓴다.
  4. 첫 커밋을 한다.
- 도중 실패하면 이미 쓴 표지를 지운다. 설치 파일은 기존 init 의 실패 처리를 따른다.
- 첫 커밋 명의(설계 §4-3):
  - 워크스페이스 저장소에 **저장소 로컬** `user.name`·`user.email` 이 있으면 그대로 쓴다.
  - 없으면 `--identity` 값을 저장소 로컬로 설정한다.
  - 그것도 없으면 멤버들의 저장소 로컬 명의(`git -C <멤버> config --local --get user.name/email`)를 본다. 모두 있고 같으면 그 값을 복사한다.
  - 어느 경우도 아니면 첫 커밋을 건너뛰고 안내한다: `저장소 명의를 정할 수 없어 첫 커밋을 건너뛰었습니다 — fodh workspace init … --identity '이름 <메일>' 로 다시`. 이미 쓴 파일은 보존하고, 다시 실행하면 이어서 커밋한다.
  - 전역 명의로 커밋하지 않는다. `-c user.*` 를 쓰지 않는다.
- 다음 안내(`nextSteps`)는 `/project-start` 가 아니라 `fodh 로 창을 열고 첫 백로그를 요청합니다(fodh backlog add --repo <이름> …)` 로 한다.
- 초기 상태는 지금 init 과 같다(IDLE). IDLE→PLANNING 전이는 이미 있다.

4-3. `add` / `remove`

- `add`: §4-1 검사 → `harness.json` 에 멤버 추가 → 표지 기록.
- `remove`: 그 멤버의 `repo` 를 가진 task 가 모두 `done` 이고, 상태 `worktrees[]` 에 그 멤버 워크트리가 없을 때만 한다. 설정에서 빼고 표지를 지운다.
- 둘 다 `--approve` 가 필요하다. 기존 `config set … --approve` 와 같은 방식이고, 두뇌가 `--approve` 를 못 쓰게 하는 기존 가드를 그대로 탄다. 기존 가드가 명령 이름 기준이면 `workspace add/remove` 도 포함되는지 확인하고 필요하면 넣는다. 훅 파일 수정이 필요하면 그 부분만 최소로 하고 결과 문서에 적는다.

4-4. `list` — 멤버마다 아래를 JSON 으로 낸다. 두뇌도 쓸 수 있다(읽기 전용).

- `name`, `path`
- `marker`: `ok`·`missing`·`mismatch`
- `branch`, `baseBranch`, `onBase`
- `trackedDirty`(개수)
- `oldHarness`: `none` 또는 `{ state, lockAlive }`

## 5. 백로그 (`src/core/backlog.ts`, `src/cli/index.ts`)

- `Task.repo?: string` 를 더한다.
- `renderBacklog`·`parseBacklog`·`backlogInSync`(와 이들을 부르는 곳)는 모드를 받는다.
  - 워크스페이스 모드 열은 `['ID','제목','분류','레포','의존','상태','repair','판단','워크트리','검수(커밋)','비고']` 이다.
  - 한 레포 모드 표는 지금과 **바이트까지 같다**.
- 워크스페이스 모드 규칙:
  - `fodh backlog add` 는 `--repo <이름>` 이 필수다. 없는 멤버면 거부한다. `--repo .` 도 거부한다(루트 task 없음).
  - 한 레포 모드에서 `--repo` 를 주면 거부한다: `한 레포 모드에서는 --repo 를 쓰지 않습니다`.
  - 모든 task 에 알려진 `repo` 가 있어야 한다. `repo` 가 없는 task 는 sync·들여오기 오류다.
- `repo` 변경:
  - `fodh backlog set T --repo X` 는 status `ready` 이고 `worktree` 가 비어 있을 때만 허용한다.
  - `backlog.md` 들여오기에서도 같은 조건을 어기면 들여오기를 거부한다. 기존 보호 칸 처리와 같은 방식이고, 문구는 `진행 중 task <T>의 레포는 바꿀 수 없습니다`.

## 7. 테스트 (새 파일 `test/w1-*.test.ts`)

임시 폴더에 멤버 git 저장소 2~3개와 워크스페이스 폴더를 만든다. 테스트 안의 git 은 허용한다. 저장소 로컬 명의를 테스트 안에서 설정한다.

1. 설정
   - 유효한 WisePharm 모양 설정이 통과한다.
   - §1-2 의 각 규칙 위반이 오류다: 이름, `.`, `.git` 파일, HOME, 루트 안쪽, 멤버 포함 관계, prefix 겹침, 빈 verify, id 중복, 최상위 verify 직접 기재.
   - `approvalConfigKeys` 가 하위 키를 잡는다.
2. 표지·루트 판정
   - 멤버 하위 폴더 → 워크스페이스 루트가 된다(`projectRoots`·`resolveCliRoot`·`startPlan` 모두).
   - 멤버에 옛 `.pi/harness.json`·상태가 있어도 표지가 앞선다.
   - 멤버 연결 워크트리 → 거부한다.
   - 표지 불일치 → 오류다.
   - 표지 있는 멤버에서 `fodh init` → 거부한다.
3. `workspace init`
   - 성공 흐름: 설정, 표지 3개, 첫 커밋 명의 복사.
   - 멤버 하나가 실패 조건이면 아무것도 쓰지 않는다: 살아 있는 잠금, 옛 상태 IMPLEMENT, 다른 워크스페이스 표지, 병합 안 된 prefix 브랜치, baseBranch 없음.
   - 병합된 prefix 브랜치는 허용한다.
   - 명의가 없거나 멤버마다 다르면 커밋을 건너뛰고 안내한다.
   - `--identity` 가 동작한다.
   - `nextSteps` 문구를 확인한다.
4. `add`/`remove`
   - `--approve` 없이는 거부한다.
   - remove 는 미완 task 가 있으면 거부한다.
   - remove 뒤 표지가 사라진다.
5. 백로그
   - 워크스페이스 표 왕복(render → parse)이 된다.
   - 한 레포 표가 기존 fixture 와 바이트 동일하다.
   - `--repo` 필수·거부 규칙을 확인한다.
   - `set --repo` 조건과 md 들여오기 보호를 확인한다.
6. doctor: 워크스페이스 검사 실패·경고 사례를 확인한다.
7. `repoOf`·`workspaceMembers`: 두 모드를 모두 확인한다.

## 8. 하지 않는 것(W2·W3)

- 워크트리 생성·제거·검증·병합·`merge.base`
- codex·cleanup·audit·turn
- 훅 경계(멤버 main 읽기 전용, git 허용 목록, 승인 정규화, 비밀 정책 합집합)
- CLAUDE.md 관리 블록·brain-rules·스킬·상태줄

W1 이 끝난 뒤 워크스페이스 설정이 있는 루트에서 PICK 이후 흐름을 돌리면 W2 전이라 틀릴 수 있다. 이것은 W2 에서 고친다. W1 은 이 흐름을 막지 않아도 된다.
