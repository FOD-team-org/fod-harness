# W2 레포별 git·병합·검증·위임 결과 (2026-09-27)

W2 v0.2를 구현했다. 새 W2 테스트 **7파일 55개 통과**, `npm run typecheck` 통과. Git 저장소가 아닌 워크스페이스 루트에서 멤버 3개를 순서대로 PICK → 구현(fake Codex) → 검수 → MERGE → DOCS → CLEANUP까지 실행하는 통합 테스트도 통과했다.

영향받는 기존 회귀 검사는 **43파일, 1,205개 통과·10개 실패·1개 건너뜀**이다. 실패는 샌드박스의 `/bin/ps` 차단 및 그에 따른 시작 시각·프로세스 잔존 확인 실패다. 따라서 기존 회귀 전체 통과라는 완료 조건은 이 환경에서 충족했다고 보고하지 않는다. 기존 테스트는 수정하지 않았다.

## 스펙 차이와 구현 선택

1. **W1 해석 API 유지.** `repoOf`의 문구·동작은 바꾸지 않았다. W1 백로그 파서가 먼저 거부하는 옛 repo 없는 JSON에도 W2 지정 문구를 내기 위해 `executionTask`에서 해당 조건만 먼저 확인한다.
2. **옛 브랜치 거부가 소유 증거를 만들지 않게 했다.** 스펙의 create pre+repo+branch 증거를 사용하되 `foreign-branch`로 끝난 시도의 pre는 제외한다. 그렇지 않으면 첫 호출에서 거부한 사용자 브랜치가 두 번째 호출에서 하네스 브랜치로 오인된다. fail에 고정 `reason: 'foreign-branch'`와 branch를 남긴다. 이미 `worktree add`가 성공하고 상태 기록 전 끊긴 경우에는 Git 목록의 실제 경로·브랜치를 대조한 뒤 기존 작업 트리를 인계한다.
3. **단일 레포의 옛 기록 fallback 보존.** `record.base`가 없는 기존 작업 트리를 복구할 때 기존 `registeredBase` 흐름을 유지했다. §1-1의 “지금처럼 HEAD”는 현재 구현의 `merge-base <branch> HEAD` 경로와 다르므로 §0-5의 호환성 제한을 우선했다. workspace에는 명시된 멤버 기준 브랜치를 적용했다.
4. **경로 검사 범위.** 설정의 worktrees.root가 workspace 또는 멤버 안에 들어가는 것은 config 단계에서 거부한다. 기본 형제 작업 트리의 부모인 `..` 자체를 금지하지 않는다. 실제 `<prefix><T>` 경로는 create 단계에서 안쪽·조상 양방향을 검사한다.
5. **목록 출력.** workspace `porcelain`은 `Record<repoName, string>`, 실패가 있을 때만 `error: Record<repoName, string>`이다. `registeredInGit`은 각 기록의 repo 목록에 대해서만 계산한다. 단일 레포 출력 구조는 유지했다.
6. **단일 레포 헤더.** 선택적 `targetRepo` 치환값을 기존 sandbox 줄 앞에 배치했다. 단일 레포에서는 빈 문자열이므로 기존 텍스트·개행과 동일하다. home 경로는 기존 처리대로 `~`로 표시한다.
7. **병합 실행과 stderr.** `/bin/ps` 조회가 필요 없는 새 detached 그룹을 직접 종료한다. 기본 제한은 단계별 600,000ms이며 테스트에서만 코어 API의 `timeoutMs`를 주입한다(CLI 옵션 없음). stderr는 마지막 4KB를 모은 뒤 redact하며, 잘려서 비밀값의 접두어를 잃었을 수 있는 첫 부분 줄은 버린다. 오류/CLI에는 고정 문구만 보낸다.
8. **재시도·기록.** 기준점이 없을 때는 첫째 부모 사슬 전체 200개까지만 검사한다. 정상 병합 완료 직후 죽어 남은 표시 파일은 소유 증거가 맞는 재시도에서 지운다. 이미 Git 커밋이 끝난 뒤 기록이 실패하면 커밋을 되돌리지 않으며 재시도가 기존 병합을 확인해 기록한다. 이전 프로세스가 남긴 unknown pre는 기존 복구 경로에도 계속 노출될 수 있다.
9. **경고와 W1 설정 검증 구분.** 경고 함수는 전달받은 설정의 각 경로를 직접 조회하므로 Git 조회 실패·체크아웃 소실을 경고로 돌려준다. W1 `loadConfig`가 처음부터 유효하지 않은 멤버 경로를 거부하는 정책은 유지했다. 따라서 명령이 설정 로드 단계부터 실패하는 경우까지 경고만으로 계속 실행한다고 보장하지 않는다.

## 기존 테스트 변경·범위 보존

기존 테스트를 고친 줄은 **0줄**이다. §11-3의 열거 기대값 추가 예외도 사용하지 않았다. 새 테스트만 추가했다.

작업 시작 때 저장한 SHA-256과 비교해 기존 테스트 117파일을 포함한 보호 대상 **162파일 모두 동일**함을 확인했다. 훅, CLAUDE.md 관리 블록 템플릿, brain-rules, 스킬, `templates/prompts/MERGE.md`, 상태줄, `docs/설계/`는 변경하지 않았다. `claude-md.ts`의 변경은 스펙이 요구한 새 명령의 목록 제외 필터뿐이다.

실제 저장소에서 git 명령을 실행하지 않았고 add/commit/branch/stash/reset/checkout도 하지 않았다. Git 변경은 테스트가 생성한 임시 저장소에서만 발생했다. 실제 claude/codex/cswap/pi/osascript와 네트워크는 사용하지 않았다. 기존 fake 실행기와 주입을 재사용했고 비밀 파일을 읽거나 비밀값을 결과 문서에 기록하지 않았다.

## 남은 한계

- `/bin/ps`가 필요한 기존 회귀 10개 실패·1개 건너뜀은 남아 있다. 기존 테스트 수정이나 환경 제약 우회는 하지 않았다. 단일 레포 회귀 전체 통과는 미확인이다.
- 새 병합의 시간 제한은 짧은 주입값으로 그룹 종료·되돌림을 검증했다. 실제 10분 대기, 실서비스 provider, 실제 사용자 저장소의 훅·명의, 네트워크 서비스와의 연동은 실행하지 않았다.
- W3의 훅 경계·관리 블록·두뇌 MERGE 프롬프트 연결은 이번 변경에 포함하지 않았다. `worktree merge`는 상태를 자동 전이하지 않는다.

## W3가 알아야 할 API

### 멤버 해석·기준점

- W1 `repoOf(root, config, taskOrRecord)` / `ResolvedWorkspaceMember`가 설정 해석의 원본이다.
- `src/core/workspace-task.ts`: `executionTask(root, id, config)`, `taskMember(root, config, task)`, `recordMember(root, config, record)`, `assertRecordRepo(config, task, record?)`, `repoEvidence(config, member)`를 사용한다. 작업 트리·검증 설정은 반환 멤버에서 읽는다.
- `baseTip(member)`은 멤버 기준 브랜치 커밋, `isAncestor(path, base, tip)`은 Git 오류 시 false다.
- `src/core/merge-base.ts`의 `checkMergeResume(root, task)`는 MERGE 재개 직전에만 호출한다. false면 task가 판단으로 막혔으므로 PICK 결정을 다시 구한다. 새 resume 호출 경로를 만들면 이 검사를 거쳐야 한다.
- `Task.merge`는 `{ commit?: string; base?: string; baseJudgment?: string }`. JSON 숨은 필드이며 md 표에는 추가하지 않는다.

### 병합 CLI·출력·실패·표시 파일

```sh
fodh worktree merge T01
fodh codex research 조사.md --repo web
```

코어 `mergeWorktree(root, taskId)`는 `src/core/worktree.ts`에서도 import할 수 있다. `harness-worktree` 잠금 안에서 실행한다.

반환값은 `{ taskId, repo?, branch, mergeCommit, alreadyMerged?, warnings? }`. workspace만 repo를 포함하며 untracked 경고는 `warnings.untracked = { count, paths }`(앞 5개 경로)다. FF 여부는 출력이 아니라 원장 ok의 `fastForward: true`에 남는다.

`worktree:merge` fail reason은 `dirty`, `branch`, `tip`, `base`, `merge-head`, `already-in-base`, `conflict`, `hook`, `not-started`, `timeout`, `record`다. 실행 단계 실패에는 `stage`, `exitCode`, `aborted`, 선택적 `stderrTail`이 함께 기록된다. stderrTail을 사용자 오류 메시지로 재출력하지 않는다.

표시 파일은 멤버 Git common dir의 `fodh-merge.json`, 모양은 `{ runId, taskId, review, at }`다. 남은 MERGE_HEAD를 정리할 때 표시 파일·review·가장 최근 unknown pre의 runId까지 모두 일치해야 한다. 원장만으로 사용자 병합을 중단하면 안 된다.

성공해도 상태는 MERGE다. 다음 DOCS 전이는 기존 `fodh state transition DOCS --task T01 --commit <review>` 경로에서 수행한다. 기존 `backlog set --merge-commit`도 유지된다.

### 감사·경고·복구

- `AuditBoundary.members?: string[]`는 멤버 실제 경로 배열이다. `runTurn`이 현재 설정을 해석해 전달한다. 멤버 안쪽이면서 등록된 작업 트리 밖인 편집은 기존 `audit:path-boundary` warn `{ path }`가 된다. Bash 경로 후보도 검사한다.
- `workspaceBranchWarnings(root, config): Promise<string[]>`는 단일 레포에서 `[]`; workspace에서 기준 브랜치 이탈·detached·Git 실패 경고와 `workspace:base-branch` warn `{ repo, branch }`를 남긴다(Git 실패 branch=null). 호출자는 빈 배열이면 기존 응답에 warnings 키를 넣지 않는다.
- 복구 프롬프트의 unknown JSON 줄은 원장 evidence에 repo가 있을 때만 repo를 덧붙인다. 없는 경우 기존 줄을 유지한다.
