## 1. 설정 (`src/core/config.ts`)

```json
"watch": { "stallMinutes": 10, "childTimeoutMinutes": 30, "pollSeconds": 5, "stableSeconds": 10, "tickSeconds": 30 }
```

- 모두 양수. `stallMinutes`·`childTimeoutMinutes` 는 정수. 검증 실패 메시지는 기존 형식(`watch.stallMinutes는 양의 정수여야 합니다`).
- `fodh config get watch` 로 기본값이 보여야 한다(`mergeDefaults` 경로).

## 2. 감지 규칙 (`src/core/watcher.ts`)

`tick(root, { now?, isProcessAlive?, ctx? })` 는 아래 4종을 순서대로 검사하고 `{ emitted: InboxRecord[], status: WatcherStatus }` 를 돌려준다. 상태는 `.pi/harness-watcher.json` 에 저장한다(기존 `judgment` 키는 그대로 두고 `watch` 키를 추가).

### 2-1. 판단대기 변경 (`judgment-changed`)

- 대상 경로 = `loadConfig(root).judgment.file` (매 tick 재해석). 파일이 없으면(ENOENT) 관측 해시 `null` 로 두고 이벤트 없음.
- 내용 SHA-256 을 계산해 `watch.judgment.observed = { hash, since }` 로 기록한다. 해시가 바뀌면 `since = now`.
- **자기 수정 억제**: 관측 해시가 `judgment.expectedHash`(기존 `save()` 가 기록) 와 같으면 `lastEmitted` 를 그 해시로 맞추고 이벤트 없음.
- **안정화**: 관측 해시가 `expectedHash` 와 다르고 `lastEmitted` 와 다르며 `now - since ≥ stableSeconds` 이면 인박스 `{ kind:'judgment-changed', path, hashBefore:lastEmitted ?? expectedHash, hashAfter, size }` 를 `detected → queued` 로 기록하고 `lastEmitted = hashAfter`.
- 같은 해시로 되돌아오면(동일 해시 재저장) 새 이벤트 없음. **이미 기록된 미적용 인박스 항목은 취소하지 않는다.**
- 설계 표의 `changedLines` 는 이전 본문 사본이 필요하므로 P2 에서는 생략한다(결과 문서에 명시).

### 2-2. 두뇌 정지 (`stalled`)

- 조건: 상태가 활동 상태(오케스트레이터의 `active` 집합과 동일 — 공용 상수로 빼서 `src/core/state.ts` 에서 export) 이고 `awaitingUser !== true` 이고 `now - max(lastEventAt, enteredAt, savedAt) > stallMinutes`.
- 인박스 `{ kind:'stalled', state, task, lastEventAt, runId, minutes }`. 중복 방지: 같은 `runId`(없으면 `state+enteredAt`) 로는 한 번만.
- 상태·runId 가 바뀌면 다시 감지할 수 있다.

### 2-3. 자식 초과 (`child-timeout`)

- 레지스트리 `.pi/harness-procs.json` 의 각 항목에 대해: 살아 있고(`isProcessAlive(pid)` — 기존 `src/core/lock.ts` 의 함수 재사용) `now - startedAt > 한계` 이면 `{ kind:'child-timeout', pid, pgid, runId, kind:proc.kind, minutes }`. 한계 = `kind === 'brain'` 이면 `brain.maxTurnMinutes`, 그 외 `childTimeoutMinutes`.
- 죽어 있으면 `{ kind:'child-gone', pid, pgid, runId }`. 레지스트리 정리는 하지 않는다(P4/기존 reclaim 경로).
- 중복 방지 키 `pid+startedAt+kind`.

### 2-4. 세션 복구 (`recover`)

- `tick()` 이 아니라 확장의 `session_start` 에서 한 번: 상태가 활동 상태·`recovering`·`paused(*)`·`WAIT_*` 중 하나이면 `{ kind:'recover', state, task, savedAt, resumeState }` 를 기록한다. IDLE·PROJECT_READY·DONE_ALL 은 기록하지 않는다.
- 중복 방지 키 `sessionStartedAt`(확장이 생성한 시각) — 같은 세션에서 두 번 기록하지 않는다.

### 2-5. 인박스 중복 방지 (`src/core/inbox.ts`)

- `addInbox(root, { kind, dedupeKey?, ... })`: 같은 `dedupeKey` 를 가진 항목이 `applied` 가 아닌 상태로 있으면 새로 만들지 않고 기존 항목을 돌려준다(`{ record, created:false }` 형태로 바꾸거나 별도 `addInboxOnce` 를 추가 — 기존 호출부·테스트 호환 유지).
- 워처가 만든 항목은 기록 직후 `queued` 로 올린다(프로바이더는 `applied` 아닌 항목 전부를 다음 턴에 붙인다 — 기존 동작).

## 3. Pi 확장 (`extensions/watcher/index.ts`)

- `session_start`: `root = ctx.cwd`, 최신 `ctx` 보관(`hasUI`·`isIdle()`·`ui.notify` 용). 복구 감지(2-4) 실행 후 즉시 `decideInbox`(§4) 호출. 그다음 타이머 시작: `pollSeconds` 마다 `tick()`(판단대기 해시), `tickSeconds` 마다 전체 `tick()`. 두 타이머 모두 `unref()`. 판단대기 파일의 **부모 디렉터리**에 `fs.watch({ persistent:false })` 를 걸어 이벤트가 오면 즉시 한 번 `tick()`(디바운스 500ms). `fs.watch` 실패(EMFILE 등)는 원장 `watcher:fs-watch fail` 로 기록하고 폴링만 계속한다.
- 워처가 인박스에 새 항목을 만들 때마다 오케스트레이터의 `decideInbox(pi, ctx, root, records)` 를 호출한다(같은 프로세스이므로 모듈 import; `pi` 는 워처 자신의 `ExtensionAPI` 를 넘긴다 — `pi.sendMessage` 는 어느 확장에서 불러도 같은 세션으로 간다).
- 모든 타이머 콜백은 try/catch. 실패는 원장 `watcher:tick fail` + 1분에 최대 1회 `ctx.ui.notify(warning)`. 예외를 Pi 로 전파하지 않는다.
- `session_shutdown`: 타이머 정리, `fs.watch` close, 진행 중 tick 완료 대기.
- `hasUI === false`(print 모드) 면 타이머·fs.watch 를 시작하지 않는다(단일 턴). `session_start` 복구 기록만 남긴다.
- 동시 실행 방지: `tick()` 이 이미 실행 중이면 새 호출은 건너뛴다(플래그).

## 4. 오케스트레이터 결정 (`extensions/orchestrator/index.ts`, `resume.ts`)

### 4-1. 공용 자동 재개 `autoResume(pi, root, ctxLike, reason)` (`resume.ts`)

- 기존 `agent_end` 의 본문(대기 표지 검사 제외)을 그대로 옮긴다: 활동 상태 확인 → `recovering` 1회 제한 → `maxAutoTurns` 초과면 `stopForJudgment` + 알림 → `autoTurns+1` → `send(..., automatic=true)` try/catch 원복. `ctxLike = { cwd, hasUI, isIdle, notify }`.
- 추가 가드: `ctxLike.isIdle() === false` 이면 아무것도 하지 않고 `{ skipped:'busy' }` 를 돌려준다(턴 진행 중 — 프로바이더가 다음 턴 프롬프트에 인박스를 붙이므로 충분).
- `agent_end` 는 대기 표지·awaitingUser 검사 뒤 `autoResume(..., 'agent_end')` 를 호출한다. 기존 orchestrator 테스트는 그대로 통과해야 한다.

### 4-2. `decideInbox(pi, ctx, root, records)`

| kind | 결정 |
|---|---|
| `judgment-changed` | `readJudgment(root, { answered:true })` 로 적용 가능한 답이 있으면 `applyJudgments(root)` 실행(`/judged` 와 같은 경로: 결정 완료 표·task 해제·상태 복귀). 적용된 게 있고 상태가 활동 상태이면 `updateState({ awaitingUser:false, autoTurns:0 })` 후 `autoResume`. 적용 가능한 답이 없으면 `notify('판단대기 변경 감지 — 적용할 답 없음(다음 턴에 전달)', 'info')` 만. `applyJudgments` 가 재질문을 만든 경우(부정·모호) 그 결과를 알림에 포함 |
| `stalled` | `autoResume(..., 'stalled')` (idle 이 아니면 건너뜀). 건너뛴 경우와 `stopForJudgment` 가 실행된 경우 모두 warning 알림 |
| `child-timeout` / `child-gone` | warning 알림만. 인박스는 다음 턴에 두뇌에게 전달됨(P4 전까지 회수 없음) |
| `recover` | `doctorFresh(state)` 이고 상태가 활동 상태이고 `awaitingUser !== true` 이면 `autoResume(..., 'recover')`; 그 외(`paused(*)`, `WAIT_*`, `recovering` 포함)는 info 알림 `이전 세션 상태: <state>[ /<task>] — /develop-start 또는 /judged 로 이어갑니다` 만 |

- `awaitingUser === true` 인데 `judgment-changed` 로 답이 적용된 경우 → 사용자가 채팅 대신 문서로 답한 것이므로 대기를 풀고 재개한다(위 규칙에 포함).
- 결정 결과는 원장에 `watcher:decide:<kind>` `ok|skip` + evidence `{ ids, applied, resumed }` 로 남긴다.

### 4-3. `/status`

- 출력 JSON 에 `watcher: { lastTickAt, judgment: { observedHash(앞 12자), stableFor(초), expectedHash(앞 12자) }, stalledSince?, childTimeouts: n }` 추가.
