## 중간 (필수)

**M1 죽은 `spawn:`·foreign 기록 영구 실패** — `src/core/cleanup.ts processes()`
- `spawn:` 기록: 그룹(pgid)과 pid 가 모두 죽어 있으면 신호 없이 `removeProc` 하고 `stale` 목록에 보고한다(codex 면 meta 미마감 시 `lost` 로 마감). 살아 있으면 지금처럼 `unverified`.
- `reclaimCodexOwner` 결과 `foreign`(pid 재사용)·`gone`: 신호 없이 `removeProc` + `stale` 보고. `unverified`(살아 있으나 신원 불일치)만 `unverified` 로 남긴다.
- `ok = !residual.length && !unverified.length` 는 유지하되 `stale` 은 실패로 세지 않는다. 보고서·`cleanupReport`·CLEANUP.md 의 잔존 수 계산에서 `stale` 을 빼고 `stale` 필드를 추가한다.
- 테스트: 죽은 `spawn:` 기록 → 두 번째 실행에서 레지스트리 비고 ok:true; foreign(pid 재사용을 `processStartedAt` mock 으로 흉내) → stale 보고 + 신호 없음(kill spy 0회).

**M2 `updateState` 커밋 전 정리 호출** — `src/core/state.ts`
- 순서를 바꾼다: CAS 커밋 → (changed && WAIT_/paused) `runCleanup(scope:'processes')` 를 **try/catch** 로 best-effort 실행(실패는 원장 `cleanup:processes fail` + evidence.error, 상태 전이는 이미 기록됨) → notify 도 try/catch(실패는 원장 `notify:<key> fail`).
- CAS 루프 재시도 상한 5회(초과 시 `상태 갱신 경합이 계속됩니다` 오류). 정리는 루프 밖에서 1회만.
- `cleanupLine` 은 정리 결과가 있을 때만 붙인다.
- 테스트: `runCleanup` 이 throw 해도 전이가 기록되고 `state:` 원장 + `cleanup:processes fail` 원장이 남는다; notify throw 가 호출자에게 전파되지 않는다; CAS 5회 초과 오류.

**M3 메모리 타이머의 `decidePending` 중복** — `extensions/watcher/index.ts`
- 60초 타이머는 `memoryTick(root)` 만 하고, 그 뒤 결정은 `run()`(pending 공유·직렬화) 을 호출해 poll 경로와 같은 통로를 탄다. `memoryPending` 가드는 memoryTick 중복만 막는다.
- 테스트: 같은 틱에 메모리 타이머와 poll 타이머가 겹쳐도 같은 인박스 레코드에 대한 `decidePending` 처리(오케스트레이터 핸들러 호출)가 1회.

**M4 메모리 회복이 `paused(memory)` 에서만 처리됨** — `extensions/orchestrator/index.ts` memory-recovered
- `state === 'paused(memory)'` **또는** `(state === 'WAIT_RESOURCE' && lastPaused === 'memory')` 이면 `lastPaused` 해제 → `PICK` 전이 → autoResume. 그 외 상태에서도 `lastPaused === 'memory'` 면 `lastPaused` 만 해제한다(위임 거부 해제).
- 테스트: WAIT_RESOURCE+lastPaused=memory 에서 recovered → PICK + lastPaused undefined + autoResume 호출; READY+lastPaused=memory → 상태 유지, lastPaused 해제.

**M5 실행 중 verify 를 정리가 죽임** — `src/core/cleanup.ts processes()`
- `kind === 'verify'` 기록 중 `processIdentity` 가 `owned` 이고 heavy 슬롯(또는 기록의 runId) 이 살아 있는 것은 `protectedGroups` 에 넣어 `protected` 로 보고한다(활성 위임과 같은 취급). 죽은 verify 기록은 M1 규칙으로 stale 정리.
- `src/core/verify.ts`: 외부 신호(SIGTERM/SIGINT) 로 중단된 경우 결과에 `interrupted: 'signal'` 을 넣고 원장 evidence 에도 기록한다. `templates/prompts/VERIFY.md`·`FIX.md`: `interrupted` 가 있으면 코드 결함으로 보지 말고 검증을 다시 실행하라는 한 줄.
- 테스트: 살아 있는 owned verify 기록은 `/cleanup` 에서 protected; 죽은 verify 기록은 stale.

**M6 worktree 제거 조건과 CLEANUP 순서의 순환** — `src/core/cleanup.ts worktrees()`
- 제거 허용 조건: `task.status === 'done'` **또는** `(state.state === 'CLEANUP' && state.taskId === item.taskId && options.taskId === item.taskId)`. 위임 없음 + `git status --porcelain` 비어 있음은 유지.
- `templates/prompts/CLEANUP.md`: `fodh cleanup run --task <T> --scope all` 이 워크트리까지 제거한다는 설명을 맞춘다(제거 실패·더러움은 `kept` 로 보고되고 계속 진행).
- 테스트: 임시 git 저장소에서 CLEANUP/T01 + clean 워크트리 → 제거; 같은 조건에 더러운 워크트리 → kept(`작업 트리 변경 있음`); 다른 task 의 워크트리는 건드리지 않음.

**F1 `/cleanup` 결과가 60초 제한에 걸림** — `extensions/orchestrator/index.ts` `/cleanup`
- 알림 키를 `cleanup:<runId>` 로 해 사용자가 직접 요청한 결과는 항상 표시한다. 본문에 `stale`·`protected` 수도 넣는다.
- 테스트: `/cleanup dry` 직후 `/cleanup` 도 TUI notify 가 호출된다.
