# VC1 보정 4 — 위임 스펙

- 기준: VC1 + 보정 1·2·3 작업 트리(미커밋). VC1 118개 통과, typecheck 통과.
- 근거: Opus 4차 검수(APPROVE_WITH_FIXES). 높음 1(probe 재현), 중간 2, 낮음 3.
- 범위

## J1 [높음] replace 객체로 HEAD 감지 속이기

- 검수 재현(등록 워크트리, 빈 설정)
  1. 두뇌가 `git hash-object -w <약한 package.json>` 과 `git replace <실제 blob> <약한 blob>` 을 친다. 훅이 둘 다 허용한다.
  2. 그 뒤에도 status 는 비어 있고, `git diff main..HEAD` 도 비어 있다.
  3. `runVerify` 가 `ok:true, clean:true` 로 끝나고, 채워진 명령은 `[typecheck, lint]` 뿐이다(`npm test` 빠짐). head 가 실제 커밋이라 REVIEW 게이트도 통과한다.
  4. replace ref 는 공유 `refs/replace` 에 남으므로 새로 고침도 복구하지 못하고, 다음 task 에도 이어진다.
- 결정: 두 겹으로 막는다.
  1. **감지·clean 용 git 은 replace 를 따르지 않는다.**
     - 대상: `gitSnapshot`, `dirtyPaths`, HEAD 트리 읽기(ls-tree·show·cat-file·rev-parse), J2 의 공통 디렉터리 확인.
     - 모두 한 헬퍼(예: `harnessGit(cwd, args)`)로 모은다. 헬퍼는 `--no-replace-objects` 전역 옵션을 쓰고, env 에 `GIT_NO_REPLACE_OBJECTS=1` 을 넣는다(J2 env 정리와 같이).
  2. **훅: 두뇌의 `git replace` 쓰기를 막는다.**
     - `pretooluse.mjs` 의 "이력·참조 재작성" 목록에 넣는다. 조회(`git replace`, `-l`·`--list`, `--format=…` 만 있는 경우)는 허용한다. 삭제(`-d`)도 막는다. 사용자 터미널 몫이다.
     - 검수자가 보는 `git show`·`diff` 가 replace 로 바뀌는 것도 이것으로 막는다.
- 테스트
  - 검수 probe 를 그대로 회귀로 둔다(임시 저장소에서 replace ref 를 직접 만든다). 첫 채움이 `npm test` 를 포함하는지, 새로 고침·clean 판정이 replace 를 무시하는지 확인한다.
  - 훅: `git replace A B`·`-f`·`--edit`·`--graft`·`-d` 는 거부, `git replace -l`·인자 없음은 허용.

## J2 [중간] git 환경 고정과 공통 git 디렉터리 확인

- 문제
  - git 호출이 `process.env` 를 그대로 물려받는다. 단일 레포 모드 훅은 `GIT_*` 를 검사하지 않는다. 그래서 두뇌가 `GIT_DIR=… fodh verify run` 처럼 저장소나 설정(`GIT_CONFIG_*`)을 바꿀 수 있다.
  - 등록 워크트리의 `.git` 파일은 워크트리 안이라 두뇌가 고칠 수 있다. 워크트리 안에 가짜 저장소를 만들고 `.git` 파일이 그쪽을 가리키게 하면, 같은 커밋 sha 로 다른 내용을 읽힐 수 있다(가짜 저장소의 오브젝트 파일은 두뇌가 쓸 수 있다).
- 결정
  - `harnessGit` 헬퍼의 env 는 `process.env` 에서 `GIT_` 로 시작하는 키를 **모두** 빼고, `GIT_NO_REPLACE_OBJECTS=1` 을 넣는다.
    - 옵션(`-c`)으로 `core.fsmonitor=false`·`core.untrackedCache=false`·`core.trustctime=true`·`core.checkStat=default`·`core.ignoreStat=false` 를 고정한다(J4 와 같음).
    - 대상은 J1 과 같다. 사용자가 설정한 검증 명령 실행 env 는 바꾸지 않는다.
  - **공통 git 디렉터리 확인**: 기준 경로가 등록 워크트리면 두 값의 realpath 가 같아야 한다.
    - `harnessGit(base, ['rev-parse', '--git-common-dir'])`(상대 경로면 base 기준으로 푼다)
    - 그 워크트리가 속한 저장소 main 경로(단일 레포 루트, 워크스페이스는 멤버 경로)의 같은 값
    - 다르면 git 정보를 못 읽은 것과 같게 처리한다.
      - 첫 채움·새로 고침·detect: 보정 3 의 `등록 워크트리에서 git 정보를 읽을 수 없습니다` 로 실패. 새로 고침만은 조용히 현재 설정으로 실행.
      - 검증 증거: `clean` 은 `null`, `head` 는 `null`.
    - 증거가 이렇게 남으면 REVIEW 게이트는 지금처럼 등록 워크트리의 `clean === true` 를 요구하므로 막힌다. 게이트 쪽 코드가 이 값을 쓰는지 확인만 하고 게이트 로직은 바꾸지 않는다.
  - 등록 여부와 main 경로를 얻는 방법은 기존 `state.worktrees`·config 멤버 정보를 쓴다. 방식은 자유다.
- 테스트
  - `GIT_DIR` 을 다른 저장소로 둔 env 에서 `runVerify` → 감지·clean 이 등록 워크트리 기준인지, 또는 실패하는지 확인한다.
  - 등록 워크트리 `.git` 파일을 워크트리 안 가짜 저장소로 바꾼 뒤 `runVerify` → 첫 채움 실패, 설정 그대로, 증거 `clean` 이 true 가 아님.
  - 정상 워크트리·워크스페이스 멤버 워크트리는 통과한다.

## J3 [중간] skip-worktree 항목은 모두 dirty

- 보정 3 I2 는 "작업 트리에 없는 S 항목"을 sparse checkout 으로 보고 허용했다.
  - 그러나 두뇌가 `update-index --skip-worktree` 뒤 실패하는 테스트 파일을 지우는 것과 구별되지 않는다.
  - 그러면 검증은 그 파일 없이 돌고, 증거는 clean 이며, 커밋 diff 에는 흔적이 없다.
- 결정: `ls-files -v` 에 `S`(또는 소문자) 항목이 **하나라도** 있으면 dirty 다.
  - sparse checkout 은 하네스 등록 워크트리에서 지원하지 않는다고 README 한계 표에 한 줄 적는다.
  - `core.sparseCheckout` 설정은 두뇌가 바꿀 수 있으므로 판단 근거로 쓰지 않는다.
- 테스트
  - 보정 3 의 "없는 sparse S 항목 허용" 테스트를 dirty 로 바꾼다.
  - skip-worktree + 파일 삭제 → clean=false.

## J4 [낮음] clean 판정 설정 고정

- J2 의 `-c` 고정 옵션을 `status`·`ls-files`·`diff` 류 모든 clean 판정 호출에 적용한다.
- 테스트: 저장소에 `core.trustctime=false`·`core.checkStat=minimal`·`core.ignoreStat=true`·`core.untrackedCache=true`·`status.showUntrackedFiles=no` 를 설정한다. 그 상태에서 수정·미추적 파일이 있으면 clean=false 여야 한다(기존 I2 테스트에 설정만 더해도 된다).

## J5 [낮음] 새로 고침·첫 채움의 쓰기 오류

- 새로 고침의 `writeAutoVerify` 가 try 밖이다.
  - 검수 재현: 이름에 줄바꿈이 든 폴더(`a\nb/package.json`)를 커밋하면 다음 run 이 `verify.commands는 문자열 배열이어야 합니다` 로 throw 한다.
  - 사용자가 동시에 설정을 바꿔 생기는 `verifyUserSetError` 도 같은 경로로 throw 한다.
- 결정
  - 새로 고침: 감지·쓰기 오류는 모두 잡는다. 현재 설정으로 계속 실행하고, 원장에 `verify:auto-config` warn(via `refresh`, 오류 문구 redact)을 남긴다.
  - 첫 채움: `writeAutoVerify` 오류는 throw 하지 않고 `finish({ ok:false, error })` 로 돌려준다.
  - 감지: 폴더·파일 이름에 제어 문자(`\x00-\x1f`, `\x7f`)가 있으면 fs·HEAD 모드 모두 그 항목을 건너뛴다. 건너뛸 이름 규칙과 같다.
- 테스트
  - 줄바꿈 폴더 커밋 뒤 run → throw 없음, 기존 명령 실행.
  - 새로 고침 중 `verifyUserSetError` → 현재 설정으로 실행, warn 원장.
  - 첫 채움 쓰기 오류 → `ok:false`.

## J6 [낮음·성능] HEAD 모드 git 호출 수

- 지금은 디렉터리마다 `ls-tree` 를 하나씩 띄운다. 새로 고침 때문에 일반 run 마다 이 탐색이 돈다.
- 결정
  - HEAD 모드의 git 호출 수가 디렉터리 수에 비례하지 않게 한다. 다음 중 하나를 쓴다.
    - 깊이 단계마다 여러 경로를 한 번에 `ls-tree` 한다(`<sha> -- dir1/ dir2/ …`, 경로가 많으면 나눠서).
    - 파일 내용은 `cat-file --batch` 한 번으로 읽는다.
  - 결과는 fs 모드와 같아야 한다(보정 3 동등성 테스트가 그대로 통과).
  - 일반 run 1회의 git 호출 수를 세는 테스트를 하나 둔다. 예: 최상위 폴더 40개인 저장소에서 새로 고침 감지의 git 호출이 20회 이하. 세는 방법은 자유다.
- 서브모듈(gitlink 160000)은 HEAD 모드에서 탐색하지 않는다. README 한계 표에 한 줄 적는다: init(fs) 이 서브모듈 스택을 채우면 새로 고침은 일어나지 않고 설정은 그대로다.

## 작업 규칙

- 전체 테스트(`npm test`, 인자 없는 `npx vitest run`)는 돌리지 않는다.
  - 반드시 돌릴 파일
    - vc1 3개, `verify.test.ts`, `p7-verify-cwd.test.ts`, `p7-evidence.test.ts`, `p7-commit.test.ts`, `p7-state.test.ts`, `p1-state-revision.test.ts`
    - 훅 관련: `rg -l "update-ref" test/` 로 찾은 파일 전부(w3a golden 포함)
    - `templates.test.ts`, `w3b-templates.test.ts`, `w3b-golden.test.ts`
  - 모든 vitest 호출에 `FODH_NOTIFY_OS=off --maxWorkers=1 --no-file-parallelism` 을 붙인다. 한 번에 파일 3개 이하로 나눠 돌린다.
  - `npm run typecheck`·`git diff --check` 도 돌린다.
- VC1 이전 테스트의 단언은 바꾸지 않는다.
  - 훅 golden 에 `git replace` 쓰기가 허용으로 들어 있으면 이 스펙의 의도 변경이다. 결과 문서에 그 케이스를 적고 기대값만 거부로 바꾼다. 다른 기존 단언이 깨지면 멈추고 적는다.
- `/bin/ps` 차단 때문에만 실패하는 테스트는 기록만 한다.
- 커밋·브랜치는 만들지 않는다(임시 저장소는 괜찮다). 비밀값을 쓰지 않는다.
- 결과 문서 끝에 "보정 4" 절을 더한다. 내용: J1~J6 변경 파일:줄, 새·바뀐 테스트, 돌린 파일과 결과 수.
