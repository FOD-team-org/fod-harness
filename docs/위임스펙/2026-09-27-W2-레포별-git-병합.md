## 0. 공통 규칙

0-1. 멤버 해석은 한 곳에서 한다.
- task 의 멤버는 `repoOf(root, config, task)` 로 얻는다.
  - `repoOf` 자신의 오류 문구는 바꾸지 않는다(`test/w1-config.test.ts:18` 이 단언한다).
  - W2 호출자는 워크스페이스 모드에서 `task.repo` 가 없으면 `repoOf` 를 부르기 전에 이 오류를 낸다: `task <T>에 레포가 없습니다: fodh backlog set <T> --repo <이름>`.
- 상태 `worktrees[]` 기록의 멤버를 얻는 도우미를 하나 둔다.
  - `record.repo` 가 있으면 그 이름의 멤버다.
  - 없으면 한 레포 모드에서는 루트 멤버(`.`)다. 워크스페이스 모드에서는 오류다.
- W2 가 손대는 코드 경로는 워크트리·검증 설정을 **`ResolvedWorkspaceMember` 에서만** 읽는다. 한 레포 멤버 `.` 는 최상위 설정을 담고 있다. `config.worktrees`·`config.verify` 를 직접 읽지 않는다(W1 검수 주의).

0-2. "기준 끝(tip)"은 모드에 따라 다르다.
- 워크스페이스 모드: 멤버의 `refs/heads/<baseBranch>` 커밋.
- 한 레포 모드: 루트 `HEAD`. 지금 `rootHead` 와 같다.

0-3. 원장 evidence 에 `repo: <멤버 이름>` 을 더한다. **워크스페이스 모드에서만** 더한다.
- 대상: `worktree:create/remove/link/link-excluded/setup/commit/merge`, `verify:run`.
- 한 레포 모드 evidence 는 키 순서까지 지금과 같다.

0-4. 멤버에 대한 git 은 기존 `git()` 도우미처럼 `git -C <멤버 경로>` 로 부른다. stderr 는 redact 한다.
- 예외는 §4 의 병합·커밋 단계다. 여기서는 stderr 를 오류에 옮기지 않는다.

0-5. 한 레포 모드에 **의도적으로** 더해지는 것(이것 말고는 한 레포 동작이 바뀌면 안 된다)
- REVIEW→MERGE 전이 때 `task.merge.base` 를 쓴다(3-2). 백로그 JSON 의 숨은 칸이고 md 표는 같다.
- `validateTaskCommit` 의 기준점 순서가 `task.merge.base` → 상태 `mergeBase` 다(2절). 둘 다 같은 값이 들어가므로 결과는 같다.
- 재개 때 기준점 검사와 `병합 기준점 어긋남` 판단(3-3).
- 새 명령 `fodh worktree merge`(§4).
- 이 넷은 기존 테스트의 기대값을 바꾸지 않는 범위에서 더한다. 기존 테스트가 이 때문에 깨지면 멈추고 보고한다.

## 1. 워크트리 (`src/core/worktree.ts`, `src/core/worktree-setup.ts`)

1-1. `createWorktree(root, taskId, base?, setupOptions)`

- 멤버 M = task 의 멤버다. 저장소 검사(`--is-inside-work-tree`)는 M 에서 한다.
- base
  - 한 레포 모드: 지금 그대로다. 기본 `HEAD`, 루트가 브랜치 위여야 한다, `baseBranch` = 루트 현재 브랜치.
  - 워크스페이스 모드:
    - `--base` 가 넘어오면 거부한다: `워크스페이스 모드에서는 --base 를 쓸 수 없습니다 — 멤버 기준 브랜치(<b>)에서 갈라집니다`.
    - `baseBranch` = `M.baseBranch` 다.
    - `refs/heads/<baseBranch>` 가 없으면 `멤버 <이름>에 기준 브랜치 <b>가 없습니다` 오류를 낸다.
    - 새 브랜치는 `refs/heads/<baseBranch>` 에서 가른다. M 의 체크아웃이 다른 브랜치여도 그렇다.
  - CLI 는 `--base` 가 없으면 `undefined` 를 넘긴다. 다른 호출자도 확인한다.
- 경로: `canonical(resolve(M.path, M.worktrees.root ?? '..', <prefix><T>))`.
  - 워크스페이스 루트 안쪽·조상이면 거부한다.
  - 워크스페이스 모드에서는 **모든 멤버 경로**의 안쪽·조상도 거부한다.
  - 같은 검사를 `loadConfig`(워크스페이스 모드)·`fodh doctor` 에도 둔다. 멤버의 `worktrees.root` 가 루트나 어느 멤버 안으로 떨어지면 설정 오류다. 워크트리를 만들 때가 되어서야 알게 하지 않는다.
- 옛 브랜치
  - 같은 이름 브랜치가 있는데 상태 `worktrees[]` 에 이 task 기록이 없을 때:
    - 워크스페이스 모드
      - 하네스가 만든 브랜치면 이어 쓴다. 판정: 원장에 이 task 의 `worktree:create` **pre** 가 있고 그 evidence 의 `branch`·`repo` 가 같다. 이런 경우는 둘이다.
        - `worktree add` 와 상태 기록 사이에서 끊긴 경우(pre 만 있다).
        - RECLAIM·DOCS 에서 미완료 task 의 워크트리를 지운 경우(`removeWorktree` 는 브랜치를 지우지 않는다).
      - 이어 쓸 때 base 커밋 = 그 원장 줄들 가운데 가장 최근 `worktree:create` ok 의 `base`. 없으면 `merge-base <branch> refs/heads/<baseBranch>`.
      - 그 밖이면 거부한다. 문구는 `옛 브랜치 <이름>이 남아 있습니다 — 사용자가 지운 뒤 다시`. 원장은 `worktree:create fail`.
    - 한 레포 모드: 지금처럼 이어 쓴다.
  - 기록이 있고 폴더만 없을 때는 두 모드 모두 지금처럼 이어 쓴다.
    - base 커밋 = `record.base`.
    - `record.base` 가 없으면 워크스페이스는 `merge-base <branch> refs/heads/<baseBranch>`, 한 레포는 지금처럼 `HEAD` 다.
- `worktree prune`·`worktree add`·`show-ref` 는 M 에서 한다.
- 상태 기록
  - 워크스페이스 모드는 기록 **맨 앞**에 `repo: M.name` 을 둔다.
  - 워크스페이스 모드의 `worktree:create` pre evidence 에도 `repo` 를 넣는다(위 이어 쓰기 판정에 쓴다).
  - 한 레포 모드 기록은 키·순서가 지금과 같다(`repo` 없음).
- `links`·`setup`·`setupTimeoutMinutes` 는 M 의 값이다.

1-2. `registeredBase`
- 기록의 멤버에서 `merge-base refs/heads/<branch> <X>` 를 계산한다.
- X 는 워크스페이스 모드면 `refs/heads/<record.baseBranch>`, 한 레포 모드면 `HEAD`(지금 그대로)다.

1-3. `linkDependencies`
- 원본 = `resolve(M.path, item)`. 원장은 워크스페이스 루트에 남긴다.
- 인자를 (원장 루트, 원본 루트, 워크트리, …)로 나눈다.
- exclude 줄은 지금처럼 워크트리의 common dir(= M 의 `.git`)에 쓴다.

1-4. `setupWorktree`
- 준비 명령과 시간 제한은 기록 멤버의 `worktrees.setup`·`setupTimeoutMinutes` 를 쓴다.
- 메모리 검사와 로그 경로는 워크스페이스 루트 그대로다.

1-5. `removeWorktree`
- `git worktree remove` 는 기록 멤버에서 부른다.
- 멤버를 알 수 없는 기록(워크스페이스 모드인데 `repo` 없음)이면 오류를 낸다. 아무것도 지우지 않는다.
- 브랜치는 지금처럼 지우지 않는다. 다시 만들 때는 1-1 의 원장 판정으로 이어 쓴다.

1-6. `listWorktrees`
- 한 레포 모드: 출력 모양·값이 지금과 같다.
- 워크스페이스 모드
  - 멤버마다 `worktree list --porcelain` 을 모은다.
  - `registeredInGit` 은 **그 기록 멤버**의 목록으로 판정한다.
  - `porcelain`·`error` 의 워크스페이스 모양(예: 멤버 이름 → 값)은 네가 정하고 결과 문서에 적는다.

1-7. `commitWorktree`
- 로직은 그대로다(워크트리 안에서 커밋하므로 레포별 명의·훅이 돈다).
- 원장 evidence 에 0-3 의 `repo` 만 더한다.

## 2. 커밋 검증 (`validateTaskCommit`)

- 루트에서 하던 git 은 모두 task 멤버 M 에서 한다. 대상은 `.git` 존재 검사, `rev-parse`, `cat-file`, `merge-base`, `rev-list` 다.
  - 한 레포 모드는 M = 루트라 지금과 같다.
- 워크스페이스 모드에서 워크트리 기록의 `repo` 가 task 의 `repo` 와 다르면 오류를 낸다: `task <T> 워크트리 기록의 레포(<a>)가 task 레포(<b>)와 다릅니다`. §4 도 같은 검사를 한다.
- merge 종류
  - 브랜치 검사: M 체크아웃 브랜치가 기준 브랜치여야 한다.
    - 기준 브랜치는 워크스페이스 모드면 `M.baseBranch`, 한 레포 모드면 지금처럼 `record.baseBranch` 다.
    - 워크스페이스 문구: `멤버 <이름> 브랜치가 기준 브랜치(<b>)가 아닙니다`.
    - 한 레포 문구와 `base-branch-unknown` 경고는 지금 그대로다.
  - 기준점: 먼저 `task.merge.base` 를 쓴다.
    - 없고 한 레포 모드면 상태 `mergeBase`(옛 진행 중 task 대체값)를 쓴다.
    - 둘 다 없으면 지금처럼 `merge-commit:merge-base-unknown` 경고를 남긴다.

## 3. task 별 병합 기준점 (`merge.base`)

3-1. 타입과 저장
- `Task.merge` = `{ commit?: string; base?: string; baseJudgment?: string }`.
- 백로그 JSON 에만 둔다. md 표 모양은 바뀌지 않는다.
- md 들여오기·`backlog sync` 가 이 숨은 칸을 보존해야 한다. 지금 `merge.commit` 보존 방식을 따르고 테스트로 확인한다.
- `spec.rev` 가 오르면 지금처럼 `merge` 전체가 초기화된다.

3-2. REVIEW → MERGE(재개가 아닌 전이)
- 기준 끝(0-2)을 계산해 `task.merge.base` 에 쓴다. 이미 값이 있어도 덮어쓴다. `baseJudgment` 는 지운다.
  - 기준 끝은 전이를 확정하는 `updateState` 콜백 **안에서** 계산한다(지금 `rootHead` 처럼). 콜백 밖에서 미리 구해 두지 않는다.
  - 워크스페이스 모드에서 계산이 실패하면 전이를 거부한다: `멤버 <이름> 기준 브랜치(<b>) 끝을 읽을 수 없습니다`.
  - 한 레포 모드에서 `rootHead` 가 null 이면(git 이 아닌 루트, 예: p7-correction8) `merge.base` 를 쓰지 않는다. 전이는 지금처럼 된다.
- 상태 `mergeBase`
  - 한 레포 모드: 지금처럼 `rootHead` 를 쓴다.
  - 워크스페이스 모드: 바꾸지 않는다(루트 HEAD 는 의미가 없다).
- 잠금은 겹쳐 잡지 않는다. 전이를 커밋한 뒤 같은 `transitionState` 호출 안에서 `setTask` 로 쓴다.
  - 그 사이에 끊기면 `merge.base` 없는 MERGE 가 된다. 이 경우는 3-3·§4 의 "없음" 경로로 처리한다.
  - 더 안전한 순서가 있으면 결과 문서에 근거를 적고 써도 된다.

3-3. 재개로 MERGE 에 들어갈 때
- 대상은 `runPick` 의 RESUME(`next === 'MERGE'`)이다. `transitionState(…, { resume: true })` 를 부르는 곳은 `runPick` 하나뿐이다. 다른 호출자가 생기면 같은 검사를 거치게 한다.
- 일시정지(paused·WAIT_JUDGMENT)에서 MERGE 로 돌아오는 경로도 PICK 을 지나 이 RESUME 분기로 들어온다. 따로 우회로를 만들지 않는다.
- **전이 전에** 검사한다.

| 경우 | 동작 |
|---|---|
| `merge.base` 가 있고 기준 끝의 조상 | 그대로 재개 |
| `merge.base` 없음 | 워크스페이스: 기준 끝으로 정하고 원장 `merge-base:reset` warn(`reason: 'missing'`). 한 레포: 아무것도 하지 않는다(상태 `mergeBase` 대체값) |
| 조상 아님, `merge.baseJudgment` 의 판단이 판단기록에 완료됐고 **선택이 ①** | 기준 끝으로 다시 정하고 `baseJudgment` 를 지운다. 원장 `merge-base:reset` warn(`reason: 'judged', judgment`). 그대로 재개 |
| 조상 아님, 그 밖 | 재개하지 않는다. 아래 판단을 올린다 |

- 조상 판정에서 git 이 실패하면(기준 브랜치 없음, 커밋 없음, 시간 초과 등) "조상 아님"으로 본다. 막는 쪽으로 닫는다.
- 선택 번호는 판단기록에 남은 답을 지금 판단 분류기로 다시 읽어 얻는다. ② 보류로 완료됐거나 번호를 읽을 수 없으면 "그 밖"이다.
- 올리는 판단
  - 제목: `병합 기준점 어긋남 <T>·<repo>: 새 기준점으로 병합 / 보류`. 한 레포 모드는 `·<repo>` 없이 `병합 기준점 어긋남 <T>: …`.
  - 배경: `<repo> <baseBranch>가 검수 때 기준점(<짧은 sha>) 뒤로 되돌려졌습니다. 확인 없이 병합하지 않습니다.`
  - 선택지: `['지금 기준 브랜치 끝을 새 기준점으로 삼아 병합 재개', '보류(task 를 막힌 채로 둔다)']`
  - 추천: `① 되돌림이 의도한 것이면 새 기준점으로 병합`
  - 그 밖: `blocks: <T>`, `resolution: 'resume'`, `dedupeKey: merge-base:<T>:<base>`
  - `origin` 은 넘기지 않는다. 그래서 오토파일럿 대상이 아니다.
- 판단을 올린 뒤
  - `setTask(T, { status: 'blocked(<id>)', judgment: <id>, merge: { baseJudgment: <id> }, resume: task.resume ?? { status: task.status, state: 'MERGE', at: <지금> } })` 를 한다.
    - `resume` 을 남기는 이유: 회수(`reclaimTask`)를 거치지 않은 일시정지 복귀는 `task.resume` 이 없다. 없으면 ① 적용 뒤 task 가 `ready` 로 풀려 SPEC 부터 다시 시작한다. 재개 지점(MERGE)을 잃지 않게 한다.
    - `task.resume` 이 이미 있으면 그대로 둔다.
  - 상태 파일의 `resumeTask`·`resumeState` 는 이 task 를 가리킬 때만 지운다. 막힌 task 로 곧장 다시 RESUME 하지 않게 한다.
  - 바뀐 백로그로 PICK 결정을 다시 계산한다. 고아 task 처리(`decidePick` 의 `remaining` 재계산)처럼 `resumeTask` 없이 계산한다. 다시 계산한 결정이 또 MERGE RESUME 이면 같은 검사를 한다. 이 반복은 백로그 task 수만큼으로 제한한다. 넘으면 `pick:merge-base-loop` 판단을 올리고 멈춘다.
- `resolution: 'resume'` 이므로 ① 적용은 task 를 `task.resume.status` 로 풀고, ② 보류는 막힌 채로 둔다. 풀린 task 는 저장된 재개 지점(MERGE)으로 다시 이 검사를 지난다. 이때 표의 셋째 줄로 재개된다.

## 4. `fodh worktree merge <T>` (새 명령, 두 모드 공통)

설계 §6-1 을 그대로 구현한다. 아래는 구현 세부다.

4-1. 잠금과 조건
- `harness-worktree` 잠금 안에서 한다. 다음을 모두 만족해야 한다.
  - 상태 `MERGE`, `state.taskId === T`
  - `task.review.commit` 이 있고 `review.high === 0`
  - 등록된 워크트리 기록이 있다. 워크스페이스 모드에서는 `record.repo === M.name` 이다(2절 검사).
- M = task 멤버. 기준 브랜치 b 는 2절 규칙과 같다.
  - 한 레포 모드에서 `record.baseBranch` 가 없으면 현재 브랜치를 쓰고 `merge-commit:base-branch-unknown` warn 을 남긴다.
- M 에 `.git` 이 없으면 `git 저장소가 아닙니다` 오류를 낸다.

4-2. 원장 `worktree:merge` pre 와 끝맺음
- pre evidence: `{ repo?, branch, review, baseTip }`. `repo` 는 워크스페이스 모드에서만 넣는다.
- pre 를 쓴 뒤의 **모든 출구**는 같은 runId 의 ok 또는 fail 로 끝맺는다. `try/finally` 로 보장한다. 사전 검사 거부도 fail 이다.
- fail evidence: `{ repo?, reason, stage?, exitCode?, aborted? }`.
  - `reason` 은 고정 코드 하나다: `dirty`·`branch`·`tip`·`base`·`merge-head`·`already-in-base`·`conflict`·`hook`·`not-started`·`timeout`·`record`.
  - 한 레포 모드에서 git merge 자체가 "덮어쓸 로컬 변경" 으로 거부한 경우는 `not-started` 다(4-6).
- 끝맺지 못한 pre(프로세스가 죽은 경우)는 지금처럼 복구 프롬프트의 unknown 항목으로 나온다.

4-3. 이미 병합됨
- 다음 중 하나면 git 을 건드리지 않고 4-7 로 간다. 출력에 `alreadyMerged: true` 를 넣는다.
  1. `rev-list --first-parent --merges <merge.base>..refs/heads/<b>` 로 찾은 병합 커밋 가운데 둘째 부모가 `review.commit` 인 것이 있다. 그 커밋이 병합 커밋이다. 하네스 병합 뒤 기준 브랜치에 다른 커밋이 더 쌓인 경우도 여기서 잡힌다.
     - `merge.base` 가 없으면(한 레포 옛 task) 상태 `mergeBase`, 그것도 없으면 b 끝의 첫째 부모 사슬 200개까지만 본다.
  2. 사용자가 fast-forward 로 넣어서 `review.commit` 이 b 끝의 조상이고 병합 커밋이 없다. 이때 병합 커밋 = `review.commit` 이다. 원장 ok 에 `fastForward: true` 를 남긴다.
- 찾은 커밋은 4-7 에서 `validateTaskCommit` 으로 다시 확인한다. 확인에 실패하면 오류를 낸다: `검수 커밋이 이미 <b>에 들어 있지만 병합 기록으로 확인할 수 없습니다 — 사용자가 확인`. 원장 fail `reason: 'already-in-base'`.

4-4. 남은 병합(`MERGE_HEAD`, M 에서 `rev-parse -q --verify MERGE_HEAD`)
- 하네스 표시 파일로만 주인을 가린다. 원장만으로 판정하지 않는다(옛 pre 가 남아 있으면 사용자 병합을 지울 수 있다).
  - 표시 파일: `<M 의 git common dir>/fodh-merge.json` = `{ runId, taskId, review, at }`. 4-6 의 1단계 **직전에** 쓰고, 병합이 끝나거나 되돌린 뒤 지운다.
- 하네스가 남긴 것으로 보는 조건(모두):
  - `MERGE_HEAD` 값이 `review.commit` 이다.
  - 표시 파일이 있고 `taskId`·`review` 가 같다.
  - 표시 파일의 `runId` 가 원장에서 이 task 의 `worktree:merge` pre 가운데 **끝맺지 않은 가장 최근 것**이다.
- 그러면 `merge --abort` 하고 표시 파일을 지운 뒤 계속한다. 옛 runId 는 fail(`reason: 'merge-head', aborted: true`)로 끝맺는다.
- 아니면 사용자 병합이다. 아무것도 건드리지 않는다. 판단을 올리고 오류를 낸다.
  - 오류: `멤버 <이름>에 진행 중인 병합이 있습니다 — 사용자가 정리한 뒤 다시`
  - 판단 제목: `진행 중인 병합 <T>·<repo>: 정리 뒤 재시도 / 보류`. 선택지 `['사용자가 병합을 끝내거나 되돌렸다 — 다시 시도', '보류']`, `blocks: <T>`, `dedupeKey: merge-head:<T>:<MERGE_HEAD>`, `origin` 없음. `resolution` 은 두지 않는다(task 를 막지 않는다).
  - 원장 fail `reason: 'merge-head'`.

4-5. 사전 검사. 하나라도 어기면 오류를 내고 git 을 바꾸지 않는다. 원장 fail 의 `reason` 을 괄호에 적었다.
1. M 체크아웃 브랜치 = b (`branch`).
2. 추적 파일 미커밋 변경이 없다(`status --porcelain --untracked-files=no`) (`dirty`).
   - **워크스페이스 모드만** 검사한다.
   - 한 레포 모드는 루트에 하네스 문서(`docs/backlog.md` 등) 변경이 늘 있다. 그래서 git merge 자체의 보호(덮어쓸 변경이 있으면 거부)에 맡긴다. 지금 두뇌 `git merge` 와 같은 수준이다.
3. task 브랜치 끝 = `review.commit` (`tip`).
4. `task.merge.base` 가 b 끝의 조상이다 (`base`).
   - 없으면: 워크스페이스는 b 끝으로 정하고 원장 `merge-base:reset` warn(`reason: 'missing'`). 한 레포는 상태 `mergeBase` 를 쓰고, 그것도 없으면 이 검사를 건너뛴다.
   - git 이 실패하면 조상 아님으로 본다.
5. 무시되지 않은 추적 안 된 파일은 **경고만** 한다.
   - 출력 `warnings.untracked = { count, paths }`. `paths` 는 앞 5개, redact 한다.
   - 원장 `worktree:merge:untracked` warn.
   - 워크스페이스 모드만 한다.

4-6. 병합
0. 표시 파일(4-4)을 쓴다.
1. `git -C M merge --no-ff --no-commit --no-autostash <review.commit>`
2. `git -C M commit -m "merge(<T>): <task 제목>"`
- 금지: `--no-verify`, `-c user.*`, `--author`.
- 실행 방식(두 단계 공통)
  - stdin 은 닫는다(`ignore`). 훅이 입력을 기다리며 멈추지 않게 한다.
  - stdout 은 버린다. stderr 는 끝 4KB 만 메모리에 두고 redact 한다. 이 꼬리는 **원장 evidence 의 `stderrTail` 에만** 남긴다. 오류 문구·CLI 출력에는 넣지 않는다.
  - 시간 제한은 단계마다 10분이다. 넘으면 **프로세스 그룹 전체**를 죽인다(`detached` + 음수 pid). 기존 `proc-tree`·`procs` 도우미가 있으면 쓴다.
- 실패 분류
  - 1단계가 0 이 아닌 값으로 끝났고 `MERGE_HEAD` 가 없다: 병합이 시작되지 않았다(`not-started`). 되돌릴 것이 없다. 표시 파일을 지운다. 문구: `병합을 시작하지 못했습니다: <T> → <repo> <b> — 기준 브랜치의 로컬 변경·잠금을 확인`.
  - 1단계 실패이고 `MERGE_HEAD` 가 있다: 충돌(`conflict`). `merge --abort`. 문구: `충돌: <T> 를 <repo> <b>에 병합할 수 없습니다 — 되돌렸습니다`
  - 2단계 실패: 훅 거부(`hook`). `MERGE_HEAD` 가 있으면 `merge --abort`. 문구: `레포 커밋 훅이 거부했습니다 — 명의·훅을 확인(되돌렸습니다)`
  - 시간 초과(`timeout`): 그룹을 죽이고, `MERGE_HEAD` 가 있으면 `merge --abort`. 문구: `병합이 10분 안에 끝나지 않았습니다 — 되돌렸습니다`
  - 한 레포 모드 문구에는 `<repo>` 자리에 아무것도 넣지 않는다(`<T> 를 <b>에 …`).
  - 모든 문구는 고정이다. **git stderr·훅 출력은 오류·CLI 출력에 옮기지 않는다.**
  - 원장 fail evidence: `{ repo?, reason, stage: 'merge'|'commit', exitCode, aborted, stderrTail? }`.
- abort 뒤에는 `MERGE_HEAD` 가 없어야 하고 표시 파일도 지워져야 한다. abort 가 실패하면 표시 파일을 남기고 오류 끝에 `— 되돌리기도 실패했습니다, 사용자가 확인` 을 붙인다.

4-7. 기록
- 병합 커밋은 방금 만든 b 끝, 또는 4-3 에서 찾은 커밋이다. `validateTaskCommit(root, T, <sha>, 'merge')` 로 확인한다.
  - fast-forward(4-3 의 2)는 병합 커밋 모양이 아니므로 `validateTaskCommit` 의 merge 검사를 거치지 않는다. 대신 `review.commit` 이 b 끝의 조상이고 task 브랜치 끝과 같음을 확인한다.
  - 확인에 실패하면 원장 fail `reason: 'record'`. git 은 되돌리지 않는다(이미 커밋됐다).
- `setTask(T, { merge: { commit } })` 를 한다. `merge.base` 는 보존된다.
- 원장 `worktree:merge` ok. evidence: `{ repo?, branch, review, mergeCommit, alreadyMerged?, fastForward? }`.
- 출력 JSON: `{ taskId, repo?, branch, mergeCommit, alreadyMerged?, warnings? }`.
- 전이는 하지 않는다. DOCS 로의 전이는 두뇌가 지금처럼 `fodh state transition DOCS --task T --commit <review>` 로 한다.

4-8. 기존 경로
- `fodh backlog set --merge-commit` 은 두 모드 모두 그대로 남긴다. 검증은 2절(멤버 기준)을 따른다.
- 한 레포 모드에서 두뇌가 루트에서 치는 `git merge` 흐름도 그대로다.

## 8. 기준 브랜치 어긋남 경고

- 워크스페이스 모드에서 **모든 멤버** 체크아웃이 자기 `baseBranch` 위인지 본다.

  - 문구: `멤버 <이름> 체크아웃이 <b>가 아닙니다(현재 <브랜치|detached>) — 이 체크아웃을 읽는 다른 레포 검증이 틀릴 수 있습니다`
  - 원장: `workspace:base-branch` warn, evidence `{ repo, branch }`.
- 부르는 곳
  - `runPick` 이 SPEC·RESUME 을 고를 때: 결정 결과에 `warnings` 를 더한다.
  - `runVerify`: 결과에 `warnings` 를 더한다.
  - 막지는 않는다. 병합(§4)만 자기 멤버 어긋남을 막는다.
- 한 레포 모드에서는 부르지 않는다. 출력에 `warnings` 키가 생기지 않는다.
- 이 검사에서 git 이 실패하면(멤버 경로 없음 등) 예외를 던지지 않는다. `멤버 <이름> 브랜치를 읽을 수 없습니다` 경고 한 줄로 바꾼다.

임시 폴더에 멤버 git 저장소 3개(web·backend·app)와 워크스페이스를 만든다. 테스트 안의 git 은 허용한다. 저장소 로컬 명의를 설정한다. Codex 는 기존 `test/fake-codex` 를 쓴다.

1. 전 흐름(`w2-flow`)
   - 백로그: T01(web) → T02(backend, 의존 T01) → T03(app, 의존 T02).
   - 각 task 를 PICK → SPEC → 워크트리 → IMPLEMENT(가짜 Codex 가 파일 변경) → 커밋 → VERIFY → REVIEW(검수 증거) → `worktree merge` → DOCS → CLEANUP 으로 끝까지 돈다.
   - 확인할 것
     - T01 병합 전에는 T02 가 PICK 되지 않는다.
     - 각 병합 커밋이 해당 멤버 `main` 에 있다. 둘째 부모는 review 커밋이고, 메시지는 `merge(Txx): …` 다.
     - 워크스페이스 루트에 제품 코드가 없다.
     - 원장 evidence 에 `repo` 가 있다.
     - 워크트리가 멤버에서 지워졌다.
   - 기존 흐름 테스트의 도우미를 재사용한다.
2. 워크트리
   - 멤버 체크아웃이 다른 브랜치여도 base 는 `main` 이다.
   - 경로는 멤버 형제다.
   - `links` 원본과 `setup` 명령은 그 멤버 것이다.
   - 등록 안 된 옛 브랜치는 거부한다. 등록된 기록은 폴더가 없어도 이어 쓴다.
   - 하네스가 남긴 브랜치는 이어 쓴다: (가) `worktree add` 직후 상태 기록 전에 끊긴 경우(원장 pre 만), (나) RECLAIM 에서 미완료 task 워크트리를 지운 뒤 다시 만드는 경우. base 는 원장의 ok `base` 다.
   - 멤버 `worktrees.root` 가 루트·다른 멤버 안이면 `loadConfig`·doctor 가 설정 오류로 알린다.
   - 워크스페이스 `--base` 는 거부한다. 기준 브랜치가 없으면 오류다.
   - `list` 는 워크스페이스 모양, remove 는 멤버에서 지운다.
3. 기준점
   - REVIEW→MERGE 가 `merge.base` = 멤버 기준 끝을 쓴다.
   - T01(web)이 MERGE 에서 회수된 사이 T02(backend)가 REVIEW→MERGE 를 지나 병합된다. 그 뒤 T01 재개와 `worktree merge` 가 통과한다.
   - web main 을 되돌리면: 재개하지 않는다, 판단을 올린다(`resolution: resume`, origin 없음), task 는 blocked 다. 판단을 ①로 적용하면 새 기준점으로 재개하고 `merge-base:reset` 을 남긴다. ② 보류면 막힌 채다.
   - 같은 되돌림을 **회수 없이** 일시정지(paused) → PICK 복귀 경로로도 확인한다. 막을 때 `task.resume.state === 'MERGE'` 가 남고, ① 적용 뒤 SPEC 이 아니라 MERGE 로 재개한다.
   - 판단이 완료됐지만 답이 ② 인데 누가 task 를 손으로 풀어 둔 경우: 재개하지 않고 다시 판단을 올린다.
   - 조상 판정 git 실패(기준 브랜치를 지운 경우)는 막는 쪽이다.
   - 다시 계산한 PICK 이 또 어긋난 MERGE 를 고르면 그것도 막는다. 반복 한도를 넘으면 멈춘다.
   - 한 레포 모드: git 이 아닌 루트(p7-correction8 모양)에서 REVIEW→MERGE 는 지금처럼 되고 `merge.base` 를 쓰지 않는다.
   - `merge.base` 가 없으면 기준 끝으로 정하고 경고를 남긴다.
   - md 들여오기·sync 뒤에도 `merge.base` 가 보존된다.
4. `worktree merge`
   - 성공: pre-commit 훅이 실제로 돈다(훅이 표시 파일을 남기게 한다). 백로그 `merge.commit`, 원장 pre·ok 를 확인한다.
   - 재실행: 병합 뒤 기록 전에 끊긴 경우를 흉내 낸다. git 을 건드리지 않고 기록만 한다(`alreadyMerged`).
     - 그 사이 기준 브랜치에 다른 커밋이 더 쌓인 경우에도 `alreadyMerged` 로 찾는다.
     - 사용자가 fast-forward 로 넣은 경우는 `alreadyMerged`·원장 `fastForward: true` 다.
   - 하네스가 남긴 `MERGE_HEAD`(표시 파일 runId = 끝맺지 않은 최근 pre)는 abort 뒤 진행한다. 옛 runId 는 fail 로 끝맺는다.
   - 사용자 `MERGE_HEAD` 는 오류이고 그대로 남는다. 판단이 올라간다. 원장에 옛 pre 가 남아 있어도(표시 파일 없음) 사용자 것으로 본다.
   - pre 뒤 모든 출구(사전 검사 거부 포함)가 ok/fail 로 끝맺어져 unknown 이 남지 않는다. fail 의 `reason` 코드를 확인한다.
   - 병합이 시작되지 못한 경우(`not-started`, 예: 한 레포 모드에서 병합이 덮어쓸 추적 파일 변경)는 abort 하지 않는다.
   - 훅이 stdin 을 읽으려 해도 멈추지 않는다. 시간 초과는 테스트용으로 짧게 줄여 그룹 종료·abort 를 확인한다(시간 값은 테스트에서만 주입).
   - 워크트리 기록의 `repo` 가 task 레포와 다르면 거부한다.
   - 거부: 추적 파일 미커밋, 다른 브랜치, 브랜치 끝 ≠ review, `merge.base` 조상 아님, 상태·task·high 조건.
   - 추적 안 된 파일은 경고만 한다(개수·경로·원장).
   - 충돌은 abort 하고 `MERGE_HEAD` 가 없다. 문구는 고정이다.
   - pre-commit 거부: 훅이 stderr 에 비밀값 모양 문자열을 찍게 한다. abort 하고, 문구는 고정이며, 그 문자열이 오류·출력·원장 어디에도 없다.
   - 사용자 `review.commit` 이 이미 들어간 경우는 오류다.
   - 한 레포 모드: 루트 병합이 성공한다. 루트 `docs/backlog.md` 미커밋 변경이 병합을 막지 않는다.
5. 검증: 멤버 명령·시간 제한을 쓴다. 루트·멤버 main·다른 워크트리 cwd 는 거부한다. 워크트리 없는 task 는 정해진 문구로 거부한다. 기준 브랜치 경고가 결과·원장에 남는다.
6. 위임
   - 워크스페이스 머리말 줄이 정확한 문구다. 한 레포 머리말은 고정 스냅샷과 바이트까지 같다.
   - `gitTask` 가 멤버 `.git` 을 본다.
   - `research --repo`: cwd = 멤버 main, read-only. 거부 사례 3개(한 레포 모드, 없는 멤버, `--cwd` 동시)를 확인한다.
7. 감사: 워크스페이스에서 Bash `cp a ../web/src/x.ts` 는 경계 경고다. 등록 워크트리 쓰기는 경고가 없다. 한 레포 판정은 불변이다.
8. 복구 프롬프트: `repo` evidence 가 있는 unknown 항목에 `repo` 가 나온다. 한 레포는 불변이다.
9. PICK 경고: 멤버가 다른 브랜치면 결정 결과에 `warnings` 가 있고 원장에 남는다. 멤버 경로가 사라져 git 이 실패해도 예외 없이 경고 한 줄이다. 한 레포에는 키가 없다.

## 11. 규칙

1. git 금지. fod-harness 저장소에서 commit·branch·stash·reset·checkout 등을 하지 않는다. 테스트가 만든 임시 저장소 안의 git 만 허용한다.
2. **전체 테스트 스위트 실행 절대 금지.** 새 `test/w2-*` 와 영향받는 기존 테스트 파일만 `--maxWorkers=1 --no-file-parallelism` 으로 돌린다. 전체 직렬은 메인이 돌린다.
3. 기존 테스트 파일은 고치지 않는다.
   - 예외: 새 기능이 등록돼 목록이 하나 늘어나는 열거 기대값(명령 목록·명령표 등)에 새 항목을 **더하는 것**만 허용한다.
   - 지우거나 약하게 바꾸는 것은 금지다.
   - 고친 줄은 결과 문서에 파일:줄과 전후를 모두 적는다.
4. 실제 claude/codex/pi/osascript 실행 금지. 네트워크 금지. `FODH_NOTIFY_OS=off`.
5. 비밀 파일(`.env*`·키·인증 파일)을 열지 않는다.
6. 스펙과 코드가 어긋나거나 더 안전한 방법이 있으면 추측해서 넓히지 말고 멈춰서 보고한다. 작은 구현 선택은 결과 문서에 근거와 함께 적는다.
