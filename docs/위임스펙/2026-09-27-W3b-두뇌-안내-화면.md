## 4. MERGE 프롬프트 (`templates/prompts/MERGE.md`)

4-1. 파일 전체를 아래로 바꾼다(두 모드 공통, 20줄). → D8

```
# MERGE
## 지금 할 일
1. `fodh backlog get {{taskId}}`으로 `review.commit`과 `review.high = 0`을 확인한다.
2. `fodh worktree merge {{taskId}}`로 병합한다. 하네스가 task 레포의 기준 브랜치에 병합 커밋을 만들고 `merge.commit`을 기록한다. `git merge` 를 직접 치지 않는다. 비-git 프로젝트는 병합 없이 `fodh backlog set {{taskId}} --merge-commit none` 이다.
3. 출력에 `warnings`(추적 안 된 파일 등)가 있으면 DOCS 작업일지에 옮겨 적는다. 출력에 `error` 가 있으면 그 문구가 원인이다.
4. `fodh state transition DOCS --task {{taskId}} --commit <review.commit>`으로 전이한다.
병합 실패(충돌·기준 브랜치·미커밋 변경·커밋 훅 거부)는 재시도하거나 git 으로 정리하지 않고 아래 판단 등록·회수 명령으로 회수한다.
## 산출물
하네스가 만든 병합 커밋과 `merge.commit` 기록.
## 끝내는 조건
`fodh backlog get {{taskId}}` 에 `merge.commit` 이 있고, 검수 대상과 실제 작업 SHA 가 일치한다.
## 다음 fodh 명령
- 완료 → `fodh state transition DOCS --task {{taskId}} --commit <검수한작업sha>`
- 병합 실패·승인 필요 → `fodh judgment add --title "<제목>" --background "<배경>" --options "선택1|선택2" --recommend "<추천>" [--detail <문서>] --blocks {{taskId}} --reclaim` 판단 등록 시 배경은 두 문장 안으로 쓴다. 긴 근거는 문서에 쓰고 `--detail <문서>`로 연결한다.
## 금지
두뇌는 소스 파일을 쓰지 않는다. Write/Edit 는 docs/·CLAUDE.md 에만, 구현은 위임한다.
승인 미결 동작을 실행하지 않는다.
review.commit 을 바꾸는 판단을 만들지 않는다.
`git merge`·`git merge --abort`·`git reset` 으로 병합하거나 실패한 병합을 정리하지 않는다.
`대기: 사용자` 는 쓰지 않는다. 사용자 결정은 `fodh judgment add … --blocks {{taskId}} --reclaim`
```

- 템플릿 공통 제약(`templates.test.ts` 14-23)을 지킨다: 5절 순서, 25줄 이하, 금지 첫 줄, 치환 키 `taskId` 만.
- 판단 예시는 필수 플래그를 모두 가진다(같은 파일 63행 테스트). F27·F28 마지막 줄 문구는 그대로다.

## 10. 규칙

1. git 금지.
   - fod-harness 저장소에서 commit·branch·stash·reset·checkout 등을 하지 않는다.
   - 테스트가 만든 임시 저장소 안의 git 만 허용한다.
2. **전체 테스트 스위트 실행 절대 금지.**
   - `npm test`·인자 없는 `vitest run` 도 금지다.
   - §11-1 의 파일만 `--maxWorkers=1 --no-file-parallelism` 으로 돌린다. 전체 직렬은 메인이 돌린다.
3. 기존 테스트 파일은 고치지 않는다.
   - 예외 1: 열거 기대값에 새 항목을 **더하는 것**
   - 예외 2: §0-1 의 E1·E2 뿐이다.
   - 지우거나 약하게 바꾸는 것은 금지다.
   - 고친 줄은 결과 문서에 파일:줄과 전후를 모두 적는다.
4. 실제 claude·codex·pi·osascript 를 실행하지 않는다. 네트워크를 쓰지 않는다. `FODH_NOTIFY_OS=off` 다.
5. 비밀 파일(`.env*`·키·인증 파일)을 열지 않는다. 테스트가 임시 폴더에 만드는 가짜 파일만 예외다.
6. `hooks/` 는 고치지 않는다. §6 은 import 만 한다. 꼭 고쳐야 한다고 판단되면 멈추고 보고한다.
7. `docs/설계/` 를 고치지 않는다.
8. 스펙과 코드가 어긋나거나 더 안전한 방법이 있으면, 추측해서 넓히지 말고 멈춰서 보고한다. 작은 구현 선택은 결과 문서에 근거와 함께 적는다.
9. 골든은 소스·템플릿을 고치기 전에 한 번만 만든다. 다시 만들지 않는다.

### 설계·인계와 코드의 어긋남
1. 설계 §9 의 원본 규칙(스키마·디자인 토큰·규제 문구 = web, OpenAPI = backend)은 WisePharm 전용인데 설정 키가 없다 → D5.
2. 설계 §9 는 멤버 표에 검증 명령을 넣는다. AGENTS.md 까지 생각하면 표 둘이 낫다 → D3.
3. 설계 §10 의 "상태줄"은 없다. 있는 것은 자동 진행 표시(`fodh-autopilot`)뿐이다 → 새 키 `fodh-task`.
4. 설계 §10 "알림 제목": TUI 는 본문만 보여 준다(notify.ts 58). 제목은 macOS·원장에만 간다 → D10.
5. 설계 §11 은 W1·W2 에서 다 끝났다. W3 행의 doctor 몫은 없다.
6. 설계 §10 의 원장·복구 `repo` 는 W2 에서 끝났다(worktree.ts·verify.ts·worktree-merge.ts evidence, turn.ts 47).
7. W3a 인계 "거부되면 명령을 나눈다"는 brain-rules 3행 "`[경계]` … 같은 동작을 재시도하지 않으며"와 부딪힌다 → D6.
8. W3a 인계의 "멤버 비밀 패턴 앞 `/`" 조언은 두뇌가 아니라 설정 작성자 몫이다 → 결과 문서 WisePharm 절.
9. `templates/prompts/PLANNING.md` 4단계 `fodh backlog add` 에 `--repo` 가 없다. 설계 §9 는 이 파일을 들지 않았다 → D14.
10. 지금 MERGE.md 에는 비-git 경로가 없다. `fodh worktree merge` 는 비-git 을 거부한다(worktree-merge.ts 73·75). 그래서 `--merge-commit none` 줄을 더했다.
11. 설계 §13 W3 행의 `skills/*`·`templates/prompts/MERGE.md` 는 기존 테스트가 문구를 고정한다(F19, W1 고정본) → E1·E2 가 필요하다.
12. `autopilotBlocked` 는 지금 최상위 사용자 규칙도 `requiresApproval` 에 든 것만 본다. 훅은 거르지 않는다 → D13(워크스페이스에서만 맞춘다).

### 위험·남는 한계
- R1 한 레포 기존 프로젝트: 업그레이드 뒤 첫 develop-start 에서 CLAUDE.md 가 바뀌어 "커밋 필요" 알림이 한 번 뜨고 스킬 두 개가 갱신된다. 결과 문서와 릴리스 안내에 적는다. develop-start 전까지는 CLAUDE.md 가 옛 흐름표를 보인다. MERGE.md 는 지시문마다 읽혀 곧바로 새 안내가 되고, 새 brain-rules 줄이 우선한다. doctor 는 템플릿 변경을 감지하지 않는다(표식은 설정 해시).
- R2 한 레포 MERGE 가 `git merge --no-ff` 에서 `fodh worktree merge` 로 바뀐다. 이 명령은 더 엄격하다(루트 브랜치·task 브랜치 끝·기준점 검사). 그래서 판단이 늘 수 있다. 병합 방식(`--no-ff`)은 같다(worktree-merge.ts 137). 훅은 한 레포 MERGE 의 직접 `git merge` 를 막지 않는다(pretooluse.mjs 540-544). MERGE.md·brain-rules 안내에만 기댄다.
- R3 상태줄 라벨은 session_start·agent_end·`/status`·develop-start 때만 갱신된다. 두뇌 턴 한가운데의 PICK 전환은 턴이 끝날 때 반영된다.
- R4 하네스 자체의 `listWorkspace`(workspace.ts 224-241) `git status` 는 `--no-optional-locks` 를 쓰지 않는다. 사용자 git 과 `index.lock` 이 드물게 부딪칠 수 있다. 이번 범위 밖이다.
- R5 코드 조각 없이 산문으로만 쓴 위험 동작(예: "시드 데이터를 넣는다")은 멤버 규칙에 걸리지 않는다. description 부분 일치와 키워드 정규식만 잡는다. 훅이 실행 때 막으므로 실행되지는 않는다. 펜스 블록·짝 안 맞는 백틱 속 명령도 코드 조각으로 보지 않는다(산문 비교만).
- R6 한 레포에서 `requiresApproval` 에 없는 사용자 규칙은 계속 자동 진행을 막지 않는다(원래 비대칭, D13).
- R7 워크스페이스 해시가 바뀌어 W1~W3a 시기에 만든 워크스페이스 CLAUDE.md 는 doctor 에서 낡음으로 나온다. 실제 적용 전이라 영향은 없다. develop-start 가 다시 만든다.
- R8 두뇌가 멤버 CLAUDE.md·AGENTS.md 를 실제로 먼저 읽는지는 안내에만 기댄다. 강제 장치는 없다.
- R9 turn.ts 239 의 `[경계]` 사용자 안내는 "다시 시도하지 말고 위임"이다. brain-rules 3행 예외(한 번 고쳐 다시 치기)와 문구가 다르다. turn.ts 는 이번 범위 밖이다. 결과 문서 "남은 한계"에 적는다.
