## F17 (high) — 워처 `slot-free` 는 슬롯 파일을 봐야 한다 (`src/core/watcher.ts` slotCheck)

라이브 재검: Fable 이 슬롯을 살아 있는 무관 프로세스(tmux 서버) 명의로 점유한 뒤 두뇌가 `codex 슬롯 사용 중` → `paused(slot)` 까지는 정상. 이후 슬롯 파일을 비웠는데도(`{"codex": null}`) 워처는 `state.awaitingSlot.owner` 의 pid 생사만 보므로(`slotOwnerIdentity(waiting.owner)` = owned) 4분 넘게 `slot-free` 를 내지 않았다. 실제 운영에서는 다른 프로젝트의 Codex 가 끝나면 `releaseSlot` 으로 파일이 비워지지만 그 하네스 프로세스(Pi/워처)는 계속 살아 있으므로 같은 문제가 난다.

- 판정 규칙: 매 검사에서 `~/.pi/agent/fod-harness/slots.json` 을 읽어 (a) `codex`·`heavy` 슬롯이 모두 비어 있으면 free, (b) 채워져 있으면 그 파일의 소유자(대기 시점 소유자가 아니라 **현재** 소유자)에 대해 `slotOwnerIdentity` 를 보고 죽었으면 free(`acquireSlot` 이 stale 로 치우는 것과 같은 기준), owned/unknown/orphan 이면 계속 대기. 소유자가 바뀌었으면 `awaitingSlot.owner` 를 현재 소유자로 갱신하고 원장 `slot:owner-changed`.
- unknown 10회 알림(보정 5 L2)은 현재 소유자 기준으로 유지.
- 테스트: 소유자 pid 가 살아 있어도 슬롯 파일이 비면 `slot-free`; 파일이 다른 살아 있는 소유자로 바뀌면 대기 유지 + owner 갱신; 그 소유자가 죽으면 `slot-free`.

## F22 (medium) — 판단으로 막힌 task 를 재개하면 원래 단계로 돌아가야 한다 (`src/core/judgment*.ts` resume 정책, `src/core/pick.ts`, `src/core/backlog.ts`)

라이브 재검: MERGE 단계의 T02 가 `judgment add --reclaim` 으로 `blocked(A10)` 이 됐다가 답 ② 적용(정책 resume = "ready 로 되돌려 재개") 으로 `ready` 가 되자 PICK 이 T02 를 **SPEC 부터** 다시 시작했다(검수·병합 증거는 그대로인데 단계 정보가 사라짐). 두뇌는 SPEC→RECLAIM→PICK 을 반복했고 중간에 T18 을 잘못 집기도 했다(`SPEC T18` 뒤 다시 T02).

- 추가 관찰: RECLAIM→PICK 에서 `taskId` 가 비워지고 `resumeTask` 도 없어, 답 적용 뒤 PICK 은 T02 를 **고아**로 보고 또 다른 판단(A14 "고아 task T02: 재개/폐기") 을 만들어 WAIT_JUDGMENT 로 갔다. 사용자 CLI 에는 상태를 MERGE 로 되돌릴 수단이 없다(`backlog set --status merge` 는 "상태는 전이로만 바뀝니다"). 즉 RECLAIM 진입 시 `resumeTask: { taskId, resumeState: <RECLAIM 직전 상태> }` 를 보존하고, 판단 답 적용(resume) 뒤 PICK 은 그 `resumeTask` 로 RESUME 해야 한다(고아 판정보다 먼저).

- PICK 이 현재 `taskId` 가 있는 task 루프 상태에서 다른 task 를 집지 않도록: `state.taskId` 가 있고 그 task 가 `ready/doing/...` 이면 그 task 를 우선 RESUME(다른 task 선택 금지). 테스트 2건(MERGE 에서 blocked → 답 → MERGE 복귀; taskId 유지 시 다른 task 미선택).
