# P1 구현 결과 (2026-09-24)

기준: `2026-09-24-P1-상태기계-명령.md`, 설계 v0.3.1 및 P1.5 main 병합본.

**최종 `npm test`: 470개 중 468 통과 / 2 실패. `npm run typecheck`: exit 0 / 오류 0.** 실패는 아래 실제 ps 조회 2개이며 전체 0 실패 기준은 환경 밖 재검증이 남았다.

P1 상태기계·백로그·PICK·RECLAIM·판단 적용·Pi 명령·자동 재개 루프를 구현했다. 실제 위임, 워처, 자원 측정, 파일·워크트리 삭제는 이번 범위에 포함하지 않았다. 아래 테스트 결과는 가짜 Claude와 Pi API 대역을 사용한 이번 실행의 결과이며, 이전 Fable의 247개 통과나 실제 Claude 실기를 이번에 재현했다는 의미는 아니다.

## 새 명령과 모듈

CLI는 기존 방식대로 stdout에 JSON 한 덩어리를 반환한다. 오류는 exit 1이며 repair 초과에는 action=reclaim, DoD 미달에는 missing 배열이 포함된다.

- `fodh state transition <to> [--task ID] [--commit SHA] [--system]`
- `fodh backlog list [--json]`, `get ID`, `add --title … --category … [--depends …]`
- `fodh backlog set ID`: status, depends, title, category, repair, judgment, worktree, review-commit, review-high, verify-ok, merge-commit, docs-ok, cleanup-ok 및 추가 spec-rev 옵션.
- `fodh pick`, `fodh reclaim --task ID --judgment A번호`, `fodh cleanup report`
- `fodh judgment apply [A번호…]`, `fodh judgment add … --blocks ID --reclaim`; 승인 성격을 명시하는 `--requires-approval` 추가.
- Pi `/project-start [이름]`, `/develop-start`, `/status`, `/judged [A번호…]`, `/cleanup`.

신규 모듈: `src/core/backlog.ts`, `pick.ts`, `reclaim.ts`, `extensions/orchestrator/index.ts`.
확장 모듈: `src/core/state.ts`, `judgment.ts`, `src/cli/index.ts`. `src/provider/turn.ts`는 훅 거부 판단에 승인 필수 메타데이터를 추가했다.
`package.json`에는 오케스트레이터 확장 등록만 추가했다.

신규 템플릿: `templates/backlog.md`, `templates/작업일지.md`, `templates/prompts/{INTERVIEW,RESEARCH,PRD_DRAFT,ARCH,REVIEW,PLANNING,PICK,SPEC,IMPLEMENT,VERIFY,FIX,MERGE,DOCS,CLEANUP,RECLAIM,recovering}.md`.
신규 테스트: `test/p1-core.test.ts`, `p1-reclaim.test.ts`, `p1-reclaim-integration.test.ts`, `orchestrator.test.ts`.

기존 `core.test.ts`, `revision.test.ts`, `provider.test.ts`의 무제한 전이 전제는 유효한 선행 상태·백로그 task·doctor로 준비하도록 바꿨다. 새 초기 autoTurns 필드도 명시적으로 검사한다. 기존 테스트를 삭제·skip하거나 프로세스 검증을 대역으로 바꾸지 않았다.

### 남은 실패 2개 — Fable 환경 밖 재실행

1. `test/revision.test.ts:197` — **잠금 소유자의 실제 프로세스 시작 시각이 다르면 PID가 살아 있어도 stale이다**. `/bin/ps -p <테스트 PID> -o lstart=` 직접 호출에서 `Error: spawn EPERM` 발생. 시작 시각 비교 전 단계에서 실패한다.
2. `test/p1-reclaim-integration.test.ts:12` — **실제 fake-claude task 소유 그룹 회수→레지스트리 0→blocked**. fake-claude 자식을 실제로 생성했으나 `processStartedAt(child.pid)`가 undefined여서 시작 시각 필요 단언에서 실패한다. 이 함수는 같은 `/bin/ps ... -o lstart=` 조회 실패를 undefined로 반환한다. 실제 소유 시각 확인·등록 이후 회수 경로는 이번 환경에서 검증하지 못했다. finally에서 테스트가 생성한 자식 그룹만 종료하고 close를 기다린다.

회수 정책 대역 테스트 10개 통과는 실제 OS 소유권 관찰 성공의 대체 증거가 아니다. 실제 Pi TUI·Claude 실기는 0회다. 위 두 테스트는 skip하거나 기대값을 완화하지 않았으며, ps 허용 환경에서 `npm test`와 `npm run typecheck` 재실행이 필요하다.

수정 중 발견한 Node strip-only의 parameter property 비지원, 이전 무제한 상태 전이에 의존하던 테스트 준비, task 가드 오류 우선순위 불일치는 최종 실행 전에 해소했다. 과거 중간 실행 결과를 최종 수치에 합산하지 않았다.

## 스펙이 침묵하거나 충돌하는 부분의 선택

1. **프로젝트 REVIEW와 task REVIEW:** §1의 REVIEW 진입 task 필수와 ARCH→REVIEW 프로젝트 흐름은 함께 적용할 수 없다. phase와 task 유무로 분리해 프로젝트 검수만 task 가드의 예외로 삼았다. task REVIEW에서 PROJECT_READY/INTERVIEW로 빠지거나 프로젝트 REVIEW에서 MERGE/FIX/RECLAIM으로 가는 것은 거부한다. WAIT_JUDGMENT는 저장한 resumeState로만 복귀한다. 옛 phase 없는 프로젝트 상태도 task가 없으면 같은 경로로 복귀한다.
2. **백로그 없는 develop-start:** §6의 PLANNING 지시와 §1의 IDLE→PLANNING 백로그 필요 조건을 함께 만족하도록 빈 백로그 템플릿을 먼저 만든다. 기존 빈 백로그의 PICK은 모든 작업 완료로 본다. 이미 진행 중인 task를 develop-start로 덮어쓰지는 않는다.
3. **정체 안전 중단:** 일반 CLI의 그래프를 넓히지 않고 내부 stopForJudgment 경로만 활동 상태→WAIT_JUDGMENT 예외를 사용한다. maxAutoTurns는 최상위 설정 키, 기본 3인 양의 정수다. 3회 자동 턴을 보낸 뒤에도 같은 상태/task면 다음 agent_end에서 중단한다. CLEANUP_FAILED와 과거 READY는 자동 재개 대상이 아니다.
4. **미완료 진행 상태:** doing 등 실행 중 task를 PICK이 임의로 ready로 복원하지 않는다. ready도 blocked도 없고 실행 증거가 남은 경우 교착 확인 판단을 만든다. 정체 답 적용도 회수되지 않은 doing을 ready로 바꾸지 않는다. 두뇌가 원장·잔존·작업 증거를 먼저 확인해야 한다.
5. **자원·과금 중단:** 메모리/예산 이력과 슬롯 부족은 ready task가 있어도 우선 대기한다. WAIT_RESOURCE 상태에서 pick만 재호출해도 이력은 유지한다. 외부에서 회복을 확인한 후 명시적인 `fodh state transition PICK`을 실행하면 메모리/예산 이력을 해제한다. P4 전에는 자원 회복 측정이 없다. billing/cleanup 이력은 판단 항목으로 확인하며, 해당 판단 적용 시 원인을 해제한다.
6. **재시도:** count는 예약한 대기 횟수다. 미래 nextAt은 그대로 반환하고, 5·15·60분 대기가 소진된 다음 호출에 판단을 생성한다. 실제 타이머·자동 깨우기는 P2 범위라 추가하지 않았다. decidePick의 시간은 입력 now 또는 상태 시각으로 결정하고, runPick이 현재 시각을 전달한다. 재시도 소진 판단 적용은 이력을 초기화하되 진행 중 task를 재실행하지 않는다.
7. **회수 안전:** 영속 레지스트리에는 runner의 살아 있는 자식 핸들이 없으므로 pgid=pid인 전용 그룹과 PID 시작 시각을 확인한다. 시작 시각 미확인·불일치·신호 실패는 CLEANUP_FAILED다. 이미 사라진 그룹은 기존 커널 ESRCH 판정으로 제거한다. brain은 회수하지 않으며, brain과 같은 그룹도 회수하지 않는다. 성공 조건의 '레지스트리 0'은 보호 brain을 제외한 전체 non-brain 0이다. 다른 task의 잔존을 발견해도 그 프로세스를 임의로 종료하지 않는다.
8. **판단 승인·해석:** 새 승인 필수 메타데이터, configured requiresApproval 이름, 승인·결제·배포·약관 등 보수적 문맥 감지를 사용한다. read --answered와 apply에 같은 조건을 적용한다. 자유 서술은 추론으로 의미를 바꾸지 않고 '사용자 지시: 원문'으로 기록한다. 번호+조건은 완료 해석과 task 비고에 남긴다. 실제 코드 커밋을 생성하거나 확인하지 않으므로 반영 커밋 칸에는 **'판단 적용; 코드 커밋 없음'**이라고 명시한다. 가짜 SHA를 만들지 않는다.
9. **재질문 연결:** 기존 A번호 발급 규칙을 유지해 다음 고유 A번호를 만들고 재질문 원본/후속 질문으로 연결한다. 이전 모호한 원문은 열린 문서에 이력을 보존하되 다시 적용하거나 재질문을 중복 생성하지 않는다. 후속 답이 확정되면 원 판단 때문에 blocked인 task도 해제한다. 다른 열린 판단이 같은 task를 막으면 차단을 유지한다.
10. **증거 무효화:** review.commit이 바뀌면 기존 high를 무효화한다. `--spec-rev`가 증가하면 repair=0 및 기존 검증·검수·병합·문서·정리 증거를 초기화한다. 일반적인 제목·순서·의존 편집과 RECLAIM에서는 부가 증거를 보존한다. 삭제한 task ID는 영속 usedIds 때문에 재사용할 수 없다.
11. **정리 보고:** report는 비파괴 레지스트리 보고이며 OS 전체 프로세스 부재의 증명이 아니다. protected brain을 별도로 표시한다. CLI --cleanup-ok는 non-brain 잔존이 있으면 거부한다. 실제 파일 정리·캐시 삭제·그룹 밖 자손 탐색은 P4에 남겼다.

의도적 적용 예외는 위 프로젝트 REVIEW task 가드, 정체 중단 내부 경로, 자원 중단 우선순위, 보호 brain 제외, 코드 커밋 없는 판단 적용 표기다. P2~P5 기능을 구현한 것으로 보고하지 않는다.

## 실행 제약 준수와 남은 실기

- git 명령은 status/diff를 포함해 실행하지 않았다. 커밋·push도 하지 않았다.
- 실제 claude·cswap·codex는 실행하지 않았다. 테스트의 실행 경로는 `test/fake-claude` 및 실제 `bin/fodh`로 한정했다.
