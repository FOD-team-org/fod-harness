## A16-1 (중간) — `agent_end` 의 유휴 검사 (`extensions/orchestrator/resume.ts:57-59`)

1. `resumeContext(ctx)` 를 만들 때 `idleAtStart = ctx.isIdle?.() ?? true` 를 저장한다. `agent_end` 분기는 `pending-input` 을 먼저 보고, 그다음 `idleAtStart && ctx.isIdle?.() === false` 이면 `busy` 로 끝낸다. 0.87.1 에서는 `idleAtStart` 가 늘 false 이므로 지금 동작 그대로다.
2. `test/orchestrator.test.ts:393-404`(M1/L8) 를 호출 순서를 고정한 두 경우로 나눈다: (a) stalled 먼저 → agent_end 는 `busy`, 전송 1회·autoTurns 1; (b) agent_end 먼저 → stalled 는 `busy`, 전송 1회. 같은 파일을 `--maxWorkers=1` 로 5회 반복 실행해 모두 통과함을 결과에 적는다.
3. 검수 참고 R6: "겹친 agent_end" 테스트(`:193-195`)는 `hasPendingMessages` 가 확장 메시지를 센다는 가정을 버리고, isIdle 기반 모형(0.73.1: 보내면 idle=false)으로 바꾼다. `pending-input` 은 사용자 텍스트 큐를 흉내 내는 별도 테스트로 유지.

## A16-2 (중간) — `agent_end` 처리 중 Esc 뒤 followUp 잔류 (`resume.ts:57-59`·`:111-117`, `extensions/orchestrator/index.ts:207-283`)

1. `ResumeContext` 에 `signal: () => ctx.signal` 을 더한다. `agent_end` 분기의 세 검사 지점(`blocked()`) 모두에서 `signal()?.aborted` 이면 `'aborted'` 로 끝내고 전송하지 않는다. 이때 state 에 `userAborted: true` 를 기록하고 autoTurns 를 올리지 않는다(기존 aborted 종료와 같은 의미). 마지막 검사와 `sendMessage` 사이에 await 가 없음을 유지한다.
2. 사용자 입력이 같은 창에 겹치는 경우(검수 A16-2 두 번째 단락)는 이번 범위가 아니다. 결과 문서 "미완" 에 한 줄로 남긴다. 단 `index.ts:284` 의 finally 가 **이번 agent_end 처리 중에 새로 걸린 `userHold`** 를 지우지 않게 한다(진입 시 값과 비교해 달라졌으면 보존).
3. 테스트: 가짜 ctx 의 `signal` 을 abort 한 뒤 agent_end → `sendMessage` 0회, autoTurns 0, `userAborted` true; 핸들러 도중(첫 검사 뒤) abort → 0회; 처리 중 `/hold` 가 걸리면 finally 뒤에도 `userHold` 유지.

## A16-3 (낮음) — 신뢰하지 않은 프로젝트의 컴팩션 설정 (`extensions/provider/compaction.ts:5-10`, `extensions/provider/index.ts:91`, `README.md:22`)

1. `compactionDisabled(root, projectTrusted)` 로 바꾸고 `index.ts` 에서 `ctx.isProjectTrusted?.() ?? true` 를 넘긴다. 신뢰하지 않았으면 전역 설정만 본다.
2. 참고 R3 도 함께: 실효값은 Pi 와 같은 우선순위(전역 → 신뢰된 프로젝트가 덮어씀)로 계산한다. 전역 false + 신뢰 프로젝트 true 이면 켜진 것으로 보고 경고한다. `PI_CODING_AGENT_DIR` 의 앞머리 `~` 는 홈으로 펼친다.
3. README 22행을 "전역 설정 또는 신뢰된 프로젝트 설정의 실효값이 false 이면 경고하지 않는다" 로 고친다.
4. 테스트: 프로젝트만 false + 비신뢰 → 경고; 같은 설정 + 신뢰 → 경고 없음; 전역 false + 신뢰 프로젝트 true → 경고; `~` 경로.

provider 의 `waitForShutdown` 이 상한(5000ms)에 걸리면 `getCurrentBrainGroup()` 이 있으면 그 그룹에 SIGKILL 을 동기로 보내고 `.pi/harness-brain-orphan.json` 표지(`signal: 'shutdown-timeout'`)를 쓴다. 테스트 1건(끝나지 않는 가짜 스트림 + 가짜 그룹 → kill 호출·표지).

## F34 (중간, 라이브) — 두뇌가 판단 없이 RECLAIM 에 들어가 멈춘다

재현(`docs/검수/2026-09-25-A16-라이브-확인.md`): SPEC/T01 에서 haiku 두뇌가 `fodh state transition RECLAIM --task T01` 을 직접 실행해 판단 없이 RECLAIM 에 들어갔고, `fodh reclaim` 은 "task를 막는 열린 판단 번호가 필요합니다" 로 실패했다. 두뇌는 `대기: 사용자` 로 끝냈고 하네스는 이를 받았다(RECLAIM 은 F28 대상 상태가 아니다). RECLAIM 의 정식 입구는 `fodh reclaim --task --judgment` 와 `fodh judgment add --blocks <T> --reclaim` 뿐이다(`src/core/reclaim.ts`).

1. CLI `fodh state transition RECLAIM` 은 거부한다: `RECLAIM 은 fodh judgment add --blocks <task> --reclaim 또는 fodh reclaim --task <task> --judgment <A번호> 로만 들어간다`. `reclaimTask` 내부의 `transitionState(root, 'RECLAIM')` 는 영향 없음. 사용자 터미널(`assertNotBrain` 통과)에서도 같은 거부가 맞는지 확인하고, 사용자에게 다른 복구 경로가 필요하면 결과 문서에 적는다.
2. 오케스트레이터 `agent_end`: 상태가 RECLAIM 이고 두뇌가 `대기: 사용자` 로 끝나면(사용자 입력 턴의 M2 수락 조건은 기존대로 우선) 받지 않는다. 현재 task 를 막는 열린 판단이 있으면 재개 접두 `[RECLAIM 에서는 기다리지 않는다. fodh reclaim --task <T> --judgment <A> 를 실행하라]`, 없으면 `[RECLAIM 에서는 기다리지 않는다. fodh judgment add --blocks <T> --reclaim 으로 판단을 등록하라]`. 원장 `turn:user-wait-rejected`(evidence `{ state: 'RECLAIM', taskId, judgment }`), 정체 안전망 3턴 유지. `pendingReclaim` 이 있으면(회수 재시도) 안내에 같은 판단 번호를 쓴다.
3. `templates/prompts/` 의 RECLAIM 안내가 있으면 같은 문구로 맞추고, 없으면 task 상태 템플릿 공통 문구에 "판단이 필요하면 `fodh judgment add --blocks <T> --reclaim` 한 번으로 등록·회수한다. `state transition RECLAIM` 은 쓰지 않는다" 를 넣는다.
4. 테스트: CLI 거부(두뇌·사용자), RECLAIM + 판단 있음 + `대기: 사용자` → 거부·안내에 A번호, 판단 없음 → `--reclaim` 안내, 3회 반복 → 기존 안전망.
