## (a) K2·K3 — Pi 종료 신호 처리기 (`src/provider/shutdown.ts`, `extensions/provider/index.ts`, `README.md`)

배경:
- Pi 0.73.1 `interactive-mode.js` 의 `registerSignalHandlers()`(`init()` 안, 확장 로드 뒤)는 SIGTERM·SIGHUP 처리기를 `process.prependListener` 로 맨 앞에 넣는다.
- SIGHUP 처리기는 `emergencyTerminalExit()` 로 동기 종료한다.
- 확장 로드 때 설치한 fodh 처리기는 그래서 두 번째가 된다. `session_start` 의 재설치(`extensions/provider/index.ts:64-65`)가 fodh 처리기를 다시 맨 앞으로 올리기 때문에 지금은 동작한다.
- 이 순서를 지키는 테스트가 없다. Pi 0.87.1 갱신(A16)에서 순서가 바뀌면 조용히 깨진다.
- SIGINT 는 처리하지 않는다. Pi 는 Ctrl+Z 로 멈춘 동안에만 SIGINT 무시 처리기를 단다(`interactive-mode.js:2703`). 그래서 외부 `kill -INT <pi>` 는 Pi 를 기본 동작으로 죽이고 두뇌는 다음 session_start 까지 고아로 남는다.

1. **K2 순서 테스트(단위).** `test/p7-brain-lifecycle.test.ts` 또는 provider 테스트에 넣는다.
   - 가짜 `pi` 로 provider 확장을 로드한다.
   - Pi 방식 처리기를 `process.prependListener('SIGHUP'|'SIGTERM', piHandler)` 로 넣는다.
   - provider `session_start` 처리기를 호출한다. 임시 루트, `ctx.model` 없음으로 doctor 를 건너뛴다.
   - `process.rawListeners(signal)[0]` 이 fodh 처리기인지 확인한다. 식별은 `shutdown.ts` 가 export 하는 표식(Symbol 속성 등)으로 한다.
   - 끝나면 `session_shutdown` 과 `process.off` 로 처리기를 모두 걷어 다른 테스트에 새지 않게 한다.
2. **K2 순서 테스트(실제 프로세스).** 기존 `F30 실제 Node SIGHUP` 테스트 옆에 실제 순서를 재현하는 케이스를 추가한다.
   - 순서: 설치(확장 로드) → `process.prependListener('SIGHUP', () => process.exit(129))`(Pi init) → 제거 후 재설치(session_start).
   - SIGHUP 을 보낸다. 두뇌 그룹이 죽고, exit 129 이고, orphan 파일이 남아야 한다.
   - 대조 케이스: 재설치를 빼면 Pi 처리기가 먼저 돌아 두뇌 그룹이 살아남는다. 테스트가 순서 변화를 실제로 잡는다는 증거이며, 테스트는 남은 그룹을 정리한다.
3. **K2 자가 교정.** `shutdown.ts` 에 `ensureShutdownReclaimFirst(): string[]` 를 둔다.
   - 설치된 fodh 처리기가 각 신호의 첫 처리기가 아니면 맨 앞으로 옮기고, 옮긴 신호 목록을 돌려준다.
   - provider `streamSimple` 에서 두뇌 턴을 시작하기 직전(`streamClaude` 호출 전)에 부른다.
   - 옮긴 신호가 있으면 원장 `shutdown:reorder`(evidence `{ signals }`)를 남긴다. 같은 Pi 프로세스에서 신호별 1회만 남긴다.
   - Pi 버전이 바뀌어 `registerSignalHandlers` 가 session_start 뒤에 불려도 첫 두뇌 턴 전에 순서가 복구된다.
4. **K3 SIGINT.** 같은 회수 처리기를 SIGINT 에도 설치한다.
   - SIGINT 가 왔을 때 fodh 것 말고 다른 SIGINT 처리기가 없으면 SIGHUP 과 똑같이 처리한다.
     - 두뇌 그룹에 TERM→KILL 을 보낸다.
     - orphan 파일 `{ pgid, signal: 'SIGINT', at }` 를 쓴다.
     - 자기 처리기를 모두 걷고 SIGINT 를 다시 보내 기본 종료(signal SIGINT)로 간다.
     - 두뇌가 없어도 다시 보내서 기존 기본 종료 동작을 지킨다.
   - 다른 SIGINT 처리기가 있으면 아무것도 하지 않고 처리기를 유지한다. Pi 가 Ctrl+Z 로 멈춘 동안의 무시 처리기가 이 경우다. 이때 두뇌를 죽이지 않고 파일도 쓰지 않는다.
   - SIGINT 처리기는 `once` 가 아니라 직접 걷는 방식이어도 된다. 반환하는 해제 함수는 세 신호 모두 걷는다.
5. **테스트(실제 프로세스, 두뇌는 `sleep` 그룹).**
   - 다른 처리기 없음 + `kill -INT` → 그룹 사망, orphan `signal: 'SIGINT'`, `child.signalCode === 'SIGINT'`.
   - `process.on('SIGINT', () => {})` 선등록(멈춤 모사) + `kill -INT` → 300ms 뒤 자식·그룹 생존, orphan 파일 없음. 이어 SIGTERM → 그룹 사망·파일 생성(처리기가 살아 있음 확인).
   - `ensureShutdownReclaimFirst` 가 뒤로 밀린 처리기를 앞으로 옮기고 원장을 1회만 남기는지 확인.
6. **주석·문서.**
   - `shutdown.ts` 4행 주석을 실제 동작(SIGHUP·SIGTERM·SIGINT, 멈춤 중 SIGINT 예외)으로 고친다.
   - 22-23행에 Pi `registerSignalHandlers` 순서와 재설치·자가 교정 이유를 적는다.
   - README 155행 "Pi 종료와 고아 두뇌" 를 바꾼다.
     - "SIGINT는 Pi 기존 처리에 맡긴다" 를 "SIGINT 도 같은 방식으로 회수한다(Pi 가 Ctrl+Z 로 멈춘 동안은 제외)" 로 바꾼다.
     - 처리기 순서 자가 교정 한 문장을 넣는다.

## (f) F31 — 두뇌의 판단 중복 등록 억제 + `fodh` 출력 원문 읽기 (`src/cli/index.ts`, `src/core/judgment.ts`, 템플릿)

배경:
- 토이 T04~T07 에서 haiku 두뇌가 `fodh worktree commit T07` 을 `-m` 없이 실행했다.
- 출력은 `2>&1 | jq '.message // .commitSha'` 로 가공해 읽었다. CLI 오류 `{"error":"커밋 메시지 -m이 필요합니다"}` 가 `null` 로 가려졌다.
- 두뇌는 없는 "git 권한 문제" 를 상상해 같은 원인의 판단을 task 마다 따로 등록했다(토이 A19 T04, A20 T05, A21 T03, A22 T06).
- 지금 dedupe 키는 `[title, blocks]` 전체라서 제목이나 task 가 조금만 달라도 새 항목이 된다.

아래 억제는 **CLI `fodh judgment add` 경로에만** 적용한다. 두뇌가 쓰는 입구이기 때문이다. 하네스 내부 등록(정체 안전망, PICK 고아 판단, 재질문)은 지금 그대로 둔다.

1. **같은 task 중복.** `--blocks T<n>`(단일 task)일 때, 답이 빈 열린 판단 중 `막힌 작업` 에 그 task 가 이미 있으면 새로 만들지 않는다.
   - 결과: `{ item: <기존>, deduped: 'same-task' }`.
   - `--reclaim` 이면 기존 id 로 `reclaimTask` 한다. 아니면 task 를 `blocked(<기존 id>)` 로 둔다.
   - 원장 `judgment:dedupe`(evidence `{ taskId, existing, title }`).
2. **비슷한 제목 확인.** 새 제목과 답이 빈 열린 판단 제목을 비교한다.
   - 토큰화: 소문자로 바꾸고, 글자·숫자가 아닌 문자로 나누고, `T\d+`·`A\d+` 와 길이 1 토큰을 뺀다.
   - 겹침 계수 = |교집합| / min(|A|,|B|).
   - 두 집합이 모두 2개 이상이고 겹침 계수가 0.6 이상이면 만들지 않는다. exit 1 과 함께 다음 오류를 낸다.
     - `비슷한 열린 판단 A21(<제목>)이 있습니다. 같은 원인이면 --same-as A21 로 이 task 를 붙이고, 다른 원인이면 --distinct 를 붙여 다시 등록하라`
   - 토이 A19~A22 제목 네 개로 테스트한다. A20→A19, A21→A20, A22→A19 가 모두 걸려야 한다. 서로 다른 주제 쌍 두 개는 통과해야 한다(예: `T05 검증 실패` / `T03 설정 결정`).
3. **`--same-as A<n>`.** 기존 열린 판단(답이 빈 항목)에 task 를 붙인다.
   - `--blocks T<n>`(단일 task)만 필요하다. title·background·options·recommend 는 필요 없다.
   - 판단 파일의 `- 막힌 작업:` 줄에 taskId 를 `, ` 로 덧붙인다. 중복은 넣지 않는다.
   - 파일 쓰기는 `addJudgment` 와 같은 잠금·저장 경로(expectedHash)를 쓴다. 워처가 이것을 사용자 변경으로 보지 않아야 한다.
   - `questionHash` 에 blocks 가 들어가므로, 워처의 질문 해시 기록(`harness-watcher.json` `judgment.questions`)을 같은 잠금 안에서 갱신한다. 사용자의 질문 수정(rev 증가)으로 보이면 안 된다.
   - task 는 `blocked(A<n>)` 로 둔다. `--reclaim` 이면 `reclaimTask(root, task, 'A<n>')`.
   - 원장 `judgment:attach`(evidence `{ taskId, judgment }`).
   - 대상이 없거나, 답이 이미 있거나, 완료 task 면 오류.
   - 사용자가 A<n> 에 답하면 기존 apply 경로가 `blocked(A<n>)` 인 모든 task 를 푼다. 붙인 두 task 가 함께 풀리는 테스트 1건.
4. **`--distinct`.** 2 의 유사도 확인만 건너뛴다. 1 의 같은 task 중복은 그대로 적용한다.
5. **템플릿·규칙 문구.**
   - `templates/brain-rules.md` 에 한 줄: "`fodh` 출력은 파이프(`| jq`, `| head`, `2>/dev/null` 등)로 가공하지 말고 그대로 읽는다. JSON 에 `error` 키가 있으면 그 문구가 원인이며, 원인을 추측해 판단을 만들지 않는다."
   - `templates/prompts/VERIFY.md` 1행에 추가: "`-m` 은 반드시 붙인다. 실패하면 출력의 `error` 를 그대로 읽는다."
   - VERIFY 의 판단 등록 안내에 "같은 원인의 열린 판단이 있으면 `--same-as A<n> --blocks {{taskId}}`" 를 추가한다.
   - IMPLEMENT·FIX 템플릿의 판단 등록 줄에도 `--same-as` 한 줄을 넣는다.
6. **테스트.** CLI 수준으로 한다.
   - 같은 task 두 번 → 1개, `deduped`.
   - 비슷한 제목 → exit 1 + 문구.
   - `--distinct` → 생성.
   - `--same-as` → 막힌 작업 줄 갱신 + task blocked + 워처가 사용자 변경으로 보지 않음(질문 rev 그대로).
   - 답이 있는 대상에 `--same-as` → 오류.
   - 내부 경로(`addJudgment` 직접 호출)는 영향 없음.
   - 템플릿 문구.

## A14 — 두뇌 모델 허용 목록 (`src/core/config.ts`, `src/provider/turn.ts`, `extensions/provider/index.ts`, `src/cli/doctor.ts`, `README.md`)

2. **설정 `brain.model`.**
   - 기본값을 `"claude-fable-5-1"` 로 바꾼다.
   - 값은 `allowedModels` 의 항목과 정확히 같아야 한다. 아니면 설정 오류를 낸다.
     - `brain.model(<값>)이 brain.allowedModels(<목록>)에 없습니다. 사용자 터미널에서 fodh config set brain.allowedModels '[…]' --approve 로 목록을 바꾸세요`
   - 기존 별칭 호환: 읽을 때 `fable` 은 `claude-fable-5-1`, `opus` 는 `claude-opus-5-5` 로 해석한다. 그 ID 가 목록에 있을 때만이다. `sonnet`·`haiku` 같은 다른 별칭은 목록에 직접 넣어야 쓸 수 있다(토이·시험용).
   - 해석한 값은 `loadConfig` 결과에만 반영한다. 파일은 다시 쓰지 않는다.
3. **실제 모델 대조(`src/provider/turn.ts`).** `system.init` 의 `event.model` 이 요청 모델과 맞고(`matchesModel`) 동시에 `allowedModels` 중 하나와 맞아야 한다.
   - `matchesModel(entry, actual)` 규칙을 넓힌다.
     - `actual` 끝의 `[...]` 접미(예: `[1m]`)는 떼고 비교한다.
     - `claude-` 로 시작하는 항목: 정확히 같거나, `actual` 이 `entry-` + 숫자(날짜 접미)다.
     - 별칭 항목: 지금 규칙.
   - 어긋나면 지금처럼 `configError` 로 분류한다. 원장 `brain:model-rejected`(evidence `{ requested, actual, allowed }`)를 남긴다.
   - doctor 턴(`haiku`, `--max-turns 3`, 프로젝트 작업 없음)은 이 대조에서 뺀다. 요청 모델과의 대조만 유지한다. README 에 "doctor 는 훅 시험용 haiku 로 돌며 두뇌 규칙과 무관" 을 적는다.
4. **Pi 모델 목록(`extensions/provider/index.ts:31-32`).**
   - 고정 `['fable','opus','sonnet','haiku']` 대신 확장 로드 때 `process.cwd()/.pi/harness.json` 을 동기로 읽어 `allowedModels` 로 등록한다. id 는 항목 그대로다.
   - 읽기나 검증에 실패하면 기본 목록으로 등록한다. 첫 `session_start` 에서 경고 알림 1회를 낸다.
   - `model_select` 의 `setConfig('brain.model', id)` 가 실패하면(목록 밖) 예외를 올리지 않는다. 오류 알림 뒤 두뇌 도구 선택을 끈 상태로 둔다.
5. **doctor.** 결과에 `brainModel`(설정값)과 `allowedModels` 를 넣는다. 상태 `brain.model` 은 지금처럼 기록한다.
6. **README "모델 배치와 교체" 절을 다시 쓴다.**
   - 두뇌는 허용 목록 안에서만 고른다. 기본 목록은 Opus 5.5·Fable 5.1, 기본값은 Fable 5.1 이다.
   - 새 모델이 나오면 아래 두 명령을 쓰고 Pi 를 다시 시작한다(Pi `/model` 목록은 시작할 때 만들어진다).
     ```
     fodh config set brain.allowedModels '["claude-opus-6","claude-fable-5-1"]' --approve
     fodh config set brain.model claude-opus-6
     ```
   - 토이·시험에서 haiku 를 쓰려면 목록에 `"haiku"` 를 넣는다.
   - "프로바이더 모델 목록은 fable, opus, sonnet, haiku 순서" 문장을 지운다.
7. **테스트.**
   - 기본 설정 → model `claude-fable-5-1`, 목록 2개.
   - 목록 밖 model → 오류 문구.
   - `fable`/`opus` 별칭 해석.
   - `haiku` 가 목록에 없으면 오류이고, 있으면 허용.
   - `allowedModels` 설정은 `--approve` 없이 거부.
