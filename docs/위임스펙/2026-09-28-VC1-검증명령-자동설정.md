## 3. 변경

### 3-1. `verify.ts` 셸 실행 (D1)

- `commandParts(cmd)` 대신 `spawn('/bin/sh', ['-c', cmd], { cwd, detached: true, stdio: ['ignore', fd, fd] })`.
- 프로세스 그룹·타임아웃·잔존 회수·`registerProc`(cmd 는 지금처럼 redact 후 200자)·RSS 측정은 그대로. 그룹 리더가 sh 가 되는 것만 다르다.
- `config.ts:176` 의 `commandParts` 검증(따옴표 닫힘)은 남겨도 된다.
- 테스트
  - `cd sub && node -e "<표지 파일 쓰기>"` 가 실제로 표지를 만든다(= 거짓 통과 회귀 방지). 기대 exit 0.
  - `false && true` → exit 1, ok=false. `exit 3` → exit 3. `echo x | grep y` → exit 1.
  - 타임아웃: `sleep 30` 을 sh 아래에서 → 시간 초과 시 손자까지 회수, residual=false.
  - 기존 verify 테스트(따옴표 인자 등)는 단언을 바꾸지 않고 통과해야 한다. 바꿔야 하면 결과 문서에 전·후를 적는다.

### 3-2. 프리셋 감지 `src/core/verify-detect.ts` (D2)

`detectVerify(base: string, options?: { platform?: NodeJS.Platform; skipPrefixes?: string[] })`
→ `{ stacks: { stack: string; dir: string; notes: string[] }[]; commands: string[]; heavy: string[] } | undefined`

- 파일 시스템만 본다. 명령을 실행하지 않는다.
- 탐색: `base` 자신, 그 아래 깊이 2 까지의 디렉터리.
  - 건너뜀: `.` 으로 시작하는 이름, `node_modules`, `build`, `dist`, `out`, `target`, `Pods`, `vendor`, `coverage`, 심링크, `skipPrefixes`(워크트리 prefix)로 시작하는 이름.
  - 한 디렉터리에서 스택을 찾으면 그 아래로 내려가지 않는다(Flutter 의 `android/`·`ios/` 하위 프로젝트 오인 방지).
  - 한 디렉터리는 아래 표의 우선순위 첫 스택 하나만 쓴다.
  - 여러 디렉터리에서 찾으면 전부 쓴다. 순서는 `dir` 경로 순(루트 `''` 먼저).
- 명령 접두: `dir` 이 `''` 이면 그대로, 아니면 `cd '<dir>' && <cmd>`(작은따옴표 셸 인용, 이름 속 `'` 는 `'\''`).

| 순위 | 스택 | 감지 | commands | heavy |
|---|---|---|---|---|
| 1 | flutter | `pubspec.yaml` 에 `sdk: flutter` 줄 | `flutter pub get` · analyze · `flutter test`(`test/` 아래 `*_test.dart` 가 있을 때만) | `ios/` 이고 darwin → `flutter build ios --debug --no-codesign`; `android/` → `flutter build apk --debug`; `web/` → `flutter build web` |
| 2 | dart | `pubspec.yaml`(flutter 아님) | `dart pub get` · `dart analyze` · `dart test`(테스트 파일 있을 때) | 없음 |
| 3 | node | `package.json` 에 `typecheck`·`lint`·`test` 스크립트 중 하나 이상 | 있는 것만 그 순서로 `<pm> run typecheck`, `<pm> run lint`, `<pm> test`. npm 기본 자리표시(`echo "Error: no test specified" && exit 1`)인 test 는 뺀다 | `build` 스크립트 → `<pm> run build` |
| 4 | go | `go.mod` | `go vet ./...` · `go test ./...` | `go build ./...` |
| 5 | rust | `Cargo.toml` | `cargo check` · `cargo test` | `cargo build --release` |
| 6 | swift | `Package.swift` | `swift build` · `swift test`(`Tests/` 있을 때) | 없음 |
| 7 | python | `pyproject.toml`·`setup.py`·`requirements.txt` 중 하나 + (`tests/`·`test/`·`pytest.ini`·pyproject 의 `[tool.pytest` 중 하나) | `python3 -m pytest -q` | 없음 |
| 8 | gradle | `gradlew` 파일 | `./gradlew test` | `./gradlew build` |

- flutter analyze: 감지한 디렉터리의 realpath 에 비ASCII 문자가 있으면 `dart analyze`, 아니면 `flutter analyze`. 비ASCII 일 때 notes 에 `flutter analyze 비ASCII 경로 오류 회피` 를 남긴다.
- node `<pm>`: `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lock`·`bun.lockb` → bun, 그 밖 → npm. test 는 `npm test`·`pnpm test`·`yarn test`·`bun run test`. 설치 명령은 넣지 않는다(워크트리 node_modules 링크를 깨지 않게).
- 아무것도 없으면 `undefined`.
- 테스트: 임시 디렉터리에 스택별 최소 파일을 만들어 표의 각 행, 하위 폴더 접두(공백·작은따옴표 이름 포함), 깊이 2 제한, 건너뜀 목록, Flutter 하위 `android/` 에 `gradlew` 가 있어도 gradle 로 안 잡힘, 비ASCII 경로 → `dart analyze`, platform `linux` 면 ios 빌드 없음, npm 자리표시 test 제외, 여러 스택 순서.

### 3-3. 자동 채움 (D3·D4)

- `config.ts` 에 내부 기록기 `writeAutoVerify(root, target, detected)` 를 둔다.
  - `target` = 단일 레포면 `verify`, 워크스페이스 멤버면 `workspace.repos.<name>.verify`.
  - `setConfig` 를 거치지 않는다(두뇌 거부 `assertNotBrain` 없음). 값은 `detectVerify` 결과만 받는다. 문자열 인자를 받는 공개 경로를 만들지 않는다.
  - 기존 `timeoutMinutes` 는 보존. 기존 heavy 가 비어 있지 않고 표지가 없으면(사용자 값) heavy 는 보존한다.
  - `auto = { at, stacks: ['flutter:app', …], hash }`. hash = `sha256(JSON.stringify({ commands, heavy }))`(실제로 쓴 값).
  - 파일 잠금 + `loadConfig(…, { dryRun: true })` 검증 + `atomicWrite`(setConfig 와 같은 방식).
  - `loadConfig` 가 `verify.auto` 를 알 수 없는 키로 경고하지 않게 한다(타입에도 선택 필드로 추가). 형식이 틀리면(객체 아님 등) 오류.
- `runVerify`
  - 단일 레포이고 `config.verify.commands` 가 비었으면: `detectVerify(realpath(taskPath), { skipPrefixes: [config.worktrees.prefix] })`.
    - 기준은 `options.cwd` 가 아니라 task 워크트리 루트(없으면 프로젝트 루트)다.
    - 찾으면 `writeAutoVerify` → 원장 `verify:auto-config`(ok, evidence `{ base, stacks, commands, heavy }`, 명령은 redact) → 알림(info, 제목 `검증 명령 자동 설정`, 본문 `<스택> → <명령 ' · ' 연결>`) → `generateClaudeMd(root)` 는 best-effort(실패는 원장 경고만) → 새 설정으로 이어서 실행.
    - 못 찾으면 지금처럼 `finish({ ok: false, error })`. error: `verify.commands 가 비어 있고 자동 감지된 스택이 없습니다(지원: flutter·dart·node·go·rust·swift·python·gradle) — 사용자가 harness.json verify.commands 를 설정해야 합니다`.
  - 워크스페이스 멤버: 멤버 verify 가 정확히 `['git diff --check']` 이고 그 멤버에 `verify.auto` 표지가 있을 때만(하네스가 넣은 자리표시) 멤버 task 워크트리에서 감지해 교체한다. 표지 없는 기존 멤버는 건드리지 않는다.
- heavy 비어 있음(D8): `--heavy` 인데 heavy 가 비면 `finish` 를 부르지 **않는다**(state.verify 를 덮지 않는다). `{ ok: false, skipped: 'heavy-empty', error: 'verify.heavy 가 비어 있어 heavy 검증을 건너뜁니다(상태 변경 없음)' }` 를 돌려준다.
  - 이유: 지금은 일반 검증 성공 뒤 `--heavy` 가 빈 heavy 로 `state.verify.ok=false` 를 써서 REVIEW 게이트가 막힌다.
- 테스트
  - 비어 있는 설정 + Flutter 모양 워크트리(가짜 `flutter` 실행 파일을 PATH 앞에 둔 스텁) → 설정이 써지고, 같은 호출에서 명령이 실행되고, 원장·표지·hash 가 맞다.
  - `FODH_BRAIN=1` 에서도 자동 채움이 된다. 같은 환경에서 `fodh config set verify.commands …` 는 여전히 거부된다.
  - 사용자 설정이 있으면 감지하지 않는다.
  - 감지 실패 → 기존처럼 ok=false + 새 error 문구.
  - 일반 성공 뒤 빈 heavy 로 `--heavy` → state.verify 가 성공 그대로.
  - 워크스페이스: 표지 있는 `git diff --check` 멤버는 교체, 표지 없는 멤버는 그대로.

### 3-4. `fodh verify detect` (D5)

- `fodh verify detect [--cwd <dir>] [--apply] [--approve] [--repo <멤버>]`.
- 기준 폴더: `--cwd`(verify 와 같은 경계 검사: 루트 또는 등록 워크트리 안) 또는 현재 task 워크트리, 없으면 루트. 워크스페이스는 task 멤버(또는 `--repo`).
- `--apply` 없으면 `{ base, detected, current: { commands, heavy, auto? }, userSet }` 만 출력. 어느 상태에서나 허용.
- `--apply`
  - 허용: 현재 commands 가 비었거나, `auto` 표지 hash 가 현재 `{commands, heavy}` 와 같을 때. 두뇌도 허용.
  - 그 밖: `사용자가 설정한 검증 명령입니다 — harness.json 을 직접 고치거나 사용자 터미널에서 --approve 로 교체하세요`. `--approve` 는 두뇌면 무시하고 거부(기존 approve 규칙과 같게).
  - 감지 결과가 없으면 쓰지 않고 오류.
  - 원장 `verify:auto-config`(evidence 에 `via: 'detect'`).
- CLAUDE.md 명령 표(`claude-md.ts` 의 VERIFY 행)에 `fodh verify detect` 를 덧붙인다. 훅이 두뇌의 이 명령을 막지 않는지 확인하고 테스트한다.

### 3-5. `fodh init`·`fodh workspace add` (D6)

- `initProject`(단일 레포, dryRun 아님): `existingCode` 이고 새로 만든 `harness.json` 이면 루트에서 감지해 `writeAutoVerify`. 결과에 `verifyDetected: { stacks, commands, heavy } | null` 을 더한다. 이미 있던 `harness.json` 은 건드리지 않는다. dryRun 이면 감지 결과만 보여 준다.
- `workspace.ts:103` 기본 멤버: 멤버 경로에서 감지해 찾으면 프리셋 + 표지, 못 찾으면 지금처럼 `['git diff --check']` + 표지(자리표시임을 표시). `workspace init` 도 같은 기본값 함수를 쓰면 같이 바뀐다.
- README 313행의 "실제 검증 명령은 사용자가 직접 설정" 문장을 자동 감지 기준으로 고친다.

### 3-6. 두뇌 지시 (D7)

- `templates/prompts/VERIFY.md`
  - 4단계를 바꾼다: "`fodh verify run` 은 verify.commands 가 비어 있으면 스택을 감지해 설정을 채우고 이어서 실행한다(원장 `verify:auto-config`). 검증 설정 때문에 판단을 올리지 않는다. 오류가 `자동 감지된 스택이 없습니다` 일 때만 `fodh judgment add …` 로 설정을 요청한다. heavy 가 비어 있다는 건너뜀 응답은 판단 사유가 아니다."
  - 한 줄 추가: "명령은 셸(`/bin/sh -c`)로 task 워크트리 루트에서 실행된다. 하위 폴더 명령은 설정에 `cd <폴더> && …` 로 들어 있다."
  - 자동 설정(표지 있음)의 명령이 도구·환경 문제로 실패하고 감지 결과가 달라질 여지가 있으면 `fodh verify detect --apply` 를 먼저 쓴다. 사용자 설정이면 지금처럼 판단.
- `templates/brain-rules.md` 20행 근처와 `skills/fodh-workflow/SKILL.md` VERIFY 설명에 같은 요지 한 줄.
- 이 템플릿을 바이트 비교하는 골든·스냅숏 테스트가 있으면 결과 문서에 적는다(골든 파일은 고치지 말 것).

### 3-7. 복수 번호 답·재질문 상한 (D9) — `judgment.ts`

- `classifyAnswer` 에 선택 인자 `{ allowMulti?: boolean }` 를 더한다(기존 호출 기본 false → 동작 그대로).
  - `allowMulti` 이고 번호가 2개 이상이고 부정·유보 정규식에 안 걸리고 모든 번호가 선택지 범위 안이면: `{ kind: 'freeform', applicable: true, selections: [중복 제거·등장 순], interpretation: '복수 선택: <선택지 a>, <선택지 b>; 원문: <답>' }`.
  - 범위를 벗어난 번호가 있으면 지금처럼 `ambiguous`.
- `classifyItemAnswer` 는 `allowMulti = !requiresApproval && !item.resolution` 으로 부른다.
- 재질문 상한: `applyJudgments` 에서 분류가 `ambiguous` 이고, 항목이 이미 재질문(`item.reaskOf`)이며, 승인 필수·resolution 이 아니면 새 재질문 대신 `interpretation = '사용자 지시(재질문 뒤 자유 서술): <답>'` 으로 적용한다.
- 모든 재질문 배경 끝에 형식 안내를 붙인다: `번호 하나만 쓰세요(예: 2). 조건은 번호 뒤에(예: 2 iOS 먼저).`
- watcher 의 자유 서술 안정 대기(`freeTextStableSeconds`)는 복수 선택 자유 서술에도 그대로 걸린다(바꾸지 않음).
- 테스트
  - 실제 답 `2,3 1차 출시땐 무조건 ios 만`, 선택지 `[웹, iOS, Android, 여러 플랫폼, 미정]`: 승인 불필요 → 적용, interpretation 에 iOS·Android 포함, 재질문 없음. 승인 필수 → 지금처럼 재질문.
  - `2,3 1차에선 ios가 먼저 이후 2주 테스트 후에 안드로이드` 도 적용.
  - resolution 항목 복수 번호 → 지금처럼 재질문.
  - 재질문 항목(`재질문 원본` 있음)에 `나중에 정할게` → 새 재질문 없이 자유 서술 적용. 같은 조건의 승인 필수 항목은 재질문.
  - 재질문 배경에 형식 안내가 붙는다.
  - `classifyAnswer` 기존 테스트 단언은 바꾸지 않는다.

## 5. 작업 규칙

- 전체 테스트(`npm test`, 인자 없는 `npx vitest run`)는 **절대** 돌리지 않는다. 관련 파일만 `npx vitest run <파일…>`. 전체는 Claude 가 돌린다.
- `npm run typecheck` 는 돌려도 된다.
- 샌드박스가 `.git` 쓰기와 `/bin/ps` 를 막는다. 커밋·브랜치는 만들지 않는다. 실제 flutter·npm 은 부르지 않는다(스텁 실행 파일로).
- 비밀값을 파일·출력에 쓰지 않는다.
- 새 테스트 파일: `test/vc1-verify-auto.test.ts`(3-1·3-3·3-4·3-5), `test/vc1-verify-detect.test.ts`(3-2), `test/vc1-judgment-multi.test.ts`(3-7).
