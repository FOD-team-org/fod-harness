## N2 (낮음) — 스냅숏 수명 (`src/core/judgment.ts:463-509`, `extensions/orchestrator/index.ts:56`, `src/provider/turn.ts:87`)

1. `beginJudgmentSnapshot`: 적용 잠금 안에서 **기존 스냅숏 파일이 있으면 먼저 `finishJudgmentSnapshot` 과 같은 비교·held 기록을 수행한 뒤**(잔존 턴의 runId 로 `judgment:held`, `endedAt = state.lastEventAt ?? now`) 새 스냅숏을 쓴다. 비교 로직은 내부 함수(`settleSnapshot(root, endedAt)`)로 뽑아 begin·finish·recover 가 공유한다(잠금은 호출자가 잡고 내부 함수는 잠금을 다시 잡지 않는다 — 재진입 불가 잠금 주의).
2. 스냅숏에 `pid: process.pid` 를 기록한다. `recoverJudgmentSnapshot`(session_start·recovering 진입): 스냅숏 `pid` 가 현재 프로세스가 아니면서 살아 있으면(`process.kill(pid, 0)` 성공) 건너뛰고 원장 `judgment:snapshot-skip`(evidence `{ pid }`) 1회; 현재 프로세스이면서 provider 턴이 진행 중이면(`turn.ts` 모듈 수준 `turnInProgress` 표지를 export, 또는 `src/core/state.ts` 대신 `src/provider/turn.ts` 에 `isTurnInProgress()`) 건너뛴다. 그 외(죽은 pid·pid 없음)는 기존대로 정산.
3. `turn.ts:87-88`: `beginJudgmentSnapshot` 을 `try` 안으로 옮기거나 begin 과 `appendLedger` 사이 예외도 `finally` 의 finish 가 처리하도록 순서를 바꾼다(begin 뒤 어떤 경로로 나가도 finish 가 호출되게).
4. finish 가 비교 중 예외를 던지면 runner 결과를 덮지 않도록 `finally` 에서 try/catch 로 감싸 원장 `judgment:snapshot-finish fail`(evidence error) 에 남기고 계속한다(9차 참고 3).
5. 테스트: 잔존 스냅숏(두뇌 답 A1 포함) + begin(doctor) → `judgment:held` A1 + 새 스냅숏; 살아 있는 다른 pid 의 스냅숏 + recover → 스냅숏 유지·`judgment:snapshot-skip`; 죽은 pid → 정산; begin 뒤 예외 → finish 호출·스냅숏 삭제.

4. README 규칙 7 표: "긴 옵션 `--recursive/--archive` 포함, 원본이 디렉터리일 때만 재귀" 로 갱신.

## F29 (낮음) — `Agent`/`Task` 별칭으로 거부 분류가 unknown (`src/provider/turn.ts:96, 215, 231`)

훅 이벤트는 도구 이름을 `Agent` 로, 결과 `permission_denials` 는 `Task` 로 보내 `canonical({tool, input})` 키가 어긋나고 두 번째 항목이 `unknown` → `hook:unclassified warn` 이 남는다(라이브 01:19). 키를 만들 때 `tool` 을 정규화한다(`Task` → `Agent`; 정규화 함수 `canonicalTool(name)` 하나로 세 지점 공유). 테스트: 훅 이벤트 `Agent` + 결과 `Task` 같은 입력 → 분류 유지, `hook:unclassified` 없음.
