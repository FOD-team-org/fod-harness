## 1. 프로세스 회수 (`runCleanup` scope `processes`)

- 대상 = 레지스트리 `.pi/harness-procs.json` 의 레코드 중 `kind !== 'brain'`. `--task T` 가 있으면 그 task 레코드만, 없으면 전부(활성 위임 `state.delegation` 의 감독 레코드는 **제외** — 진행 중 위임을 죽이지 않는다; `--force-delegation` 없음, 위임 취소는 `fodh codex cancel`).
- 보호: `cleanup.processes.neverKill` 패턴이 레코드 `cmd` 에 일치하면 건드리지 않고 `protected` 로 보고. 활성 두뇌(kind `brain`) 동일. `killPatterns` 는 레지스트리 안에서의 추가 필터가 아니라 **보고용 분류**(설계: 시스템 전역 pkill 금지). 
- 절차(레코드마다): pid 재사용 검사(`processStartedAt` vs `startedAt`, `spawn:` 값이면 신호 없이 `unverified` 보고; 리더가 죽었어도 그룹이 살아 있으면 P3 3차 H1(c) 규칙대로 회수) → **P3 3차 F7 의 프로세스 트리 스냅샷**(그룹 구성원 ∪ ppid 자손 폐쇄, ps 자신 pid 제외)을 신호 전에 찍음 → 스냅샷 전체 `SIGTERM` → 5초 → `SIGKILL` → 새 스냅샷 ∪ 이전 스냅샷 생존 여부로 잔존 확인 → 잔존 0 이면 레지스트리 제거. P3 3차가 만든 codex 전용 회수 함수를 kind 에 관계없이 재사용한다(`reclaimOwnedGroup` 은 두뇌 그룹 전용으로 남긴다).
- 결과 `{ reclaimed:[...], protected:[...], unverified:[...], residual:[...] }`. `residual.length > 0` 이면 `ok:false`.
- 원장: `cleanup:processes` `pre` → `ok|fail` evidence 위 요약(pid·kind·taskId 만, cmd 는 200자 절단·redact).
- P3 재검수 이월 항목(`docs/검수/2026-09-24-P3-Claude-재검수.md` N10·N11):
  - **N10** 워처 tick 이 `harness-watcher.json` 잠금을 쥔 채 최대 약 7초 회수를 수행한다. lost 후보 수집만 잠금 안에서 하고, 트리 회수와 `finishRun`(meta 잠금으로 멱등)은 잠금 밖에서, 인박스 방출은 다시 잠금을 잡고 한다. 테스트: 회수 중 다른 잠금 사용자가 10초 안에 실패하지 않는 것.
  - **S1** (`src/core/tool-groups.ts` 표본) 신원 확인용 pid(도구 셸)가 먼저 끝나면 살아 있는 도구 그룹이 회수에서 빠지는데 감독은 `ok` 로 마감한다. 표본 때 그룹 구성원이 바뀌면 살아 있는 다른 구성원으로 신원을 갱신하고, 회수 뒤 잔존 그룹이 있으면 `ok` 대신 원장 `residual` 을 남기며 워치독(§4)이 레지스트리 밖 잔존으로 **보고**한다.
  - **S2** `codex:tool-groups` 회수 실패 원장이 tick 마다 무제한으로 쌓인다 → N3 와 같은 제한(runId 당 첫 1건 + 10분마다 1건).
  - **S3** (`src/core/process-identity.ts`) spawn 직후 ps 실패로 자식 시작 시각이 비면 보존(unknown) 대신 슬롯 해제·신호 없는 lost 로 간다 → `childStartedAt` 이 없으면 `unknown` 으로 보존.
  - **R4** `fodh codex status <runId>` 가 procs 레코드만으로 `slotOwnerAlive` 를 불러 orphan 상태에서 `alive:false` 를 보이고 `fodh slots status` 와 어긋난다(`src/core/codex.ts:137-138`). meta 의 `childPid`·`childStartedAt` 과 `root` 를 함께 넘긴다. 테스트 1건.
  - **R5** ① 30초 표본 사이에 끝난 도구 셸이 남긴 백그라운드 작업(ppid 1)은 `toolGroups` 에 안 잡힌다 → 워치독(§4)이 레지스트리 밖 잔존을 **보고만** 한다(전역 kill 금지). ② 사용자 env 의 `BASH_DEFAULT_TIMEOUT_MS` 가 `waitMinutes` 보다 짧으면 doctor 경고 + `waitMinutes` 자동 하향. ③ `watch.codexLostFailures` 는 run 마감 시 지운다.
  - **N11** 살아 있는 감독을 `fodh codex cancel` 하면 CLI 와 감독이 같은 트리를 동시에 회수해 종료 원장이 2건 남을 수 있다. cancel 은 먼저 감독에만 TERM 을 보내고 최대 7초 동안 meta 마감을 기다린 뒤, 마감되지 않을 때만 트리를 회수한다. `finishRun` 은 원장 기록을 meta 게시 뒤로 옮기고 runId 기준 종료 항목을 한 번만 남긴다. 테스트: 살아 있는 감독 cancel → 원장 종료 1건.

## 2. 저장공간 (scope `storage`)

- 설정 `cleanup.rebuildablePaths`(기본 `[]`), `cleanup.keepPaths`(기본 `[]`), `cleanup.sharedCaches { enabled:false, paths:[] }`, `cleanup.codexRunsKeep`(기본 20).
- 각 `rebuildablePaths` 항목: 프로젝트 루트 기준 상대 경로, glob 없음(P4), `realpath` 후 루트 안이어야 하며 심링크 통과·`..` 거부, `keepPaths` 의 realpath 와 같거나 그 하위면 건너뜀. 삭제 전 `du -sk` 로 크기 기록. `rm -rf` 는 `fs.rm({recursive:true, force:true})` 로(셸 없음).
- `.pi/codex/<runId>/` 정리: `finishedAt` 있는 실행 중 최신 `codexRunsKeep` 개를 제외하고 삭제. 단 `state.delegation` 의 runId 와 `task.codexThread` 가 가리키는 실행의 `meta.json`·`last-message.md` 는 남긴다(events.jsonl·stderr 만 삭제).
- `sharedCaches.enabled` 가 true 여도 P4 에서는 **보고만**(크기·경로) 하고 삭제하지 않는다(결과 문서에 명시; 삭제는 프로젝트 소유 판정 규칙이 확정된 뒤).
- 보고: before/after `df -k /`(사용 %·가용 GB), `vm_stat` free, 스왑 사용 GB, 삭제 목록 `[ { path, sizeKB } ]`.
- 원장 `cleanup:storage`.

## 3. 워크트리 (scope `worktrees`)

- `state.worktrees` 의 각 항목: task 가 `done` 이고 `git -C <path> status --porcelain` 이 비어 있고 `state.delegation` 이 그 task 를 가리키지 않으면 `removeWorktree(root, taskId, false)`(P3, `--force` 없음). 아니면 `kept:[{ taskId, path, reason }]`.
- `--task T` 가 있으면 그 task 만. 원장 `cleanup:worktrees`.

## 4. 메모리 워치독 (`src/core/memory.ts`, 워처)

- `sampleMemory()`: `vm_stat` → free+inactive 페이지×페이지 크기, `sysctl -n vm.swapusage` → `used = N.NNM|G` 파싱, `memory_pressure` 는 호출하지 않는다(느림). 실패 시 `undefined`(감지 없음, 원장 1회).
- 워처 확장 60초 타이머(`unref`)에서 표본을 `harness-watcher.json` `watch.memory = { at, swapUsedGB, freeMB, over:boolean, overSince?, underSince? }` 로 기록.
- `swapUsedGB > cleanup.swapWarnGB`(기본 8) 가 처음 관측되면 인박스 `{ kind:'memory-pressure', swapUsedGB, freeMB }`(중복 키 `overSince`). 계속 초과 5분 → `{ kind:'memory-critical' }`(같은 overSince 로 1회).
- 회복: `swapUsedGB < swapWarnGB - 2` 가 5분 지속 → `{ kind:'memory-recovered' }`(중복 키 `underSince`).
- `fodh memory status` = 현재 표본 + `watch.memory`.

### 4-1. 오케스트레이터 결정

| kind | 결정 |
|---|---|
| `memory-pressure` | `runCleanup(scope:'processes')`(활성 위임·두뇌 제외) → warning 알림 `스왑 N GB — 잔존 프로세스 M개 회수` |
| `memory-critical` | 활동 상태이면 `paused(memory)` 로 전이(`taskId`·`resumeState` 보존, 기존 paused 규칙) + error 알림. `fodh codex` 시작 거부(§0). 인박스는 다음 턴에 전달 |
| `memory-recovered` | 상태가 `paused(memory)` 면 `PICK` 으로 전이(기존 RESUME 경로) + `autoResume`; 아니면 info 알림 |

## 5. 정리 실행 시점

- 5-1. task CLEANUP: `templates/prompts/CLEANUP.md` — `fodh cleanup run --task {{taskId}} --scope all` 실행 → `ok` 면 `--cleanup-ok`. `ok:false` 면 `fodh state transition CLEANUP_FAILED`(기존: 2회째 → `paused(cleanup)`), 그 사이 `fodh cleanup run --task {{taskId}} --scope processes` 1회 재시도.
- 5-2. RECLAIM: `reclaimTask` 가 `runCleanup(scope:'processes', taskId)` 를 쓴다(동작 동일, 보고 형식 통일).
- 5-3. `WAIT_*`·`paused(*)` 진입 직전: 오케스트레이터가 `runCleanup(scope:'processes')` 를 실행(활성 위임 제외)하고 결과를 알림에 한 줄 포함. 워처 `cleanup-due` 는 만들지 않는다(진입 지점이 오케스트레이터 안에 있으므로 직접 호출).
- 5-4. `session_shutdown`: 워처 확장이 `runCleanup(scope:'processes')` — 단 **활성 위임 감독은 제외**(세션이 꺼져도 Codex 는 계속 돌고 다음 세션의 `recover`+`codex-done` 으로 이어진다).
- 5-5. `/cleanup` 명령: `runCleanup(scope:'all')` 후 요약 알림 + 보고서 경로. `--dry-run` 인자 지원(`/cleanup dry`).

## 6. 알림 (`src/core/notify.ts`)

- `notify(root, { key, level:'info'|'warning'|'error', title, body }, ctxLike?)`: (1) 원장 `notify:<key>` 항상 (2) `ctxLike?.notify` 가 있으면 TUI (3) `notify.channels` 에 `macos` 가 있으면 `osascript -e 'display notification "<body>" with title "<title>"'`(execFile, 인자 이스케이프, 200자 절단, redact) — `hasUI === false` 여도 macos 는 보낸다. `slack` 은 §서두대로 skip.
- 속도 제한: 같은 `key` 는 60초에 1회(메모리 `Map`, 확장 프로세스 기준). 초과분은 원장 `notify:<key> skip`.
- 호출 지점(기존 `ctx.ui.notify` 직접 호출을 이 함수로 교체): WAIT_JUDGMENT 진입, `paused(*)` 진입, DONE_ALL, CLEANUP_FAILED·`paused(cleanup)`, codex-done `fail|timeout|lost`, doctor 실패, memory 3종, 두뇌 오류 3회, `stopForJudgment`. 단순 정보 출력(`/status` JSON 등)은 그대로 `ctx.ui.notify`.
- `fodh notify send --title … --body … [--level …]`: 두뇌·사용자용(로컬 알림이므로 승인 불필요; `external-send` 규칙과 무관). 원장 기록.
- 설정 `notify: { channels:['tui','macos'] }` 기본. 값 검증: 문자열 배열, 허용 `tui|macos|slack|ledger`.

## 7. 검증 실행과 배타 슬롯 (`src/core/verify.ts`)

- 설정 `verify: { commands:[], heavy:[] }`(문자열 배열, 각 항목은 `commandParts` 로 분해 가능해야 함, 셸 없음).
- `fodh verify run [--heavy] [--cwd <dir>]`: cwd 기본 = 현재 task 워크트리(없으면 루트), `--cwd` 는 P3 경계 규칙. `--heavy` 없으면 `verify.commands` 를 순서대로, `--heavy` 면 `verify.heavy`. 각 명령: `spawn(detached:true)` + 레지스트리 등록(kind `verify`, taskId) + `maxMs = verify.timeoutMinutes`(기본 30) → 종료 시 레지스트리 제거. stdout/stderr 는 `.pi/verify/<runId>/<n>.log` 에 저장(마지막 4KB 만 결과에 포함, redact).
- `--heavy`: `acquireSlot('heavy', …)` — `codex` 슬롯 점유 중이면 `{ error:'위임 실행 중에는 무거운 검증을 시작할 수 없습니다', owner }`; 실행 중 `codex` 확보 요청은 거부(§0). 종료 시 해제(stale 규칙 동일).
- 표본: 실행 중 30초마다 `ps -o rss= -g <pgid>` 합계(ps 자신 제외) peak + 시작/종료 `sampleMemory()` → 결과 `{ runId, commands:[{ cmd, exit, seconds, tailLog }], peakRssMB, swapBeforeGB, swapAfterGB, ok }` + 원장 `verify:run`.
- 상태 검사: `VERIFY` 또는 `FIX` 상태에서만(그 외 거부). 설정이 비어 있으면 `{ ok:false, error:'verify.commands 가 비어 있습니다' }` — 두뇌는 스펙의 검증 명령을 `fodh verify run` 없이 직접 실행할 수 있다(템플릿에 명시, 단 전체 스위트는 `--heavy` 경로만).
