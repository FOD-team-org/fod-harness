## K1 [낮음] 워크트리별 git 디렉터리 확인(J2 완성)

- 검수 재현: 등록 워크트리의 `.git` 포인터를 프로젝트 밖의 다른 git 디렉터리로 돌리되 `commondir` 은 진짜 공통 디렉터리를 가리키게 만든다.
  - 이러면 공통 디렉터리는 같고 HEAD·index 만 가짜다.
  - 작업 트리가 커밋과 달라도 `runVerify` 가 `ok:true, clean:true` 를 내고, head 는 실제 커밋이었다.
- 결정: J2 공통 디렉터리 확인에 두 조건을 더한다. 둘 다 공통 디렉터리 안이라 두뇌가 직접 쓸 수 없다.
  1. `realpath(harnessGit(base, ['rev-parse', '--absolute-git-dir']))` 가 `realpath(<common>/worktrees/<이름>)` 이어야 한다.
     - 하네스가 만든 워크트리는 linked worktree 다. main 경로 자체(워크트리 아님)가 기준인 경우는 `<common>` 과 같아야 한다.
  2. 그 관리 디렉터리의 `gitdir` 파일 내용의 realpath 가 `<등록 워크트리>/.git` 의 realpath 와 같아야 한다.
- 어긋나면 J2 와 같게 처리한다: 첫 채움·detect 실패, 새로 고침은 조용히 현재 설정, 증거 `head:null, clean:null`.
- 테스트: 검수 probe 재현(밖의 가짜 gitdir + 진짜 commondir) → 첫 채움 실패, 증거 null, 설정 그대로. 정상 워크트리·워크스페이스 멤버 워크트리는 통과.

## K2 [낮음] clean 판정의 attributes 고정

- 검수 재현: 두뇌가 `git config core.attributesFile <파일>` 로 clean 필터를 걸면, 크기가 같은 추적 파일 수정이 clean 으로 나온다.
- 결정: `harnessGit` 의 `-c` 고정에 `core.attributesFile=/dev/null` 을, env 에 `GIT_ATTR_NOSYSTEM=1` 을 더한다.
  - 커밋된 `.gitattributes`(LFS 등)는 그대로 따른다.
  - `core.excludesFile` 은 고정하지 않는다. 워크트리 의존성 링크가 전역 excludes·`info/exclude` 에 기대기 때문이다(`worktree.ts` 링크).
- 테스트: `core.attributesFile` + 필터 설정 뒤 같은 크기 수정 → clean=false.

## K3 [낮음] 읽는 쪽도 replace 를 따르지 않음

- 훅은 `git replace` 형태를 막지만, alias·`refs/replace` 로의 fetch·`symbolic-ref` 로 replace ref 를 만들 수 있다.
  - 감지·clean 은 `harnessGit` 이라 영향이 없다.
  - 그러나 `validateTaskCommit` 등 `worktree.ts` 의 git 헬퍼와 Codex 자식(검수자의 `git show`·`diff`)은 replace 를 따른다.
- 결정
  - `worktree.ts` 의 git 실행 헬퍼 env 에 `GIT_NO_REPLACE_OBJECTS=1` 을 넣는다.
  - 하네스가 띄우는 Codex 자식(위임·검수)과 Claude 검수 자식 프로세스 env 에도 넣는다. 찾은 위치를 결과 문서에 적는다.
  - 사용자 검증 명령 실행 env 는 바꾸지 않는다.
- 훅: 두뇌의 git 명령 인자에 `refs/replace` 가 들어 있으면 거부한다(fetch·push·symbolic-ref 등). 목록 조회용 `for-each-ref`·`show-ref`·`log` 는 허용해도 된다. 기준은 "쓰기 가능 명령"이다.
- 테스트
  - replace ref 가 있는 저장소에서 `validateTaskCommit` 이 실제 객체 기준으로 판단한다.
  - 훅: `git fetch . A:refs/replace/X`·`git symbolic-ref refs/replace/X …` 는 거부한다.

## K4 [참고] 훅: `git replace -l <pattern>` 허용

- `-l`·`--list` 뒤의 패턴 인자는 조회이므로 허용한다. 테스트 1줄을 더한다.

## K5 [참고] 첫 채움 원장 오류

- 첫 채움의 `recordAutoVerify` 가 try 밖이다. 설정 기록 뒤 원장·알림이 실패하면 throw 한다.
- 결정: 설정 기록이 성공했다면 원장·알림 오류는 잡는다. stderr 경고(redact) 뒤 새 설정으로 계속 실행한다.

## K6 [참고] 문구·README

- HEAD 목록·batch 출력이 16 MiB 상한을 넘으면 전용 문구를 쓴다: `HEAD 목록이 너무 큽니다(16 MiB 초과) — 사용자가 verify.commands 를 설정해야 합니다`. `.git 과 HEAD 를 확인하세요` 는 쓰지 않는다.
- README 한계 표에 두 줄을 더한다.
  - 하네스 git 은 PATH 의 `git` 을 쓰고 HOME 을 따른다. 두뇌가 PATH 를 바꾸는 것은 검증 명령 자체에도 해당하는 기존 한계다.
  - 자기 자신을 무시하는 미추적 `.gitignore`·`.gitattributes` 는 clean 판정에서 숨는다. 기존 REVIEW 게이트 한계이고, 감지는 HEAD 를 읽으므로 영향이 없다.

## 작업 규칙

- 전체 테스트(`npm test`, 인자 없는 `npx vitest run`)는 돌리지 않는다.
  - 반드시 돌릴 파일
    - vc1 3개, `verify.test.ts`, `hook.test.ts`, `w3a-single.test.ts`
    - `rg -l "validateTaskCommit\|worktree.ts" test/` 로 찾은 워크트리 테스트
    - Codex 자식 env 를 바꿨다면 해당 codex 테스트 파일
    - `p7-commit.test.ts`, `p7-state.test.ts`, `templates.test.ts`
  - 모든 vitest 호출에 `FODH_NOTIFY_OS=off --maxWorkers=1 --no-file-parallelism` 을 붙인다. 한 번에 파일 3개 이하로 나눠 돌린다.
  - `npm run typecheck`·`git diff --check` 도 돌린다.
- VC1 이전 테스트의 단언은 바꾸지 않는다. 바꿔야 하면 멈추고 결과 문서에 적는다. 자식 env 스냅숏 단언이 새 키 하나 때문에 깨지는 경우도 멈추고 적는다.
- `/bin/ps` 차단 때문에만 실패하는 테스트는 기록만 한다.
- 커밋·브랜치는 만들지 않는다(임시 저장소는 괜찮다). 비밀값을 쓰지 않는다.
- 결과 문서 끝에 "보정 5" 절을 더한다. 내용: K1~K6 변경 파일:줄, 새·바뀐 테스트, 돌린 파일과 결과 수.
