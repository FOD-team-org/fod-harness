## F23 (높음) — 두뇌 턴 종료가 살아 있는 Codex 위임을 죽인다

재현(원장 `a3a0d617`, `d3fa724e`, `dd5ffa9d`): 두뇌가 `fodh codex task … --wait` 를 Claude Code Bash `run_in_background: true` 로 띄우고 턴을 끝냈다. `claude -p` 가 종료하며 **백그라운드 Bash 작업의 프로세스 트리(ppid 사슬)를 통째로 죽인다** — `fodh` CLI 의 자식인 감독 프로세스(`detached: true`, 자기 pgid, 그러나 ppid 는 아직 CLI)가 SIGTERM 을 받아 `onTerm → stop('cancelled')` 로 Codex 를 끝냈다(meta `status: cancelled`, `exit: 0`, 8~14초). Fable 이 실제로 재현했다: 헤드리스 haiku 두뇌 안에서 백그라운드 Bash 로 `node` 부모 → `detached` 로 띄운 `sleep` 손자가 두뇌 종료와 함께 죽었다(부모는 SIGTERM 수신, 손자도 소멸). 포그라운드 Bash 에서 띄운 `detached` 자식은 pgid 분리 + ppid 1 로 살아남았다(T03 이 살아남은 이유 = `--wait` 없이 포그라운드로 시작).

하네스의 신호 경로(`src/provider/runner.ts` `reclaimOwnedGroup` 은 두뇌 pgid 만, `cancel()` 은 `src/core/reclaim.ts` 만 호출)는 원인이 아니다. 다음 넷을 모두 넣는다.

1. **감독 프로세스 2단 분리** (`src/core/codex.ts:108-113`, `bin/fodh-codex-supervisor`/`src/core/codex-supervisor.ts`): CLI 가 감독을 직접 자식으로 두지 않는다. CLI → 런처(짧게 살고 끝남) → 감독 순으로 띄워 CLI 가 돌아올 때 감독의 **ppid 가 1** 이 되게 한다. 구현은 `bin/fodh-codex-supervisor <root> <runId> --launch` 처럼 같은 실행 파일의 런처 모드로: 런처는 `detached: true, stdio: ['ignore','ignore', log.fd]` 로 감독을 띄우고 `child.unref()` 뒤 stdout 에 `{"pid": <감독 pid>}` 한 줄을 쓰고 즉시 exit 0 한다. CLI 는 런처를 `detached: true, stdio: ['ignore','pipe', log.fd]` 로 띄워 런처 종료를 기다린 뒤 pid 를 읽고, 이후 흐름(`processStartedAt(pid)`, `registerProc`, `updateSlot`, meta `pid/processStartedAt`)은 지금과 같다. 런처가 pid 를 못 주고 끝나면 기존 catch 경로(`finishRun fail`)로 간다. 감독 쪽 시작 잠금 검사(`current.pid !== process.pid`)는 유지.
2. **취소 표지 없는 SIGTERM 은 무시** (`src/core/codex-supervisor.ts:54-55`, `src/core/codex.ts` `cancel()`, `src/core/codex-reclaim.ts` `reclaimCodexOwner`, `src/core/cleanup.ts`): 하네스가 실행을 끝내려는 모든 경로는 신호 전에 `.pi/codex/<runId>/cancel.json` `{ by: 'cancel'|'cleanup'|'reclaim'|'watcher', at }` 를 먼저 쓴다(공용 `requestCancel(root, runId, by)` 를 `codex-record.ts` 에 두고 `cancel()` 과 소유자 회수 경로에서 호출). 감독의 `onTerm` 은 표지 파일이 있을 때만 `stop('cancelled')` 하고, 없으면 무시하며 supervisor.log 와 원장(`codex:signal`, status `skip`, evidence `{ signal: 'SIGTERM', ignored: true }`, runId 당 1회) 에 남긴다. SIGKILL 은 막을 수 없으니 README 알려진 한계에 적는다("`kill <감독 pid>` 는 무시된다 — `fodh codex cancel <runId>` 를 쓴다"). `fodh codex cancel` 명령이 없으면 CLI 에 추가(`cancel(root, runId)` 호출, 사용자 전용 아님 — 두뇌도 자기 위임을 끝낼 수 있다).
3. **살아 있는 위임은 표지 없이도 대기로 본다** (`extensions/orchestrator/index.ts:184-202`): `agent_end` 에서 `대기: 위임 <id>` 가 없거나 `<id>` 가 `state.delegation.runId` 와 다르더라도, `state.delegation` 이 있고 그 meta 가 미완(`!finishedAt`)이면 `awaitingDelegation: true, autoTurns: 0` 으로 두고 원장 `delegation:implied` (evidence `{ marker: <id|null>, runId }`) 를 남긴 뒤 자동 재개하지 않는다(두뇌가 Claude Code 작업 ID `b83qz13ws` 같은 엉뚱한 값을 적는 일이 실제로 있었다). 살아 있는 위임이 없을 때만 기존 `delegation:marker skip` → 자동 재개. 워처의 `codex-done` 경로가 `awaitingDelegation` 을 풀어 재개하는 흐름은 기존대로.
4. **템플릿·훅**: `templates/prompts/IMPLEMENT.md`·`REVIEW.md`·`RESEARCH.md`·`FIX.md` 에 "`--wait` 는 포그라운드로만 쓴다. Bash `run_in_background` 로 돌리지 않는다(턴 종료 시 프로세스 트리가 죽는다). 결과가 안 오면 `대기: 위임 <runId>` 로 턴을 끝낸다" 를 넣는다. 훅 규칙(`hooks/pretooluse.mjs`, Bash 입력 `tool_input.run_in_background === true` 이고 명령에 `fodh codex` 와 `--wait` 가 함께 있으면) `deny('--wait 를 백그라운드로 돌리지 마라. 포그라운드로 실행하거나 --wait 없이 시작한 뒤 `대기: 위임 <runId>` 로 턴을 끝내라', 'boundary')`.
5. 테스트(실제 프로세스, codex 명령은 stub `sleep`): (a) `startCodex` 뒤 감독 pid 의 `ps -o ppid=` 가 1 이고 pgid === pid; (b) 감독에 표지 없이 SIGTERM → 살아 있고 meta 미완, 원장 `codex:signal skip` 1회; 이어 `cancel()` → 표지 생성 + `cancelled`; (c) 오케스트레이터 `agent_end` 표지 없음 + 살아 있는 위임 → `awaitingDelegation true` + `delegation:implied`, 위임 없음 → 기존 skip 재개; (d) 훅 `run_in_background` + `fodh codex task --wait` 거부, 포그라운드 허용; (e) 템플릿 문구.

## F24 (높음) — 두뇌가 판단을 스스로 답하고 적용한다

재현(두뇌 transcript): `fodh judgment answer A15 "병합 진행"`(14:23Z), `fodh judgment answer A16 "적용 진행"`(14:37Z), `fodh judgment apply`(13:45Z). 판단대기는 사용자 전용인데(설계 §4) `judgment answer`·`apply` 에 `assertNotBrain` 이 없다(`src/cli/index.ts:163,192`). 현재 `assertNotBrain` 은 `state transition` 사용자 전용 전이(`src/cli/index.ts:110`)에만 있다.

1. `fodh judgment answer`, `fodh judgment apply` 에 `assertNotBrain(root, '판단 답변')` / `'판단 적용'` (오류 문구 "판단은 사용자만 답합니다: docs/판단대기.md 의 `- 답:` 줄을 사용자가 채운다"). `judgment add`·`read`·`write-status`·`inbox ack` 는 두뇌 허용 유지. 워처·오케스트레이터 내부 호출(`applyJudgments` 직접 호출)은 영향 없음.
2. 훅(`hooks/pretooluse.mjs`): 두뇌의 `Edit`/`Write`/`MultiEdit`/`NotebookEdit` 가 판단 파일(설정 `judgment.file`, 기본 `docs/판단대기.md` — 훅이 설정을 못 읽으면 기본값 + `.pi/harness-judgment*.json`)을 대상으로 하면 `deny('판단대기 문서는 사용자만 고칩니다. 새 판단은 fodh judgment add 로 등록하라', 'boundary')`. Bash 명령 문자열에 그 경로가 쓰기 맥락(`>`, `>>`, `sed -i`, `tee`, `cp … 판단대기.md`, `mv`)으로 나타나면 같은 거부(읽기 `cat`/`grep` 은 허용 — 판정은 보수적으로: 경로 앞에 `>`/`>>`/`tee`/`sed -i`/`cp`/`mv` 토큰이 있을 때만).
3. `judgment add --reclaim` 이 아닌 일반 `add` 로 등록된 판단이 두뇌 답으로 닫히는 다른 길이 있는지(`answerJudgment` 를 부르는 CLI 경로 전부) 확인해 같은 가드를 건다.
4. 테스트: `FODH_BRAIN=1` 로 `judgment answer`·`apply` 거부, 사용자 허용(기존 brain-guard 테스트 방식 재사용); 훅 Edit `docs/판단대기.md` 거부·`docs/작업일지/…` 허용·Bash `>> docs/판단대기.md` 거부·`cat docs/판단대기.md` 허용.
