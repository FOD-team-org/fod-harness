## 발견(2차 수정 후보)

| # | 심각도 | 내용 | 근거 |
|---|---|---|---|
| F1 | 중간 | `fodh judgment add --blocks T99 --reclaim` 이 task 존재 검사 전에 판단 항목을 먼저 기록 → 오류 반환에도 A1 이 판단대기에 남음(부분 쓰기). `src/cli/index.ts` 의 `addJudgment` → `reclaimTask` 순서. task 검증을 먼저 하거나 실패 시 항목을 되돌려야 한다 | 1회차 실행: `{"error":"백로그 task를 찾을 수 없습니다: T01"}` 뒤 `judgment answer A1 1` 성공 |
| F2 | 중간 | DoD 증거 필드(`--verify-ok --merge-commit --docs-ok --cleanup-ok`)와 `--status done` 을 상태와 무관하게 설정 가능 → `MERGE` 상태에서 T01 을 `done` 으로 만들면 `MERGE→DOCS` 가 "완료 또는 차단된 task는 진행할 수 없습니다" 로 거부되고 CLEANUP·PICK 도 불가, RECLAIM 은 "task를 막는 열린 판단 번호가 필요" → 두뇌가 같은 실수를 하면 판단 항목 + reclaim(그러면 done 이 blocked 로 강등) 외에 탈출구가 없음. 제안: `done` 은 CLEANUP 상태(또는 CLEANUP→PICK 전이 시)만 허용하거나, 현재 task 가 done 이면 `MERGE/DOCS→CLEANUP` 을 허용 | 8·11번 항목 |
| F3 | 낮음 | `judgment add --blocks T02`(reclaim 없음)는 판단대기에 "막힌 작업: T02" 를 적지만 백로그 T02 는 `ready` 그대로 → 문서와 표 불일치. 두뇌(fable)가 같은 제목의 판단 A3·A4 를 연달아 2건 생성했는데 dedupe 가 막지 못함(배경 문구 차이로 추정) | 9번 항목 뒤 판단대기 |
| F4 | 낮음 | `WAIT_JUDGMENT` 를 벗어난 뒤에도 상태 파일에 `resumeState`·`pickJudgment` 가 남음(정보 오염) | 7번 이후 `state get` |
| F5 | 낮음 | `WAIT_JUDGMENT → PICK` 수동 전이가 A2(교착) 미답 상태에서도 허용됨 — 스펙 §1 은 resumeState 복귀만 명시. 두뇌가 판단을 기다리지 않고 진행할 수 있음(의도라면 문서화) | 7번 항목 |
| F6 | 낮음 | `pi -p` 프린트 모드에서 `/status` 출력 없음(추정: `ctx.ui.notify` 미렌더). 대화형 TUI 확인은 사용자 몫 또는 다음 실기 | 10번 항목 |
