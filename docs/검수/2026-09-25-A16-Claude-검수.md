## 발견

### A16-1 [중간] agent_end가 유휴 검사를 통째로 버려서 0.73.1 롤백 때 지시문이 두 번 나간다. 기존 M1/L8 테스트는 불안정해졌다

- **위치:** `extensions/orchestrator/resume.ts:57-59`(agent_end 분기), `test/orchestrator.test.ts:393-404`(M1/L8, 이번 diff에서 바뀌지 않음)
- **원인:** `reason === 'agent_end'`이면 `isIdle()`를 전혀 보지 않는다.
  - 0.87.1에서는 문제가 없다. agent_end가 run 안에서 돌고, 그동안 워처 경로는 busy로 막힌다.
  - 스펙 (b)-4는 0.73.1로 되돌려도 같은 코드가 동작해야 한다고 한다. 0.73.1에서는 agent_end가 idle 상태에서 돈다.
  - 그래서 워처 경로(stalled 등)가 먼저 resume 잠금을 잡고 보내 새 run을 열면, 뒤이어 들어온 agent_end 쪽은 그 run을 보지 못하고 한 번 더 보낸다.
  - `hasPendingMessages`는 막아 주지 못한다. 사용자 텍스트 큐만 세고 확장이 보낸 custom 메시지는 세지 않기 때문이다(`agent-session.js:1591-1593`, `:2457`).
- **재현**
  - `npx vitest run test/orchestrator.test.ts -t "M1/L8" --maxWorkers=1`를 8회 돌리면 5회 통과, 3회 실패한다. 실패 메시지는 `expected "spy" to be called 1 times, but got 2 times`(`:402`)이다. 결과는 두 호출 중 어느 쪽이 먼저 잠금을 잡느냐에 달려 있다.
  - scratch `order.mts`로 순서를 고정했다. 모형은 0.73.1이다: idle에서 시작하고, 보내면 idle=false가 된다.
    - `agent_end → stalled`: sends=1, autoTurns=1, `[resumed, busy]`
    - `stalled → agent_end`: sends=2, autoTurns=2, `[resumed, resumed]`
  - 두 문서의 주장이 이 테스트로는 성립하지 않는다.
    - 결과 문서 55행: "idle=true/hasPendingMessages 미제공 호환은 기존·추가 가짜 ctx 테스트로 확인했다"
    - 스펙 (b)-5: "기존 agent_end 재개 테스트는 새 조건에서도 통과해야 한다"
  - Fable의 전체 실행(1860/1862)에서 잡히지 않은 것은 그때 잠금 순서가 맞았기 때문으로 본다.
- **수정 제안(둘 중 하나)**
  - 진입 시점의 유휴 여부를 잡아 둔다. `resumeContext(ctx)`를 만들 때 `idleAtStart = ctx.isIdle?.() ?? true`를 저장한다. agent_end 분기는 `pending-input`을 먼저 보고, 그다음 `idleAtStart && isIdle() === false`이면 `busy`로 끝낸다.
    - 0.87.1에서는 idleAtStart가 늘 false이므로 지금 동작 그대로다.
    - 0.73.1에서는 예전 동작으로 돌아간다. M1/L8은 고치지 않아도 결정적으로 통과해야 한다.
  - 두 버전 모두에 통하는 방법도 있다. 상태에 재개 순번(`resumeSeq`)을 두고, agent_end 진입 때 읽은 값과 잠금 안의 값이 다르면 `already-resumed`로 건너뛴다. 이 방법은 참고 R1도 함께 막는다.
- 어느 쪽이든 M1/L8은 순서를 고정한 두 경우(`stalled` 먼저, `agent_end` 먼저)로 나눠 결정적으로 만든다.

### A16-2 [중간] agent_end 처리 중에 Esc를 누르면, 보낸 followUp이 큐에 남았다가 다음 사용자 입력 뒤에 실행된다

- **위치:** `extensions/orchestrator/resume.ts:57-59`·`:111-117`, `extensions/orchestrator/index.ts:207-283`
- **원인:** 0.87.1 소스를 따라가면 다음 순서가 된다.
  1. agent_end 핸들러는 run 안에서 await된다. 핸들러는 autoResume 전에 상태·백로그·판단 문서를 여러 번 읽고 쓴다(수십 ms 단위). 이 사이에 사용자가 Esc를 누를 수 있다.
  2. 스트리밍 중 Esc는 `restoreQueuedMessagesToEditor({abort:true})`를 부른다(`interactive-mode.js:2332-2335`). 이 함수는 먼저 `clearAllQueues()`로 큐를 비우고, 그다음 `session.abort()`를 부른다(`:3761-3768`). abort는 `_agentRunAbortRequested`를 true로 두고 `agent.abort()`를 부른다(`agent-session.js:1608-1619`).
  3. 그 뒤에 핸들러가 `pi.sendMessage(..., {deliverAs:'followUp'})`를 부른다. `isStreaming`(= `_isAgentRunActive`)이 아직 true이므로 메시지는 `agent.followUp()`으로 들어간다(`agent-session.js:1494-1500`). 큐는 이미 비운 뒤라 이 메시지는 지워지지 않는다.
  4. `_runAgentPrompt` 루프는 abort 요청을 보고 continue 없이 끝난다(`agent-session.js:1083-1098`). followUp은 `agent.followUpQueue`에 그대로 남는다. `agent.prompt()`는 큐를 비우지 않는다(`pi-agent-core/dist/agent.js:241-247`).
  5. 사용자가 다음에 입력해 run이 열리면, 루프가 `getFollowUpMessages`로 남은 지시문을 꺼낸다(`agent.js:335`). 그래서 사용자 턴 바로 뒤에 하네스 지시문 턴이 이어진다.
  - 이 경우 마지막 assistant의 `stopReason`은 aborted가 아니므로 `userAborted`가 서지 않는다. autoTurns는 +1된 채 남는다.
- **같은 창에서 사용자가 입력하는 경우도 비슷하다.**
  - Pi는 input 핸들러를 await한 뒤에야 `_queueSteer`로 입력을 큐에 넣는다. 이 핸들러에는 우리 `index.ts:98-105`의 상태 쓰기가 포함된다.
  - 그 사이에 마지막 검사(`resume.ts:111`)를 지나면, 사용자 입력과 하네스 followUp이 둘 다 실행된다.
  - `index.ts:284`의 finally는 사용자가 방금 건 `userHold`까지 지운다.
- **재현:** 실제 pi를 실행하지 않았으므로 실행 재현은 없다. 위 소스 경로로 추적했다.
- **수정 제안**
  - `ResumeContext`에 `signal: () => ctx.signal`을 더한다. 0.87.1은 `ctx.signal`을 활성 run의 abort 신호로 준다(`agent-session.js:2449`, `agent.js:212-214`).
  - agent_end 분기의 `blocked()`가 `signal?.aborted`이면 `'aborted'`를 돌려주게 한다.
    - 세 검사 지점 모두에 걸린다. 마지막 검사와 enqueue 사이에 await가 없으므로 Esc 창이 닫힌다.
    - 이때 `userAborted: true`도 기록하면 기존의 aborted 종료와 의미가 같아진다.
  - 사용자 입력이 겹치는 창까지 닫으려면 소비 시점에 검사해야 한다. 예를 들어 지시문 `details`에 재개 순번을 싣고, `context` 이벤트에서 그 순번 뒤에 사용자 입력이 있었으면 해당 harness-orchestrator 메시지를 뺀다. 이 부분은 후속으로 미뤄도 된다.
  - 테스트: 가짜 ctx의 `signal`을 abort한 뒤 agent_end를 보내면 sendMessage 0회, autoTurns 0이어야 한다.

### A16-3 [낮음] 신뢰하지 않은 프로젝트의 `compaction.enabled=false`만으로도 경고가 꺼진다

- **위치:** `extensions/provider/compaction.ts:5-10`, `extensions/provider/index.ts:91`, `README.md:22`
- **원인**
  - Pi는 신뢰 전에는 프로젝트 `.pi/settings.json`을 읽지 않는다(`settings-manager.js:195-196`, `:275-286`, `main.js:580-586`).
  - 그런데 `compactionDisabled`는 신뢰 여부를 보지 않고 그 파일의 false도 인정한다. 그 결과 Pi는 컴팩션을 켠 채인데 하네스는 안내하지 않는다. 이는 스펙 (d)의 취지(확인하지 못하면 안내)와 어긋난다.
  - README 22행("전역 또는 프로젝트 설정에서 … false를 확인하면 경고하지 않습니다")도 같은 동작을 적었다. 같은 문서 16행("신뢰하기 전까지 무시")과 앞뒤가 맞지 않는다.
- **재현(scratch, Node):** 전역 `{}`, 프로젝트 `{"compaction":{"enabled":false}}`로 두면 `compactionDisabled()`가 true다. 판정에 신뢰 여부는 들어가지 않는다.
- **수정 제안**
  - `compactionDisabled(root, projectTrusted)`로 바꾸고, `index.ts:91`에서 `ctx.isProjectTrusted?.() ?? true`를 넘긴다(0.87.1에는 `isProjectTrusted()`가 있다, `types.d.ts:235`). 신뢰하지 않았으면 전역 설정만 본다.
  - 가능하면 Pi와 같은 우선순위로 실효값을 계산한다(참고 R3).
  - README 22행은 "전역 설정 또는 신뢰된 프로젝트 설정"으로 고친다.
  - 테스트: 프로젝트만 false이고 신뢰하지 않았으면 경고가 나야 한다.

## 참고

검증했지만 결함으로 보지 않은 것, 또는 확인하지 못한 것이다.

- **R1:** 확장이 보낸 큐는 `hasPendingMessages`에 잡히지 않는다.
  - 핸들러가 도는 동안 명령(`/judged` 등)이 `send()`(`resume.ts:39-42`, deliverAs 없음 → steer)로 보낸 지시문은 `pendingMessageCount`에 들어가지 않는다.
  - 그러면 명령 지시문과 자동 재개 followUp이 둘 다 실행될 수 있다.
  - 명령이 agent_end 핸들러 창 안에 들어와야 하므로 드물다. A16-1의 순번 방식으로 고치면 같이 막힌다.
- **R2:** settle 창
  - `_emitAgentSettled`는 `_isAgentRunActive=false`로 바꾼 뒤 `agent_settled` 핸들러를 await한다. 그동안 triggerTurn 전송은 `_deferredSettledActions`로 미뤄지고, isIdle은 true로 보인다.
  - 워처 경로 두 번이 이 창에 들어오면 둘 다 미뤄졌다가 차례로 실행된다.
  - 하네스 세 확장에는 `agent_settled`·`agent_before_settle` 핸들러가 없어 이 창은 사실상 0이다. 다른 확장과 함께 쓸 때 다시 볼 것.
- **R3:** 컴팩션 판정이 Pi와 다른 나머지 두 경우
  - 전역 false + 신뢰된 프로젝트 true: Pi는 프로젝트 값을 우선해 컴팩션을 켠다(deepMerge). 우리는 false가 하나라도 있으면 꺼졌다고 본다(scratch 결과 true).
  - `PI_CODING_AGENT_DIR='~/x'`처럼 물결표가 펼쳐지지 않은 채 오는 경우: Pi는 펼친다(`config.js:408-426`). 우리는 펼치지 않아 파일을 못 찾고 경고를 한 번 더 낸다. 안전한 쪽이다.
- **R4:** provider 대기가 상한에 걸려도 두뇌 그룹을 직접 죽이지 않는다.
  - 상한 5000ms가 `reclaimOwnedGroup`의 TERM 유예 5000ms(`runner.ts:73-76`)와 같다. 그래서 TERM을 무시하는 자손이 있으면 SIGKILL보다 상한이 먼저 끝날 수 있다.
  - 다만 실제 경로는 대부분 막혀 있다.
    - Pi는 session_shutdown 핸들러를 확장 순서대로 하나씩 await한다(`extensions/runner.js` emit). README 레시피 순서(provider → orchestrator → watcher)라면 watcher의 `runCleanup(root,{scope:'processes',sessionId})`가 같은 세션의 brain 기록을 `reclaimOwnedGroup`으로 다시 회수하고, SIGKILL까지 간다(`src/core/cleanup.ts` processes).
    - SIGTERM·SIGHUP에서는 우리 처리기가 TERM+KILL을 동기로 보내고 표지를 쓴다(`shutdown.ts:39-44`).
    - /new·/resume·/fork에서는 `teardownCurrent`가 먼저 `session.abort()`로 스트림이 끝나기를 기다린다(`agent-session-runtime.js:102-112`).
  - 남는 경우는 watcher 없이 provider만 로드한 대화형 종료다. 그때는 다음 session_start의 `recoverOrphanBrain`까지 그룹이 살아 있다.
  - 최악의 종료 시간은 provider 5초 + watcher 5초 + runCleanup 약 7초다.
  - 원하면 상한에 걸렸을 때 `getCurrentBrainGroup()`에 SIGKILL과 표지를 동기로 보내면 된다.
- **R5:** watcher 세대 가드에 빠진 곳이 있다.
  - `decidePending`(`watcher/index.ts:44-55`)은 `stopped`만 본다. `liveContext`(`:43`)는 `stopped`와 가변 `ctx`를 본다.
  - 같은 인스턴스가 shutdown 뒤에 다시 session_start를 받으면, 옛 세대 루프가 새 ctx로 결정을 이어 갈 수 있다.
  - 0.87.1은 런타임마다 팩토리를 새로 부른다(`extensions/loader.js:394-449`). 그래서 옛 인스턴스는 stopped로 남고 이 경로에 닿지 않는다.
  - 가드를 넣으려면 `decidePending(started)`로 세대 값을 넘긴다.
- **R6:** 테스트 "겹친 agent_end"(`test/orchestrator.test.ts:193-195`)는 실제에 없는 계약으로 통과한다.
  - 우리 followUp을 보낸 뒤 `hasPendingMessages`를 true로 바꾸는데, 0.87.1은 확장이 보낸 메시지를 세지 않는다.
  - 0.87.1에서 agent_end는 run마다 한 번씩 차례로만 오므로, 이 테스트가 막으려는 상황 자체가 없다.
  - A16-1을 고친 뒤에는 이 테스트를 isIdle 기반 모형으로 되돌리는 편이 낫다.
- **R7:** 대기 상한 테스트는 대상 로직을 실제로 거친다.
  - provider 테스트(`test/extension.test.ts:184-198`)는 `streamClaude`를 끝나지 않는 가짜로 바꾼다. 잠금 ENOENT, 도구 복구, 원장 1회는 증명한다. 두뇌 그룹 처리(R4)는 범위 밖이다.
  - watcher 테스트(`test/watcher-extension.test.ts:238-250`)는 tick·memory를 가짜로 둔다. 원장 1회, runCleanup 호출, 타이머 0을 확인한다.
  - 두 테스트 모두 `waitForShutdown` 자체는 흉내 내지 않고 실제로 거친다.
- **R8:** P8 참고 R2(SIGTERM 재전송 시점)는 0.87.1에서 해소됐다.
  - 신호로 종료할 때 Pi는 dispose가 끝날 때까지 자기 처리기를 해제하지 않는다(`interactive-mode.js:3362-3381`, `:3452-3468`). 중복 호출은 `isShuttingDown`으로 막는다.
  - 따라서 우리 처리기가 다시 보낸 SIGTERM은 Pi 처리기에서 무시된다. signal-exit도 리스너 수가 count와 다르므로 기본 종료하지 않는다.

#### A16-4 [낮음] RECLAIM 안내가 고르는 판단 번호가 `reclaimTask`의 전제와 다르다

- **위치:** `extensions/orchestrator/index.ts:271-273`. 대조할 곳은 `src/core/reclaim.ts:25-26`과 같은 파일 `index.ts:284-285`다.
- **원인:** `:273`은 SPEC~CLEANUP 분기의 "막는 판단" 술어를 거의 그대로 옮겼다. 그런데 이 번호는 **실행할 명령**(`fodh reclaim --task T --judgment A`)에 들어간다. 그래서 `reclaimTask`의 전제와 맞아야 하는데, 세 군데가 어긋난다.
  1. `task.status === blocked(A)`로만 맞는 판단도 고른다. 이런 판단은 `blocks`에 T가 없을 수 있다(사용자가 판단 문서를 고친 경우 등). 그런데 `reclaimTask`는 `judgment.blocks`에 T가 있어야 한다(`reclaim.ts:26`). 그러면 안내대로 실행해도 "task를 막는 열린 판단 번호가 필요합니다"로 실패한다.
  2. `!item.followup` 필터가 없다. `:284`에는 있다. 원 질문(후속 질문이 달린 것)과 재질문이 둘 다 T를 막고 있으면 문서 순서상 먼저 나오는 옛 번호를 고른다.
  3. pendingReclaim의 번호가 아직 열려 있는지 보지 않는다(`:272`). 회수 실패 뒤 그 판단이 결정 완료로 옮겨졌다면, 안내한 명령이 1과 같은 이유로 실패한다.
- **재현:** 실행 재현은 없다. 코드로 따라간 경로다.
  - 예: RECLAIM/T1, 열린 판단 A1의 blocks=`-`, T1 status=`blocked(A1)` 상태에서 두뇌가 `대기: 사용자`로 끝난다.
  - 안내는 `fodh reclaim --task T1 --judgment A1`이 되고, 실행하면 `reclaim.ts:26`에서 실패한다.
  - 두뇌가 이를 반복하면 안전망 3턴 뒤 WAIT_JUDGMENT로 멈춘다. 멈추기는 하므로 피해는 턴 낭비다.
  - 세 경우 모두 드문 상태라서 낮음으로 본다.
- **수정 제안**
  - `reclaimTask`와 같은 술어로 고른다: `open.find(item => !item.followup && item.blocks.split(/[\s,]+/u).includes(taskId))`
  - pendingReclaim 번호도 `open` 안에 있고 같은 술어를 만족할 때만 쓴다.
  - 맞는 것이 없으면 `--reclaim` 등록 안내로 떨어뜨린다.
  - 테스트: blocks 없이 status만 맞는 판단, followup 쌍, 닫힌 pendingReclaim 번호
