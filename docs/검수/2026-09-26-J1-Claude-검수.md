### 1. [중간] migrate 가 아직 이벤트가 나가지 않은 사용자 편집(externalPending)을 지운다

- 위치: `src/core/judgment.ts:205`(`!migrating && …`), `:827`(`save(..., true)`), 테스트 `test/j1-judgment-structure.test.ts:212-218`
- 재현:
  1. 하네스(Pi)가 꺼진 상태에서 사용자가 옛 형식 파일의 `### A19 … (2026-09-25)` 에 `- 답: 1` 을 쓴다. 또는 켜져 있어도 `stableSeconds` 가 지나기 전이다.
  2. doctor 의 legacy 경고를 보고 `fodh judgment migrate` 를 실행한다.
  3. 하네스를 켜서 tick 을 돈다.
- 기대: 스펙 §7-9 는 "migrate 쓰기는 이벤트를 내지 않고, 사용자 답 수정은 지금처럼 낸다"이다. migrate 전의 사용자 편집은 migrate 뒤에도 한 번 `judgment-changed` 가 되어 자동 적용되어야 한다.
- 실제:
  - `migrating=true` 이면 `originalHash ≠ expectedHash ∧ ≠ lastEmitted` 여도 `externalPending` 을 만들지 않는다.
  - migrate 가 `expectedHash` 를 새 해시로 바꾸므로 워처(`src/core/watcher.ts:110-121`)는 `hash === expectedHash` 로 보고 `lastEmitted` 만 갱신한다.
  - 결국 이벤트가 영원히 나지 않는다. 답은 파일에 남지만 자동 적용되지 않는다. 사용자가 `/judged` 를 치거나 파일을 다시 고쳐야 한다.
  - 오늘 실제 흐름(A19~A22 를 옛 파일에 답한 뒤 구조 이전)과 같은 경로라서 일어날 법하다.
  - 현재 테스트(212)는 이 동작을 "이벤트 0" 으로 단언해 굳히고 있다. 관찰만 되고 아직 방출되지 않은 사용자 편집이 migrate 뒤에 사라지는 것을 정답으로 삼는 셈이다.
- 수정안:
  - `!migrating` 조건을 지운다. 일반 `save` 와 같은 식으로 둔다. migrate 자체 쓰기는 `expectedHash` 갱신만으로 이미 이벤트가 나지 않는다.
  - 테스트 212 는 migrate 전에 `tick(now+11000)` 으로 옛 내용을 먼저 방출·정착시킨 뒤 "migrate 뒤 이벤트 0" 을 단언하도록 바꾼다.
  - 새 테스트를 더한다: 옛 파일에 답을 쓰고 tick 없이 곧바로 migrate 한다. `stableSeconds` 가 지나면 `judgment-changed` 가 정확히 한 번 나오고, `applyJudgments` 가 그 항목을 판단기록으로 옮기는지 본다.

### 2. [낮음] 날짜 제목 호환이 일반 파서에 들어가, reconcile 의 rev 증가가 안 되고 자동 적용 대상이 넓어졌다

- 위치: `src/core/judgment.ts:53`(제목 정규식 `\((?:rev\s+(\d+)|\d{4}-\d{2}-\d{2})\)`, `rev: Number(heading[3] ?? 1)`), `:142-143`(`raw.replace(/\(rev \d+\)/u, …)`)
- 재현: 옛 파일에 `### A30 — 질문 (2026-09-25)` 항목을 두고 `- 답: 1` 을 쓴다. 적용 전에 사용자가 `- 배경:`(또는 선택지)을 고친다. 그다음 `readJudgment` 또는 `applyJudgments` 를 부른다.
- 기대: 질문 해시가 바뀌면 rev 가 2 로 오르고 `- 답 기준 rev: 1` 이 붙는다. 그러면 `classifyAnswer` 가 옛 rev 에 준 답이라며 재질문하는 흐름을 탄다.
- 실제:
  - 제목에 `(rev N)` 이 없어 replace 가 아무것도 바꾸지 못한다. rev 는 1 그대로이고 `- 답 기준 rev: 1` 만 붙는다(rev == answerRev).
  - 옛 질문에 준 답이 바뀐 질문에 그대로 적용되고, questions 스냅샷도 새 해시·rev 1 로 덮인다.
  - J1 이전에는 날짜 제목 항목이 아예 파싱되지 않았다(한눈에·자동 적용 대상 아님). 이번 변경으로 손으로 쓴 날짜 제목 항목이 자동 적용 대상이 된다. 스펙 범위 밖 판정 변경이다.
  - migrate 전 옛 파일에서만 생긴다. migrate 는 제목을 정규화한다.
- 수정안(둘 중 하나):
  - (a) 날짜 제목 파싱을 migrate 전용 파서 옵션으로 한정한다.
  - (b) reconcile 치환 정규식을 `/\((?:rev \d+|\d{4}-\d{2}-\d{2})\)/u` 로 넓혀 날짜 제목도 `(rev N+1)` 로 바꾼다.
  - 어느 쪽이든 "날짜 제목 + 답 + 질문 수정 → rev 2·재질문" 테스트를 더한다.

  - 테스트: 7번 장애 주입 테스트에 "장애 후 답 변경" 변형을 더해 블록 1개(새 답)·notes 1회·저널 비움을 단언한다.

### 5. [낮음] §7-6 번호 유일성 테스트가 영속 카운터를 격리하지 못한다

- 위치: `test/j1-judgment-structure.test.ts:60-71`
- 재현: `src/core/judgment.ts:703` 의 `highestNumber` 에서 seq 읽기를 빼도 이 테스트는 통과한다.
- 기대: 스펙 §3 불변식은 "A1~A3 완료 → 판단기록 삭제 → 다음은 A4" 이고, 카운터가 있어서 A4 가 되어야 한다.

### 6. [참고] `highestNumber` 의 `/A(\d+)/gu` 에 경계가 없다

- 위치: `src/core/judgment.ts:703`
- 재현: 판단기록이나 판단 파일에 `SHA256` 이 들어간 문장이 있다.
- 기대/실제:
  - 다음 번호가 A257 로 건너뛴다. 유일성은 깨지지 않고 번호에 빈 칸만 생긴다.
  - 스펙 §3 이 `A\d+` 를 글자 그대로 적었으니 스펙 위반은 아니다. 이전 코드 `\bA(\d+)(?:-\d+)?\b` 보다는 넓다.
  - 실제 판단 문서들에는 해당 토큰이 없다(grep 확인).
- 수정안: `(?<![A-Za-z0-9_])A(\d+)(?:-\d+)?(?![0-9])`.

### 11. [낮음] 장애 뒤 답 변경 정리가 재질문 사슬의 `모호:` 멤버 블록을 남긴다

- 재현:
  1. A1 에 "둘 다" 로 답해 재질문 A2 가 생긴다. A2 에 "2" 로 답하고 apply 한다.
  2. `completeJudgment(resolveChain)` 이 A1 블록(`모호: 둘 다 → A2: 2`)과 A2 블록(`2`)을 쓴 뒤, 판단 파일 저장 전에 장애가 난다.
  3. 사용자가 A2 답을 "1" 로 바꾸고 apply 한다.
- 기대: 옛 결정의 기록이 사슬 전체에서 사라진다. 새 답으로 A1·A2 블록이 한 개씩만 남는다.
- 실제:
  - 폐기 분기는 A2 의 (rev 1, "2") 블록만 지운다. A1 의 `모호: 둘 다 → A2: 2` 블록은 남는다.
  - 본 루프가 새 답을 적용하면 A1 에 `모호: 둘 다 → A2: 1` 블록이 더 붙는다. 그러면 A1 기록 2개, 최근 결정 중복, `completed` 중복이 생긴다.
  - 질문 변경으로 재질문이 되는 경우에는 A1 이 아직 열린 채 판단기록에 "결정" 으로 남는다.
  - 장애 창, 재질문 사슬, 장애 뒤 편집이 모두 겹쳐야 해서 드물다.
- 수정안:
  - 저널 항목에 사슬 기록의 정체(`archived: [{ id, rev, answer }]`, 멤버별 `모호:` 답 포함)를 저장한다. 폐기 분기에서 그 목록 전부를 지운다.
