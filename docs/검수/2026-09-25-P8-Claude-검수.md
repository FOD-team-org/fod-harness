## 발견

### P8-1 [높음, 해소 확인] 실제 Pi에서 SIGINT가 삼켜지고 두뇌가 살아남음

- **위치:** `src/provider/shutdown.ts:29-37`, `README.md:164`
- **당초 문제:** 이전 판은 "표식 없는 SIGINT 처리기가 하나라도 있으면 양보"했다. 실제 Pi는 시작할 때 이 조건을 항상 만족한다.
  - Pi main은 `settings-manager.js`를 불러오고, 이것이 `proper-lockfile`을 불러오며, 여기서 signal-exit 3.0.7의 `onExit`이 등록된다. 그래서 SIGINT 리스너가 항상 1개 있다.
  - fodh 처리기는 이 리스너를 "다른 처리기"로 보고 return했다.
  - signal-exit 쪽은 리스너 수(2)가 자기 count(1)와 다르므로 아무것도 하지 않았다.
  - 결과적으로 `kill -INT <pi>`를 보내도 Pi와 두뇌 그룹이 모두 살아남았다. HEAD에서는 Pi가 SIGINT로 죽었으므로 회귀였다.
- **현재 상태:** 18:29 수정본은 signal-exit의 count를 빼고 판정한다(`shutdown.ts:30-36`). 같은 재현 스크립트로 다시 확인했다.
  - lockfile + fodh: `signalCode=SIGINT`, 두뇌 그룹 사망
  - lockfile + fodh + 멈춤 모사 ignore 처리기: Pi와 두뇌 모두 생존(양보)
  - 새 테스트 `P8-b signal-exit 선등록`이 실제 Pi의 signal-exit 3.0.7을 불러와 두 경우를 검사한다. 통과했다.
- **남은 것:** 참고 R1(v3와 v4가 함께 있을 때)

### P8-2 [중간] README의 모델 교체 두 명령이 기본 설정에서 둘 다 실패

- **위치:** `README.md:27-32`, `src/core/config.ts:65-66`
- **재현:** `.pi/harness.json` = `{"brain":{"model":"claude-opus-5-5"}}`. `/model`에서 Opus를 고르면 바로 이 상태가 된다.
  1. `fodh config set brain.allowedModels '["claude-opus-6","claude-fable-5-1"]' --approve` 실행 시 exit 1. 오류는 "brain.model(claude-opus-5-5)이 … 없습니다 … `fodh config set brain.allowedModels '[…]' --approve` 로 목록을 바꾸세요"이다. 방금 실행한 명령을 다시 하라고 안내하는 셈이다.
  2. `fodh config set brain.model claude-opus-6` 실행 시 exit 1(목록에 없음).
  - 파일은 바뀌지 않는다. 별칭 `opus`도 같다. `claude-opus-5-5`를 목록에서 빼는 순간 해석되지 않는다.
- **수정 제안(셋 중 하나):**
  - README 순서를 "① 양쪽 목록에 다 있는 모델(예: `claude-fable-5-1`)로 먼저 `brain.model`을 옮김 → ② 목록 교체 → ③ 새 모델 지정"으로 적는다.
  - 목록과 모델을 한 번에 바꾸는 경로(예: 한 명령에 두 키)를 둔다.
  - 오류 문구를 바꾸려는 키에 따라 다르게 낸다. `allowedModels`를 바꾸다 실패했으면 "먼저 brain.model을 새 목록 안의 모델로 바꾸세요"라고 안내한다.

### P8-3 [중간] 같은 판단을 다시 등록할 때 유사도 검사가 먼저 걸려 `--blocks -`·복수 task는 막다른 안내를 받음

- **위치:** `src/core/judgment.ts:256-266` (유사도 261-262 → dedupeKey 264-266 순서), `src/cli/index.ts:180`
- **재현(실제 `bin/fodh`):**
  - `--blocks -`로 A1과 제목·인자가 모두 같은 재등록 → exit 1, "비슷한 열린 판단 A1 … --same-as A1 로 이 task 를 붙이고 …"
  - `--blocks "T01, T02"`도 같다.
  - 안내대로 `--same-as A1 --blocks -`를 실행하면 exit 1 "--same-as는 --blocks 단일 task가 필요합니다"
  - HEAD에서는 dedupeKey가 기존 항목을 돌려줬다(멱등).
- **영향:** 프로젝트 단계 판단은 규칙상 `--blocks -`다(`templates/brain-rules.md:3`, `PRD_DRAFT.md:5`). 이런 판단을 재시도하거나 복구 턴에서 다시 등록하면 두뇌는 따를 수 없는 안내를 받는다. 결국 `--distinct`(= "다른 원인")라는 틀린 의미로 돌아가야 한다.
- **수정 제안:**
  - 유사도 검사 전에 정확한 dedupeKey(답이 빈 항목) 일치를 먼저 돌려준다. 또는 유사도 후보에서 같은 key인 항목을 뺀다.
  - blocks가 단일 task가 아니면 오류 문구에서 `--same-as`를 빼고 "이미 열린 판단 A<n>을 기다려라"로 안내한다.
  - 회귀 테스트 두 건을 추가한다(`-`, 복수 task).

### P8-4 [낮음] `matchesModel`의 접미 숫자와 `[1m]` 처리

- **위치:** `src/provider/turn.ts:397-400`
- **확인한 동작:**
  - 접미가 `\d+`이면 무엇이든 통과한다. `claude-sonnet-4`→`claude-sonnet-4-5`, `claude-opus-5`→`claude-opus-5-5`, `claude-fable-5`→`claude-fable-5-1`이 모두 true다. 요청과 다른 세대로 바꿔 쓰여도 init 대조와 허용 목록 대조를 둘 다 통과한다.
  - `[…]`는 actual 쪽에서만 떼어낸다. 그래서 허용 목록에 `claude-opus-5-5[1m]`(또는 `opus[1m]`)를 넣으면 설정 검증은 통과하지만, 모든 턴이 `brain:model-rejected` configError가 된다. 1M 문맥을 쓰려는 사용자가 넣을 법한 값이다.
- **수정 제안:**
  - 날짜 접미는 `/^\d{8}$/`로 제한한다.
  - `[…]`는 양쪽에서 떼고 비교한다. 또는 `allowedModels`에서 대괄호를 거부한다.

## 참고

검증했지만 결함으로 보지 않은 것, 또는 확인하지 못한 것이다.

- **R1:** `shutdown.ts:34`는 v3 `__signal_exit_emitter__`와 v4 `Symbol.for('signal-exit emitter')` 중 하나만 쓴다(`??`). v4는 자기 판정에서 두 count를 더한다. 따라서 두 버전이 함께 로드되면 다시 양보(삼킴)한다. Pi 0.73.1 트리에는 3.0.7 하나뿐이라(확인) 지금은 영향이 없다. Pi 0.87.1 갱신 때 두 count의 합으로 바꾸거나 다시 확인해야 한다.
- **R2(P7 기존):** SIGTERM 재전송 시점이 문제다. Pi의 `shutdown()`이 처리기를 먼저 해제하면 signal-exit만 남아 즉시 기본 종료된다. 그러면 비동기 종료(터미널 복원, runtimeHost.dispose)가 끝나기 전에 프로세스가 죽는다. 0.87.1 갱신 때 확인이 필요하다.
- **R3:** `--same-as`를 `--blocks -` 판단에 붙이면 `- 막힌 작업: -, T01`이 된다(재현함). `-`를 특별히 해석하는 코드가 없어 기능 영향은 없고 표시만 어색하다. `-`면 치환하도록 고치면 된다(`judgment.ts:240-241`).
- **R4:** `--same-as`는 task가 이미 다른 판단(예: `blocked(A3)`)에 묶여 있는지 보지 않는다. 그러면 A3의 막힌 작업 줄에 task가 남은 채 상태만 `blocked(A1)`로 바뀐다. 스펙 범위 밖이다.
- **R5:** 유사도 토큰화는 스펙대로 공백·기호로 나눈다. 그래서 한국어 조사가 붙은 형태("커밋"과 "커밋이")는 다른 토큰이 되어 재현율이 떨어진다. 토이 원문 세 쌍은 이번 테스트에서 걸린다(`p8-judgment.test.ts:118-147`).
- **R6:** `templates/prompts/VERIFY.md:15`(와 IMPLEMENT·FIX)의 same-as 줄에는 `--reclaim`이 붙어 있다. 스펙 문구에는 없다. VERIFY 19행 규칙과는 맞지만, 4단계("설정 요청 후 기다림, reclaim 없음")와는 어긋난다.
- **R7:** 프로바이더가 모델 목록을 `process.cwd()`에서 동기로 읽는다(`extensions/provider/index.ts:20-22`). 두 가지 부작용이 있다.
  - `.pi/harness.json`이 없으면 `loadConfig`는 받아들이는데도 경고를 띄운다.
  - Pi가 저장한 기본 모델 `claude-code/fable`은 새 목록(전체 ID)에 없다. 폴백 동작은 확인하지 못했다(Pi 0.87.1 이전 시 안내 필요).
- **R8:** `test/p1-reclaim.test.ts` L4는 이제 same-task dedupe 경로를 탄다. "새 판단 생성 뒤 회수 실패" 경로는 다른 테스트가 덮는지 확인하지 못했다.

## 이상 없음으로 확인한 것

- `--same-as` 저장 경로
  - `addJudgment`와 같은 파일 잠금과 `save()`를 쓴다. expectedHash와 `judgment.questions`를 워처 잠금 안에서 갱신한다.
  - rev가 바뀌지 않고, 워처의 사용자 변경 이벤트도 없다.
  - 동시 편집기가 파일을 덮어써도 apply는 task 상태(`blocked(id)`) 기준으로 풀기 때문에 task를 잃지 않는다.

- model_select 실패 경로: `ready=false`, 도구는 비운 상태, 오류 알림. 성공하면 상태 모델을 갱신한 뒤 ensureDoctor를 부른다.

  - session_start 재설치와 턴 직전 `ensureShutdownReclaimFirst`가 동작한다.
  - `shutdown:reorder`는 프로세스 전역 Set 때문에 신호마다 한 번만 기록된다.
  - 테스트의 처리기 정리가 모두 짝지어져 있다.
