## 테스트 품질 메모

- 대체로 스펙 §8 의 (a)~(j) 를 실제 동작으로 단언한다. 원장 pre→ok, 레지스트리가 비는 것, 슬롯 해제, `task.codexThread`, 인박스→`buildPrompt` 결과 조회 줄, 워처 50개와 인박스 이중 dedupe, 60초 경계, stalled 제외 모두 그렇다. 조건부 skip 이나 단언 완화는 없다.
- 부족한 곳: H1(리더만 사망), M1(meta 부재), 표지 + `대기: 사용자` 조합, `--wait` 도중 워처가 먼저 codex-done 을 결정하는 경합(M2 와 별개로, 이때 중복 재개 인박스가 한 번 더 붙는다)에 대한 테스트가 없다.

## 실기 확인 권장 (최대 5)

1. **실제 JSONL 스키마**: 토이 git 프로젝트에서 `fodh worktree create T01` → `fodh codex task` 를 실행해 `thread.started.thread_id`, `item.type==='file_change'` 의 `changes[].path`, `command_execution` 의 id, `turn.completed.usage`, 실패 시 `turn.failed` 형태를 확인한다. `-o last-message.md` 가 workspace-write 샌드박스(cwd=워크트리) 밖인 `<root>/.pi/codex/<runId>/` 에 실제로 써지는지 본다.
2. **프로세스 그룹 소속**: codex 가 `sleep 60` 같은 긴 도구 명령을 돌리는 동안 `ps -o pid,pgid,command -g <감독 pid>` 로 codex 의 도구 자식(seatbelt 래퍼 포함)이 같은 pgid 에 남는지 확인한다. 이어서 `fodh codex cancel` → 잔존 0, `cancelled`, 슬롯 null, delegation 해제를 확인한다. `timeoutMinutes=1` 로 timeout 경로도 한 번 본다.
3. **resume**: `--resume last` 에서 `-c sandbox_mode=…` 와 spawn cwd 가 실제로 적용되는지(재개 스레드의 파일 변경이 루트가 아니라 워크트리에 생기는지), read-only review 가 쓰기를 거부하는지 확인한다.
4. **tmux Pi TUI 전체 루프**: IMPLEMENT 에서 두뇌가 쓰는 표지 모양(꺾쇠·백틱 여부, L1)을 확인한다. 이어서 재개 멈춤 → codex-done → 재개 프롬프트의 `fodh codex result` 줄 → ack → VERIFY 흐름을 확인한다. VERIFY 에서 두뇌가 워크트리로 `cd` 한 뒤 `fodh` 를 실행할 때 `.pi` 가 워크트리에 생기지 않는지(M3)도 본다.
5. **감독 강제 종료**: 실행 중 감독 pid 에만 `kill -9` 를 보내고 codex 가 고아로 남는지, 다른 프로젝트에서 `fodh codex` 가 슬롯을 얻는지, 60초 뒤 워처 `lost` 이후에도 codex 가 살아 있는지 관찰한다(H1 재현). 수정 후에는 그룹 회수를 확인한다.
