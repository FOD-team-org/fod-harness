## 4. 새 발견

### 중간

**M1. 죽은 `spawn:` 기록과 foreign 기록이 레지스트리에 영구히 남아 CLEANUP이 계속 실패함**
- 위치: `src/core/cleanup.ts:32`, `:37`, `:43`
- 재현:
  1. 메모리 압박으로 ps가 타임아웃해 `spawn:` identity로 등록된 codex 또는 verify 기록을 만든다. 또는 등록된 pid가 죽고 다른 프로세스가 그 pid를 재사용하게 한다(foreign).
  2. `fodh cleanup run --scope all`을 실행한다.
  3. 기록은 unverified로 남고 지워지지 않는다. ok:false, exit 1이 된다.
  4. CLEANUP.md는 한 번 재시도한 뒤에도 실패하므로 paused(cleanup)로 간다. 이후 실행할 때마다 같은 결과가 나온다.
- 수정안:
  - `spawn:` 기록이고 `!groupAlive(pgid)`이면 신호 없이 기록만 지운다.
  - foreign 기록은 신호 없이 지우고 보고만 한다(pid가 재사용됐으므로 원 프로세스는 이미 없다).
  - ok:false는 살아 있는 unverified 그룹에만 적용한다.
  - 죽은 `spawn:` 기록과 foreign 기록이 지속되는 경우의 테스트를 추가한다.

**M2. updateState가 커밋 전에 runCleanup을 예외 처리 없이 호출함**
- 위치: `src/core/state.ts:50-53` (cleanup), `:54-61` (CAS 커밋), `:63` (notify)
- 재현(두 가지):
  - `/cleanup`이 harness-cleanup 락을 잡고 오래 걸리는 동안 provider가 `paused(billing)`이나 `WAIT_RETRY` 전이를 요청한다. runCleanup은 락을 최대 120초 기다린 뒤 예외를 던지고, 전이는 기록되지 않는다.
  - runCleanup 안에서 어떤 예외(ps 실패 등)가 나도 전이가 사라진다.
- 추가 문제:
  - 대기가 긴 동안 상태는 여전히 이전 상태여서 크래시 창이 생긴다.
  - CAS 재시도마다 cleanup을 다시 돈다(L11).
  - 커밋 후 notify(63)에서 예외가 나면 호출자에게 실패처럼 보인다.
- 수정안: 먼저 커밋하고 그 뒤에 best-effort로 cleanup을 호출한다(try/catch, 실패는 ledger에 기록). notify도 try/catch로 감싼다. 적어도 cleanup 예외는 삼키고 커밋은 진행해야 한다.

**M3. 메모리 타이머의 decidePending이 `pending` 가드 밖에서 돌아 같은 record를 두 번 결정함**
- 위치: `extensions/watcher/index.ts:86-89` (60초 타이머), `:103` (poll 경로와 가드)
- 재현:
  1. codex-done record가 생긴 직후 60초 메모리 타이머와 poll 타이머가 같은 틱에 겹치게 한다.
  2. 두 경로가 같은 record로 결정을 내린다.
  3. 두 번째 경로는 buildPrompt 전에 stale로 해소되거나(orchestrator 216-222 부근), 메모리 압박일 때 runCleanup과 경고가 두 번 나간다.
- 수정안: 메모리 틱도 같은 `run`/공유 promise 직렬화를 타게 하거나, record별 in-flight Set을 둔다. 동시 호출 테스트를 추가한다.

**M4. 메모리 회복이 paused(memory)에서만 처리되어 WAIT_RESOURCE와 lastPaused=memory 조합이 고착됨**
- 위치:
  - `extensions/orchestrator/index.ts:245-250`
  - `src/core/pick.ts:17` (decidePick → WAIT_RESOURCE)
  - `src/core/state.ts:47` (lastPaused), `:168` (해제 조건)
  - `src/core/codex.ts:45` (lastPaused memory면 거부)
- 재현:
  1. critical로 paused(memory)가 된다.
  2. 사용자가 수동으로 PICK을 한다.
  3. pick이 자원 부족으로 WAIT_RESOURCE에 들어간다. lastPaused='memory'는 유지된다.
  4. 메모리가 회복돼도 recovered 분기는 state가 paused일 때만 동작하므로 아무 일도 하지 않는다. startCodex는 계속 거부된다.
- 수정안: recovered 분기에서 `WAIT_RESOURCE && lastPaused==='memory'`도 처리한다(lastPaused 해제 → PICK → autoResume). 이 경로의 테스트를 추가한다.

**M5. 메모리 압박, paused 전이, `/cleanup`이 실행 중인 `fodh verify run`을 죽이고 테스트 실패처럼 보이게 함**
- 위치:
  - `src/core/cleanup.ts:22-27` (protectedGroups에 verify가 없음)
  - `src/core/verify.ts:20-97`
  - `extensions/orchestrator/index.ts:237-240`
- 재현:
  1. VERIFY 상태에서 `fodh verify run --heavy`로 긴 테스트를 돌린다.
  2. 메모리 압박 틱이나 `/cleanup`을 발생시킨다.
  3. processes()가 kind 'verify' 그룹을 회수한다.
  4. verify는 exit null, 실패 결과를 반환한다. brain은 이것을 코드 결함으로 읽고 FIX로 간다.
- 수정안: 살아 있는 heavy 슬롯을 쥔 verify 기록은 보호 대상에 넣는다. 또는 verify 결과에 `interrupted: 'cleanup'`을 표시하고 VERIFY.md에서 재실행하도록 안내한다.

**M6. worktree 제거 조건과 CLEANUP 순서가 순환해서 태스크 흐름에서 worktree가 지워지지 않음**
- 위치: `src/core/cleanup.ts:123` (task done이어야 함), `templates/CLEANUP.md` (cleanup-ok 다음에 status done)
- 재현:
  1. 태스크가 CLEANUP 상태에서 `cleanup run --task <id> --scope all`을 실행한다.
  2. 태스크가 아직 done이 아니므로 worktrees()가 건너뛴다.
  3. 이후 done이 되지만 그 태스크로 cleanup을 다시 실행하지 않는다. worktree가 쌓인다.
- 수정안: state가 CLEANUP이고 대상이 현재 태스크이면 허용한다. removeWorktree는 이미 CLEANUP 상태를 허용한다. 조건은 delegation 없음과 git clean만 유지한다.

### 낮음

- **L1** registerProc(`codex.ts:97`)이 `updateState({delegation})`(약 104)보다 먼저 실행된다. 그 사이에 cleanup이 돌면 새 supervisor를 회수할 수 있다. delegation을 먼저 기록하거나, 등록 시 protected 표식을 붙인다.
- **L2** `tool-groups.ts:19-24`의 witness 갱신이 재사용된 pgid를 채택할 수 있다. 새 witness의 시작 시각이 이전 샘플 시각 이하인지 확인한다.
- **L3** `watcher.ts` 약 285줄의 recovery 락 경로를 `lock.ts`의 재귀 mkdir이 만들기 때문에, 이미 지워진 `codex/<runId>` 디렉터리가 다시 생긴다. 락 전에 존재 확인을 하거나 락 위치를 run 디렉터리 밖으로 옮긴다.
- **L4** `memory.ts:40` 회복 조건 `< swapWarnGB-2` 때문에 swapWarnGB ≤ 2이면 영원히 회복하지 못한다. 또 sampleMemory의 `pressure: swapUsedGB > 8`이 설정값 대신 고정값이다. config.ts:139의 최소값을 3 이상으로 두거나 비율로 계산하고, pressure에 설정값을 쓴다.
- **L5** notify의 60초 rate limit이 프로세스 로컬 Map이다. CLI의 updateState 알림과 확장의 autoResume 알림이 macOS 알림을 중복으로 보낸다. ledger에 기반한 dedupe를 쓴다.
- **L6** 비활성 상태에서 critical이 오면 래치만 걸리고 paused는 되지 않는다. startCodex는 `lastPaused`만 보므로 허용될 수 있고, 알림은 "새 위임을 중단했습니다"라고 말한다. 비활성일 때의 문구와 동작을 맞춘다.
- **L7** storage의 rebuildablePaths가 등록된 worktree 경로를 보호 목록에 넣지 않는다. worktree 레지스트리 경로를 protectedPaths에 추가한다.
- **L8** storage의 확인 후 rm(`cleanup.ts:87`)에 작은 TOCTOU 창이 있다. rm 직전에 lstat를 다시 하는 것으로 충분하다.
- **L9** reportUnregistered(`watcher.ts:343`)가 GradleDaemon 같은 무관한 ppid-1 프로세스를 보고하고 명령줄 전체를 기록한다. 명령줄은 redact하거나 잘라서 기록한다.
- **L10** cancel의 7초 폴링이 supervisor 내부 예산(5+2초)과 거의 같아서 빠듯하다. 10초 정도 여유를 둔다.
- **L11** updateState의 CAS 루프에 상한이 없고, 재시도마다 cleanup을 다시 실행한다. 재시도 상한을 두고 cleanup을 루프 밖으로 뺀다(M2와 함께 수정).

## 5. 실기 권장 (4개 이내)

1. **실제 ps로 reclaim 확인**: codex 위임을 시작한 뒤 `/cleanup`, cancel(N11 ledger 1건, finishedAt), verify timeout을 확인한다. 샌드박스에서 실패하던 12개 테스트의 실제 동작을 대체 확인하는 용도다.
2. **Pi TUI에서 메모리 감시 전 구간**: pressure → critical → recovered를 확인한다. 수동 PICK 후 WAIT_RESOURCE 경로(M4)도 포함한다.
3. **슬롯 경합**: codex 실행 중 `fodh verify run --heavy`를 실행해 거부되는지 확인한다. verify 도중 메모리 압박이나 `/cleanup`이 오면 결과가 어떻게 되는지도 본다(M5).
4. **알림과 CLEANUP 흐름**: macOS osascript 알림에 따옴표와 줄바꿈이 섞인 문구를 보낸다. 한 태스크를 CLEANUP → done까지 보낸 뒤 worktree가 실제로 지워졌는지 확인한다(M6).

### 7-2. M1과 P1 "재사용 PID 보존" 원칙

**충돌하지 않는다.** 원 프로세스 그룹은 이미 없으므로 안전하다. 단, codex의 tool 그룹은 예외다(N2).

- **P1 원칙의 대상**: 재사용된 pid의 새 주인에게 신호를 보내지 않는 것이다. M1은 신호 없이 레지스트리 기록만 지운다(cleanup.ts:38-42, 58). 새 주인 프로세스는 건드리지 않으므로 원칙의 본뜻을 지킨다.
- **원 그룹이 이미 없다는 근거**:
  - 등록 경로 세 곳 모두 `pgid: pid`로 등록한다. 그룹 리더를 detached로 띄운 기록이라는 뜻이다(codex.ts:99, verify.ts:61, provider/runner.ts:165-166).
  - macOS(XNU)와 Linux 커널은 살아 있는 프로세스 그룹 번호(와 세션 번호)와 같은 값을 새 pid로 배정하지 않는다.
  - 따라서 pid가 재사용되어 foreign이 됐다면 원래 pgid 그룹의 구성원은 하나도 남아 있지 않다. codex 자식은 `detached:false`로 같은 그룹에 있다(codex-supervisor.ts:77).
  - 신호를 보낼 대상 자체가 없으므로 기록 제거가 곧 올바른 마감이다.
  - 기존에 unverified로 영구 보존하던 방식은 과보수였다. 그 결과가 M1의 영구 실패였다.
- **예외(N2)**: codex가 띄운 도구 프로세스는 codex와 다른 별도 그룹(meta.toolGroups)에 있다. 이 그룹들은 위의 논증에 포함되지 않는다. 자세한 내용은 7-3 N2.

### 7-3. 2차에서 새로 생긴 결함

**N1 (중간) 소유자가 죽은 verify 자식이 영구 보호되어 어떤 정리로도 회수되지 않음**
- 위치: `src/core/cleanup.ts:29-31`. 연관: `src/core/slots.ts:11-22`, `src/core/verify.ts:33, 57-61`
- 재현:
  1. brain이 Pi bash 도구로 `fodh verify run --heavy`를 실행한다. 검증 명령은 멈추는 테스트(watch 모드나 열린 핸들)다.
  2. 사용자가 Esc를 누르거나 bash 타임아웃이 난다. Pi가 셸 그룹에 SIGKILL을 보낸다(shell.js:177). verify CLI가 죽고, SIGTERM 핸들러와 30분 타이머도 함께 사라진다.
  3. detached로 띄운 검증 자식은 계속 살아 있고 신원도 owned다. 그래서 `protectedProcessGroups`가 이 그룹을 보호한다.
  4. 이후 memory-pressure, WAIT/paused 전이의 정리, `/cleanup`, session_shutdown 모두 이 그룹을 protected로 건너뛴다. cleanupReport에서도 잔존 수에 들어가지 않는다.
  5. heavy 슬롯도 자식이 살아 있으므로 계속 살아 있는 것으로 판정된다(slots.ts:15-16). codex 위임이 막힌다.
- 영향: 1차에서는 정리가 이 고아를 회수했다. 2차에서 M5 보호가 들어가면서, P4의 목적인 메모리 방어가 이 고아를 영구히 회수하지 못하게 됐다.
- 수정안:
  - verify 기록에 소유 CLI의 `ownerPid`와 `ownerStartedAt`을 저장한다(verify.ts:61, `process.pid`와 그 시작 시각).
  - `protectedProcessGroups`는 소유 CLI의 신원이 owned일 때만 보호한다. 소유 CLI가 죽었으면 일반 회수 대상으로 둔다.
  - heavy 슬롯도 같은 기준으로 판정한다. 슬롯 owner의 pid가 죽었으면 child가 살아 있어도 회수 대상으로 넘긴다.
  - 테스트: 소유 pid가 죽고 child가 owned인 verify 기록 → 회수(또는 unverified), protected 아님.

**N2 (중간) 비정상 종료한 codex 기록을 stale로 먼저 처리해서 tool 그룹 회수를 건너뜀**
- 위치: `src/core/cleanup.ts:54`(isStaleProcess가 57줄의 reclaimCodexOwner보다 먼저 실행됨), `:38-42`, `:58`, `src/core/reclaim.ts:14`
- 재현:
  1. codex supervisor와 codex가 OOM이나 SIGKILL로 함께 죽는다. codex가 띄운 도구 그룹(별도 pgid, meta.toolGroups에 witness 기록)은 살아 있다.
  2. watcher의 recoverLostRuns(60초 조건, watcher.ts:285)보다 먼저 WAIT/paused 전이의 정리, `/cleanup`, 또는 `--cleanup-ok`가 실행된다.
  3. 그러면 `isStaleProcess`가 dead이면서 그룹 없음으로 판단해 `retireStaleProcess`로 meta를 lost로 마감하고 기록을 지운다.
  4. 이제 meta.finishedAt이 있으므로 recoverLostRuns도 이 run을 건너뛴다(watcher.ts:285).
  5. 1차에서는 57줄의 `reclaimCodexOwner`가 gone 경로(codex-reclaim.ts:16-18)로 검증된 도구 그룹을 회수했다. 2차에서는 그 경로가 실행되지 않는다. 도구 그룹(jest, gradle 등)이 누수되고 보고되지도 않는다.
  6. foreign 경로(58줄)도 비슷하다. `skippedGroups`가 있어도 무시하고 stale로 처리한다. 1차에서는 잔존으로 보고했다.
- 수정안:
  - codex 기록은 `isStaleProcess`로 먼저 걸러내지 말고 `reclaimCodexOwner`를 먼저 호출한다. gone이면 검증된 도구 그룹을 회수한 뒤 retire한다. foreign이면 도구 그룹을 자체 witness로 검증해서 회수한다. 검증이 안 되면 skippedGroups를 residual이나 reportToolResidual로 보고한다.
  - 즉 `isStaleProcess` 선처리는 `kind !== 'codex'`이거나 `meta.toolGroups`가 비어 있을 때만 적용한다. cleanupReport(reclaim.ts:14)도 같다.
  - 테스트: 죽은 codex 기록과 살아 있는 owned 도구 그룹 → 도구 그룹 회수 후 stale. foreign과 살아 있는 도구 그룹 → 보고.

**N3 (낮음) critical 래치가 임계 아래 표본 하나로 풀림**
- 위치: `src/core/memory.ts:37`
- 내용: 임계 아래 표본이 한 번만 나와도 `watch.critical = false`가 된다. 중립 구간(임계-2 이상, 임계 이하)이라도 마찬가지다. 비활성 상태에서 critical이 오면 lastPaused가 설정되지 않으므로, 이 경우 L6 거부(codex.ts:45)가 회복 판정(5분 연속 `< 임계-2`) 전에 풀린다. 활성 경로는 lastPaused로 막히므로 영향이 없다.
- 수정안: critical을 `memory-recovered` 이벤트를 낼 때만 해제한다. 또는 L6 거부 조건을 `critical || over`로 한다.
